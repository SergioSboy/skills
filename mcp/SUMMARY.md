# Протокол MCP

Model Context Protocol (MCP) - это открытый стандарт подключения ИИ-приложения к внешним системам

Основные возможности:
- Доступ к внешним источникам данных
- Доступ к внешним сервисам (tools)

## Зачем нужен MCP?

К внешним системам также можно обращаться через 
- API

Какие языковые модели взаимодействуют с внешними системами?
- OpenAI GPTs Function Calling
- Anthropic Tools
- Google Vertex AI / Gemeni Functions
- LangChain Tools / LangGraph

Стандартизированный протокол который позволят подключить к любой LLM, нужный сервис

## Типы стандартов

Проприетарный стандарт (закрытый):
- OpenAI API

Открытый стандарт (опубликованный в открытом доступе):
- Model Context Protocol
- A2A (agent2agent)

## Премущества стандартных протоколов

Разработчики сервисов (tools)
- Сервис разрабатывается один раз и доступен всем ИИ агентам, использующим протокол
- Простота разработки и реализации сервиса

ИИ агенты
- Доступно большое количество сервисов

Пользователи
- Могут использовать более "умные" и "умелые" ИИ приложения

MCP для ИИ агентов - это тоже самое что TCP/IP для интернета

## MCP сервер

Типы серверов MCP
- Локальный (запускается на локальном компьютере)
- Удаленный (запускается на сервере в интернете)

MCP сервер предоставляет клиенту три типа примитивов
- Tools - инструменты для вызова
- Resources - какие-то источники данных, файлы, БД
- Prompts - промпты

Основные компоненты MCP

## Уровни протокола MCP

- Уровень данных (Data Layer)
   Определяет что именно клиент и сервер передают друг другу и в каком формате
- Транспортный уровень (Transport Layer)
   Задает механизмы передачи данных

## Уровень данных

Определяет протокол коммуникации между клиентов и сервером MCP

Уровень данных основан на JSON-RPS 2.0
- Структура сообщений
- Семантика сообщений

Задачи уровня данных:
- Управление жизненным циклом
   Занимает инициализацей вызовов примитивов сервера и клиента, разрывом соединения и контролем за тем что задачи  выполняются
- Примитивы сервера: Tools, Resources, Prompts
   Позволяет выдавать эти примитивы клиентам
- Примитивы клиента: Sampling, Elicitation, Logging
   Позволяет использовать примитивы клиента
- Утилиты
   Позволяют решать технические задачи, проверка соединения между клиентом и сервером


## Типы сообещний уровня данныхх

- Запрос (Request)
- Ответ (Response)
- Уведомление (Notification)

### Пример запроса уровня данных

```json
{
   "jsonrpc": "2.0",
   "id": 2,
   "method": "tools/list"
}
```

### Пример ответа уровня данных

```json
{
   "jsonrpc": "2.0",
   "id": 2,
   "result": {
      "tools": [
         0: {
            "name": "resolver",
            "title": "Resolver 1"
         }
      ]
   }
}
```

### Пример уведомления уровня данных

```json5
{
   "jsonrpc": "2.0",
   "method": "notifications/tools/list_changed"
}
```

## Транспортный уровень

Определяет механизмы передачи данных между клиентом и сервером

Механизмы передачи данных:
- Stdio - взаимодействие с локальным MCP-сервером
- Streamable HTTP - взаимодействие с удаленным MCP-сервером по сети
- Custom transport - можно реализовать свой собественный вариант транспортного уровня

Задачи транспортного уровня:
- Установка соединения между клиентом и сервером
- Формирование сообщений
- Обеспечение безопасной передачи данных

### Streamable HTTP

Позволяет подключаться к удаленному серверу

Используются протоколы HTTP/HTTPS
- Streamable - данные большого объема могут передаваться в нескольких сообщениях
- Сервер может использовать Server-Sent Events для отправки информации клиенто по своей инициативе

Точка доступа Streamable HTTP
- Должны поддерживать методы GET и POST

# Уровень данных в MCP

Уровень данных определяет протокол для коммуникации между клиентом и сервером

## Структура запроса JSON-PRS 2.0

- jsonrpc
   Строка с версей 
- method
   Название метода который хотим вызвать
- params
   Параметры метода, который хотим вызвать (позиционные или именнованные)
- id
   Идентификатор запроса. Не обязательно для запросов типа "Уведолмление"

## Структура ответа JSON-RPC 2.0

- jsonrpc
   Строка с версией
- result
   Результат выполнения запроса
- error
   Описание ошибки, возникшей при выполнении запроса
- id
   Идентификатор ответа. Должен совпадать с идентификатором соответствующего запроса.

## JSON-RPC 2.0 в MCP

Типы сообщений
- Запрос, ответ, уведомление

Примитивы сервера в MCP
- tools
- resources
- prompts

Этапы взаимодействия клиента и сервера MCP
- Инициализация - установка соединения между клиентом и сервером
- Обнаружение примитивов, которые предоставляет сервер - какие инструменты есть на сервере для чего они используются и как именно клиент может их вызвать
- Обращение к нужному примитиву

## Спецификация

[Model Context Protocol](https://modelcontextprotocol.io) (MCP) — это открытый протокол, обеспечивающий бесшовную интеграцию между LLM-приложениями и внешними источниками данных и инструментами. Независимо от того, создаёте ли вы IDE на основе ИИ, улучшаете чат-интерфейс или разрабатываете собственные AI-рабочие процессы, MCP предоставляет стандартизированный способ подключения LLM к необходимому им контексту.

Эта спецификация определяет авторитетные требования протокола, основанные на TypeScript-схеме в [schema.ts](https://github.com/modelcontextprotocol/specification/blob/main/schema/2026-07-28/schema.ts).

Руководства по реализации и примеры доступны на [modelcontextprotocol.io](https://modelcontextprotocol.io).

Ключевые слова «ДОЛЖНО» (MUST), «НЕ ДОЛЖНО» (MUST NOT), «ТРЕБУЕТСЯ» (REQUIRED), «СЛЕДУЕТ» (SHOULD), «НЕ СЛЕДУЕТ» (SHOULD NOT), «РЕКОМЕНДУЕТСЯ» (RECOMMENDED), «НЕ РЕКОМЕНДУЕТСЯ», «МОЖЕТ» (MAY) и «ОПЦИОНАЛЬНО» (OPTIONAL) в этом документе следует трактовать согласно [BCP 14](https://datatracker.ietf.org/doc/html/bcp14) ([RFC2119](https://datatracker.ietf.org/doc/html/rfc2119), [RFC8174](https://datatracker.ietf.org/doc/html/rfc8174)), когда и только когда они написаны полностью заглавными буквами.

## Обзор

MCP предоставляет стандартизированный способ для приложений:
- делиться контекстной информацией с языковыми моделями;
- предоставлять инструменты и возможности AI-системам;
- создавать композитные интеграции и рабочие процессы.

Протокол использует сообщения [JSON-RPC](https://www.jsonrpc.org/) 2.0 для организации связи между:
- **Хостами** — LLM-приложениями, инициирующими соединения;
- **Клиентами** — коннекторами внутри хост-приложения;
- **Серверами** — сервисами, предоставляющими контекст и возможности.

MCP частично заимствует идеи у [Language Server Protocol](https://microsoft.github.io/language-server-protocol/), который стандартизирует поддержку языков программирования во всей экосистеме инструментов разработки. Аналогичным образом MCP стандартизирует интеграцию дополнительного контекста и инструментов в экосистему AI-приложений.

### Базовый протокол
- Формат сообщений [JSON-RPC](https://www.jsonrpc.org/)
- Независимые запросы без сохранения состояния
- Согласование возможностей для каждого запроса

### Возможности
Серверы предлагают клиентам любые из следующих возможностей:
- **Resources (Ресурсы)** — контекст и данные для пользователя или модели ИИ;
- **Prompts (Подсказки)** — шаблонные сообщения и рабочие процессы для пользователей;
- **Tools (Инструменты)** — функции, которые может выполнять модель ИИ.

Клиенты могут предлагать серверам следующую возможность:
- **Elicitation (Запрос уточнений)** — инициированные сервером запросы дополнительной информации у пользователей.

### Дополнительные утилиты
- Конфигурация
- Отслеживание прогресса
- Отмена операций
- Отчёты об ошибках

### Расширения
Помимо базового протокола, MCP определяет опциональные [расширения](/extensions/overview), добавляющие модульную, специализированную или экспериментальную функциональность. Расширения всегда подключаются по желанию и требуют явной поддержки как клиентом, так и сервером, согласуемой при инициализации. Среди заметных расширений:
- **[Tasks (Задачи)](/extensions/tasks/overview)** — асинхронное выполнение длительных операций с опросом, вводом в процессе выполнения и устойчивыми дескрипторами;
- **[Skills over MCP (Навыки через MCP)](/community/working-groups/skills-over-mcp)** — насыщенные структурированные инструкции для рабочих процессов агентов, обнаруживаемые и используемые через MCP;
- **[MCP Apps (Приложения MCP)](/extensions/apps/overview)** — интерактивные элементы интерфейса (графики, формы, видеоплееры), отображаемые встроенно в диалогах.

## Безопасность и доверие

Model Context Protocol предоставляет мощные возможности за счёт произвольного доступа к данным и путей выполнения кода. Вместе с этой мощью появляются важные аспекты безопасности и доверия, которые все разработчики реализаций обязаны тщательно учитывать.

### Ключевые принципы

1. **Согласие и контроль пользователя**
    - Пользователи должны явно соглашаться на любой доступ к данным и операции и понимать их суть.
    - Пользователи должны сохранять контроль над тем, какие данные передаются и какие действия выполняются.
    - Разработчикам следует предоставлять понятные интерфейсы для проверки и авторизации действий.

2. **Конфиденциальность данных**
    - Хосты должны получать явное согласие пользователя перед предоставлением его данных серверам.
    - Хосты не должны передавать данные ресурсов куда-либо ещё без согласия пользователя.
    - Данные пользователя должны быть защищены соответствующими средствами контроля доступа.

3. **Безопасность инструментов**
    - Инструменты представляют собой произвольное выполнение кода и должны рассматриваться с соответствующей осторожностью.
        - В частности, описания поведения инструментов, такие как аннотации, следует считать недоверенными, если они не получены от доверенного сервера.
    - Хосты должны получать явное согласие пользователя перед вызовом любого инструмента.
    - Пользователи должны понимать, что делает каждый инструмент, перед тем как разрешить его использование.

### Рекомендации по реализации

Хотя сам MCP не может обеспечивать соблюдение этих принципов безопасности на уровне протокола, разработчикам **СЛЕДУЕТ**:
1. Встраивать в свои приложения надёжные механизмы согласия и авторизации.
2. Предоставлять чёткую документацию по аспектам безопасности.
3. Реализовывать соответствующие средства контроля доступа и защиты данных.
4. Следовать лучшим практикам безопасности в своих интеграциях.
5. Учитывать аспекты конфиденциальности при разработке функциональности.
