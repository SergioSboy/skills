# Проектирование сложных архитектур данных

## Цель

Научиться проектировать архитектуру данных для нескольких систем и хранилищ:
определять владельцев данных, потоки между ними, способы согласования и
аналитический контур с контролем качества.

## План изучения

### 1. Ландшафт данных

- Составлять карту источников, хранилищ и потребителей данных.
- Классифицировать данные: операционные, справочные, аналитические, журналы.
- Определять систему-источник истины (system of record) для каждой сущности.
- Выявлять дублирование данных и неявные зависимости между системами.

### 2. Владение и границы

- Применять принцип «база данных на сервис» и запрет общей БД между сервисами.
- Назначать владельца для каждого набора данных.
- Определять контракты данных: схема, семантика, частота обновления, SLA.
- Разобрать подходы Data Mesh и централизованной платформы данных.

### 3. Polyglot persistence

- Сочетать несколько типов хранилищ в одной системе под разные задачи.
- Синхронизировать данные между ними без двойной записи.
- Учитывать стоимость эксплуатации каждого дополнительного хранилища.
- Описывать, какое хранилище главное при расхождении.

### 4. Интеграция и перемещение данных

- Разобрать пакетную загрузку (ETL, ELT) и потоковую обработку.
- Изучить CDC (Change Data Capture) на примере Debezium.
- Использовать брокер сообщений как журнал изменений.
- Проектировать идемпотентную загрузку и повторную обработку.

### 5. Согласованность в распределённой системе

- Разобрать распределённые транзакции и причины отказа от 2PC.
- Применять Saga, Outbox и компенсирующие действия.
- Проектировать сверку (reconciliation) данных между системами.
- Определять допустимую задержку согласования для каждого потока.

### 6. Аналитический контур

- Разобрать хранилище данных (DWH), озеро данных и lakehouse.
- Изучить слои данных: сырые, очищенные, витрины.
- Моделировать витрины: звезда, снежинка, Data Vault.
- Отделять аналитическую нагрузку от операционных БД.

### 7. Качество, метаданные и lineage

- Описывать проверки качества: полнота, уникальность, свежесть, корректность.
- Вести каталог данных и описание полей.
- Строить lineage: откуда пришло значение и через какие преобразования.
- Реагировать на нарушение контракта данных у источника.

### 8. Безопасность и жизненный цикл

- Классифицировать персональные и чувствительные данные.
- Применять маскирование, шифрование и разграничение доступа.
- Определять сроки хранения, архивирование и удаление.
- Планировать резервное копирование и восстановление для всего ландшафта.

## Практический проект

Спроектировать архитектуру данных для платформы заказов:

- карта данных: сервисы заказов, оплаты, склада и каталога, их хранилища и
  потребители;
- источник истины и владелец для каждой сущности;
- контракты данных для двух потоков между сервисами;
- передача изменений заказов через outbox или CDC в брокер сообщений;
- сверка заказов и платежей с отчётом о расхождениях;
- аналитический контур: сырой слой, очищенный слой и витрина продаж;
- проверки качества и lineage для витрины продаж;
- классификация персональных данных и правила их хранения;
- диаграммы потоков данных и ADR по ключевым решениям.

## Критерии завершения

- У каждой сущности есть один источник истины и владелец.
- Между сервисами нет общей БД и двойной записи без гарантий доставки.
- Для каждого потока определены контракт, задержка и способ повторной
  обработки.
- Расхождения между системами обнаруживаются сверкой.
- Аналитическая нагрузка не влияет на операционные БД.
- Для витрины можно показать происхождение каждого показателя.
