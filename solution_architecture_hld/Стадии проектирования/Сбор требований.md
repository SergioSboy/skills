# Функциональные требования

- Что мы вообще собираемся делать? 
- Что будет делать наша система?
- Какие основные фичи? Самые важные фичи

Порядок действий:

1. Уточнение функций
2. Выявление наиболее важных функций

Результат:

Набор основных важных функций необходимых к реализации


Конвертируем функции в список действий пользователя:

Список того что может делать пользователь в сервисе. 

Это также требует перерасмотра и уточнений от заказчика.

# Нефункциональные требования

## Расчет нагрузки

Нагрузка:
- Сколько будет пользователей в системе?
- Как часто они нажимают на кнопки / делают запросы?

Из получнной нагрузки расчитываем:
- С помощью этих данных происходит расчет RPS на чтение/запись/редактирование
- Размер передаваемых данных (байт)

Сколько пользователей?

- Считаем в AU (active users)
- MAU (monthly active users)
- DAU (daily active users)

Уточнение про MAU, нельзя просто разделить на 30 дней или умножить все завист от системы

Используем в расчетах вовлеченность пользователей и считаем:

1000 MAU, вовлечнность = 50%

1000 * 0.5 = 500 DAU
 
Как часто пользователи нажимают на кнопки?

Из списка действий пользователей с этапа функциональных требований мы формируем количество действий пользователя в день

Что может делать польователь - Сколько раз в сутки он это делает

## Расчет RPS

Исходя из полученных данных можно посчитать RPS:

86400 секунд в сутках, но это число нельзя использовать без учета пиковой нагрузки:

- В какие-то дни пользователей больше?
- В какие-то часы пользователей больше?
- Есть ли сезонность?

После уточнения количества часов пользователеской активность выводим получившийся результат
(8 часов в день = 28800)

Считаем:

28800 секунд

500 DAU 

Формула:

Количество действий в сутки * DAU / количество пользовательской активности 

После этого можно посчитать отношения чтение/запись:

Общее количество запросов на чтение / Общее количество запросов на запись

## Расчет размера хранимых данных

1. Берем всю нагрузку на запись. Выясняем какие действия создают реальные записи в Базу данных (занимают место)
2. Узнаем сколько весит единица данных.

Формула расчета:

RPS * размер единицы данных * количество секунд в году
                                                           
## Технические характеристики системы

- Availability (доступность. Время непрерывной работы без простоев)
- Reliability (надежность. Процентов ответов без ошибок)
- Consistency (согласованность данных. Строгая или конечная)
- Latency (время ответов API)

## SLA

Технические характеристики задаются через SLA

SLA - service level agreement. Цель, которую задал пользователь

Пример:

API для смежной команды должна работать SLA: latency: 200ms

## SLO

SLO - service level objective. Цель, которая ставиться нашему сервису (с запасом от SLA)

Пример:

API внутри сервиса должно работать SLO: latency: 150ms

## SLI

SLI - service level indicator. Метрика для цели

Пример:

После каждого вызова API фиксируется время ответа. За какой-то промежуток времени высчитывается среднее значение.
Если средний показатель превышает 400ms, срабатывает alert.

## Перцентиль

Перцентиль - это разновидность квантилей

Квантиль - это разделение всех данных на промежутки одинакового размера. Например, квартиль.

Пример с квартилем:

Какой-то промежуток времени разделен на 4 части (q25, q50, q75)

q50 latency: 500ms

Обозначает, что половина запросов должна отвечать меньше 500ms


Пример с перцентилей:

Какой-то промежуток времени разделен на 100 равных частей (p1, p2, p3,... p99)

p90 latency: 1000ms

Обозначает что 90% всех запросов должно отвечать быстрее чем за 1000ms

## Как задается Availability?

availability = 99.99

Обозначает, что 99.99 времени система должна быть доступна

То есть система может быть недоступна только 0.01% времени

В абсолютных числах

86400 * 0.01 * 0.01 = 8.64 секунды в день
8.64 * 365 = 3153 секунды в год

## Каз задается Reliability?

reliability = 99.99

Обозначает, что 99.99% запросов должны выполнятся без ошибок

То есть допускается 0.01% ошибок за выбранный промежуток времени

SLI мониторится ежедневно и еженедельно


## Разница между 99.9 и 99.99

Availability 99.99: downtime: 8 секунд в день, 52 минуты в год
Availability 99.9: downtime: 1.2 минуты в день, 8.5 часов в год

Чтобы перейти с 99.9 -> 99.99 требуется резервирование ресурсов и настройка инфраструктуры
                                                                      
## Latency

Время ответа какой-то API

Учитываем, что задается изначально SLA, поэтому SLO должно быть с запасом

Важно понимать какое время какие операции занимают
                                            
## Долгие операции и как их избегать

- Чтение c HDD. Выбирать SSD диски или использовать кэш.
- Поход в другой сервис. Выполнять асинхронно, конкурентно, использовать кэш, стараться по возможности избегать.
- Запросы на сервис на дальние расстояния. Использовать CDN.

## Consistency

### Strong consistency

Данные изменились - сразу же везде отображаются новые данные.

Запрещает испоьзовать асинхронность. Необходимо писать в тот сервис из которого происходит чтение.

Сначала сохраняем данные в конечное хранилище, потом отвечаем пользователю.

Из-за этих шагов происходит увеличение latency сервиса.

### Eventual consistency

После изменения данных где-то могут быть все еще старые данныхе но в конечном итоге везде будут новые через какое-то время.

Можно использовать асинхронность. Можно возвращать ответ пользователю, если еще не сохранили данные.


## PACELC

given P choose A or C, else choose L or C
                                         
Выбирем latency, пожертвовали consistency

Записываем в master и сохраняем в slave (используем асинхронную операцию сохранения)
