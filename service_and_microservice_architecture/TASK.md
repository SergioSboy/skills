# Сервисная и микросервисная архитектура

## Цель

Научиться определять границы сервисов и обосновывать, когда разделение системы
на сервисы оправдано, а когда оно добавляет лишнюю сложность.

## План изучения

### 1. Основные понятия

- Разобрать SOA, микросервисы и модульный монолит.
- Отличать сервис как единицу развёртывания от модуля как единицы кода.
- Изучить принципы автономности, слабой связности и владения данными.
- Понять закон Конвея и влияние структуры команд на архитектуру.

### 2. SOA и микросервисы

- Сравнить SOA с ESB и микросервисы со «smart endpoints and dumb pipes».
- Разобрать размер сервиса: по бизнес-возможности, а не по количеству кода.
- Изучить антипаттерн распределённого монолита.
- Понять, почему общая база данных между сервисами нарушает их автономность.

### 3. Определение границ сервисов

- Выделять сервисы по бизнес-возможностям (business capabilities).
- Использовать bounded contexts из DDD как основу границ.
- Оценивать частоту совместных изменений и интенсивность взаимодействия.
- Проверять, что сервис можно изменить и развернуть независимо от других.

### 4. Данные в микросервисах

- Применять принцип database per service.
- Разобрать репликацию данных через события и материализованные представления.
- Изучить Saga, Outbox и CQRS.
- Определить владельца каждой сущности и источник истины.

### 5. Взаимодействие сервисов

- Сравнить синхронные API и асинхронные события.
- Разобрать оркестрацию и хореографию.
- Проектировать контракты API и событий с обратной совместимостью.
- Изучить contract testing (например, Pact).

### 6. Инфраструктурные паттерны

- Изучить API Gateway, Backend for Frontend и service mesh.
- Разобрать service discovery, конфигурацию и управление секретами.
- Применять retry, timeout, circuit breaker и bulkhead.
- Настроить распределённую трассировку и корреляцию запросов.

### 7. Когда разделение оправдано

- Определить признаки: разная нагрузка, разные требования к доступности,
  независимые команды, разный темп изменений, требования безопасности.
- Определить признаки преждевременного разделения: небольшая команда,
  неустойчивые требования, сильная связность сценариев.
- Оценить стоимость разделения: инфраструктура, эксплуатация, согласованность.
- Изучить поэтапное выделение сервисов через Strangler Fig.

### 8. Организация и эксплуатация

- Распределить владение сервисами между командами.
- Определить требования к CI/CD, независимому деплою и откату.
- Описать SLO и зоны ответственности каждого сервиса.
- Подготовить каталог сервисов с владельцами, контрактами и зависимостями.

## Практический проект

Определить границы сервисов для системы заказов:

- список бизнес-возможностей и соответствующих им сервисов
  (заказы, каталог, оплата, склад, доставка, уведомления);
- владелец данных и источник истины для каждой сущности;
- контракты синхронных API и асинхронных событий между сервисами;
- сценарий оформления заказа через оркестрацию или хореографию;
- обоснование для каждого сервиса: почему он выделен или оставлен внутри
  другого;
- перечень случаев, в которых разделение не оправдано, с объяснением.

## Критерии завершения

- Каждый сервис соответствует одной бизнес-возможности и владеет своими данными.
- Отсутствуют общие базы данных и циклические синхронные зависимости.
- Контракты API и событий описаны и поддерживают обратную совместимость.
- Решение о разделении обосновано и содержит оценку его стоимости.
