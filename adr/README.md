# ADR (Architecture Decision Records)

## Цель

Научиться фиксировать архитектурные решения в виде ADR так, чтобы через
полгода было понятно, что решили, почему и какие варианты отвергли.

## План изучения

### 1. Основные понятия

- Разобрать назначение ADR: сохранить контекст и причину решения.
- Отличать архитектурно значимое решение от обычной детали реализации.
- Понять, почему ADR неизменяем после принятия.
- Разобрать журнал решений (decision log) как набор ADR проекта.

### 2. Шаблоны

- Изучить шаблон Майкла Найгарда: контекст, решение, статус, последствия.
- Изучить MADR: варианты, критерии, плюсы и минусы каждого варианта.
- Изучить шаблон Y-statement для краткой записи решения.
- Выбрать шаблон для команды и обосновать выбор.

### 3. Содержание ADR

- Описывать контекст: проблему, ограничения, требования и силы, влияющие на
  решение.
- Перечислять рассмотренные варианты, включая «ничего не менять».
- Сравнивать варианты по явным критериям.
- Записывать последствия: положительные, отрицательные и новые риски.

### 4. Жизненный цикл

- Использовать статусы: proposed, accepted, rejected, deprecated, superseded.
- Заменять решение новым ADR со ссылкой на прежний, а не переписывать старый.
- Нумеровать ADR и давать им понятные заголовки.
- Указывать дату, авторов и участников обсуждения.

### 5. Процесс принятия

- Определять, кто предлагает, обсуждает и утверждает ADR.
- Проводить ревью ADR через merge request.
- Ограничивать время обсуждения и фиксировать несогласие.
- Связывать ADR с задачей, HLD и изменениями в коде.

### 6. Хранение и инструменты

- Хранить ADR в репозитории в Markdown рядом с кодом или документацией.
- Изучить инструменты `adr-tools` и `log4brains`.
- Вести индекс ADR со статусами.
- Делать ADR доступными для поиска новым участникам команды.

### 7. Типичные ошибки

- Запись решения без контекста и альтернатив.
- Подгонка обоснования под уже принятое решение.
- Слишком общие ADR, которые нельзя проверить.
- ADR на каждую мелочь и потеря значимых решений среди шума.

## Практический проект

Вести журнал решений для системы заказов:

- выбрать шаблон ADR и оформить его как файл-образец в репозитории;
- написать минимум пять ADR: выбор базы данных, синхронное или асинхронное
  взаимодействие, выбор брокера, применение CQRS, стратегия аутентификации;
- в каждом ADR — минимум два рассмотренных варианта и критерии сравнения;
- один ADR заменить новым со статусом superseded и взаимными ссылками;
- индекс ADR со статусами и ссылками;
- провести ревью одного ADR через merge request и учесть замечания.

## Критерии завершения

- Каждый ADR содержит контекст, варианты, решение и последствия.
- По ADR можно понять причину решения без устных пояснений.
- Изменённые решения оформлены новыми ADR, старые не переписаны.
- ADR хранятся в репозитории, пронумерованы и собраны в индекс.
- Отрицательные последствия решений записаны так же явно, как положительные.
