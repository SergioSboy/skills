# RESTful API Design

### Ресурсы и представления

Ресурс - это сущность с которой работает API

Например:

- пользователь - `/users/42`
- товар - `/products/42`
- статья - `/articles/42`

Представление - это форма, в которой ресурс передается клиенту. 

Например:

```json
{
  "id": 1,
  "name": "CanCan"
}
```

### Методы GET, POST, PUT, PATCH, DELETE

- GET - получение ресурса;
- POST - создание ресурса или выполнение какой-то операции;
- PUT - полная замена существующего ресурса;
- PATCH - частичное изменение ресурса;
- DELETE - удаление ресурса.

Дополнительно:

- HEAD - получение метаданных;
- OPTIONS - получение информации о доступных возможностях.

### Безопасные и идемпотентные операции

Безопасные:

- GET
- HEAD
- OPTIONS

Операция, которая не должна изменять состояние ресурса на сервере.
Многократное выполнение такого запроса не должно изменять ресурс.

Идемпотентные:

- GET
- PUT
- DELETE
- HEAD
- OPTIONS

Операция, которую можно выполнять один или несколько раз с одним и тем же результатом состояния сервера.



### HTTP-заголовки, content negotiation и кеширование

HTTP-заголовки - дополнительные параметры HTTPS-запроса или ответа. Они передают информацию о 
запросе, ответе и передаваемых данных.

- Content-Type - формат данных в теле запроса или ответа;
  ```
  Content-Type: application/json
  ```
- Accept - какие форматы ответа клиент готов принять;
  ```
  Accept: application/json
  ```
- Authorization - данные для аутентификации/авторизации;
  ```
  Authorization: Bearer <token>
  ```
- Cache-Control - правила кеширования.
- ETag - дентификатор конкретной версии ресурса, используется в частности для проверки актуальности кеша.

Content negotiation - 
механизм, с помощью которого клиент и сервер договариваются о том, в каком формате передать представление ресурса.

Например:

Клиент отправляет:

```
GET /users/42
Accept: application/json
```

Сервер отвечает:

```
Content-Type: application/json

{
  "id": 42,
  "name": "Иван"
}
```

Content-Type описывает тело текущего ответа сообщения, а Accept - предпочтение клиента
относительно ответа.

Кеширование позволяет сохранить ответ и использовать его повторно,
вместо того чтобы каждый раз обращаться к серверу.

Например:

Клиент сделал запрос:

```
GET /products/42
```

Сервер:

```
HTTP/1.1 200 OK
Cache-Control: max-age=3600
```

Это означает, что ответ от сервера можно считать актуальным в течении 3600 секунд.

Чтобы проверить не изменился ли ресурс, используютя условные запросы.

Сервер сначачала отправляет
```
ETag: "abc123"
```

При следующем запросе клиент может отправить:
```
If-None-Match: "abc123"
```

Если ресурс не изменился, сервер отвечает:
```
HTTP/1.1 304 Not Modified
```

### HTTP-статусы

Успешные ответы:

- 200 OK 
  Запрос успешно выполнен, и сервер возвращает результат.

- 201 Created
  Используется, когда запрос создал новый ресурс.

- 204 No Content
  Операция успешно выполнена, но возвращать тело ответа не нужно.

Клиентские ошибки:

- 400 Bad Request
  Сервер не смог нормально обработать запрос из-за его некорректного формата или структуры.

- 401 Unauthorized
  Клиент не прошёл аутентификацию.

- 403 Forbidden
  Сервер знает, кто клиент, но этот клиент не имеет права выполнять операцию.

- 404 Not Found
  Запрашиваемый ресурс не найден.

- 422 Unprocessable Content
  Запрос синтаксически корректный, сервер его понял, но не может выполнить его из-за ошибок в данных.

Ошибки сервера:

- 500 Internal Server Error
  На сервере произошла непредвиденная ошибка, из-за которой он не смог выполнить запрос.

### Версионирование

Версионирование нужно, чтобы изменять API, не ломая существующих клиентов.

Версия в URL:

```
/api/v1/users
```

```
/api/v2/users
```

Версия через Accept:

Подход, когда версию передают через HTTP-заголовок

```
GET /api/users/42
Accept: application/vnd.myapi.v1+json
```

Обратная совместимость:

- Новая версия не должна ломать клиентов старой версии.
- Если старый клиент спокойно игнорирует дополнительные поля, это обычно backward-compatible изменение.
- Старый клиент продолжает получать привычные поля.

другое:

- добавление необязательного поля в response;
- добавление нового endpoint;
- добавление новых необязательных параметров;
- улучшение внутренних деталей реализации без изменения контракта.

Вывод из эксплуатации:

v1 → deprecated

Можно добавить HTTP-заголовки:

```
Deprecation: true
Sunset: Wed, 30 Sep 2027 00:00:00 GMT
```

### Формат ответа

Структура data, meta, errors

Успеншный ответ:

```
{
  "data": {
    "id": 42,
    "name": "John"
  },
  "meta": {}
}
```

Список с пагинацией:

```
{
  "data": [
    {
      "id": 1,
      "name": "John"
    },
    {
      "id": 2,
      "name": "Alice"
    }
  ],
  "meta": {
    "page": 1,
    "per_page": 20,
    "total": 42
  }
}
```

Ошибка:
```
{
  "data": null,
  "errors": [
    {
      "code": "invalid_parameter",
      "field": "sort",
      "message": "Unsupported sort field"
    }
  ]
}
```

page-based

```
GET /api/v1/users?page=2&per_page=20
```

cursor-based pagination

```
GET /api/v1/users?limit=20&cursor=eyJpZCI6MjB9
```

### Аутентификация

С помощью JWT и Authorization
Клиент отправляет:

```
GET /api/v1/users
Authorization: Bearer eyJhbGciOiJIUzI1NiJ9...
```

API keys

API key — простой секрет, который идентифицирует приложение или интеграцию.

```
GET /api/v1/users
X-API-Key: 7f8a9c...
```

Использование:

- server-to-server;
- внутренних сервисов;
- cron/jobs;
- простых интеграций;
- публичного API, где нужен простой идентификатор клиента.

API key обычно не описывает пользователя и его права так подробно, как OAuth.

OAuth 2.0

предназначен прежде всего для делегированного доступа.

OAuth особенно полезен, когда:

- есть сторонние приложения;
- пользователь должен разрешать доступ к своим данным;
- нужны scopes;
- нужен refresh token;
- нужен централизованный authorization server.

Безопасное хранение

Для Rails можно использовать

```
bin/rails credentials:edit
```

### Rate Limiting

Rate limiting — ограничение количества запросов за определённый промежуток времени,
чтобы защищать API от brute-force, DDoS на уровне приложения,
случайного перегруза и злоупотребления API.


- Ограничивать по IP

  Например, не больше 100 запросов в минуту с одного IP

- Ограничивать по пользователю или токену

  IP не всегда хороший идентификатор.
  Например, тысячи пользователей могут находиться за одним NAT.

- Разные лимиты для разных endpoint'ов

- Необходимо добавить хранение лимита в общем Storage (REDIS)

rate limiting должен работать не только внутри одного Rails-процесса,
а учитывать реальную production-схему Load Balancer → несколько Rails → общий Redis
