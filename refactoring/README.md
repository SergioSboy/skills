# Рефакторинг

## Цель

Научиться улучшать структуру существующего кода без изменения его поведения:
находить «запахи» кода, применять приёмы рефакторинга небольшими безопасными
шагами и подтверждать сохранность поведения тестами.

## План изучения

### 1. Основные понятия

- Разобрать определение рефакторинга и его отличие от переписывания и
  исправления ошибок.
- Понять, зачем нужен рефакторинг: читаемость, снижение стоимости изменений,
  поиск ошибок.
- Изучить, когда рефакторить: правило трёх, перед добавлением функции, при
  исправлении ошибки, во время Code Review.
- Разобрать, когда рефакторинг не нужен или опасен: код под замену, отсутствие
  тестов, сжатые сроки релиза.

### 2. Технический долг

- Разобрать виды технического долга: осознанный и случайный, разумный и
  безрассудный.
- Научиться фиксировать долг в задачах и оценивать стоимость его обслуживания.
- Планировать рефакторинг в рамках обычной работы, а не отдельными
  «большими переделками».

### 3. Запахи кода (Code Smells)

- Изучить запахи раздувания: длинный метод, большой класс, длинный список
  параметров, одержимость примитивами, группы данных.
- Изучить запахи нарушения ООП: switch-операторы, отказ от наследства,
  временное поле.
- Изучить запахи, мешающие изменениям: расходящиеся модификации, стрельба
  дробью.
- Изучить лишнее: дублирование, мёртвый код, ленивый класс, спекулятивная
  общность, избыточные комментарии.
- Изучить запахи связанности: завистливые функции, неуместная близость,
  цепочки вызовов, посредник.

### 4. Безопасный процесс рефакторинга

- Работать маленькими шагами: одно изменение — запуск тестов — коммит.
- Разделять рефакторинг и изменение поведения в разных коммитах.
- Использовать автоматические рефакторинги IDE и понимать их ограничения.
- Применять линтеры и статический анализ (например, RuboCop, Reek,
  SonarQube) для поиска проблемных мест.

### 5. Приёмы составления методов

- Extract Method / Inline Method.
- Extract Variable / Inline Temp.
- Replace Temp with Query.
- Split Temporary Variable, Remove Assignments to Parameters.
- Replace Method with Method Object.

### 6. Перемещение функций и организация данных

- Move Method / Move Field, Extract Class / Inline Class.
- Hide Delegate / Remove Middle Man.
- Replace Primitive with Object, Introduce Parameter Object.
- Encapsulate Field и Encapsulate Collection.
- Replace Magic Number with Symbolic Constant.

### 7. Упрощение условий и обобщение

- Decompose Conditional, Consolidate Conditional Expression.
- Replace Nested Conditional with Guard Clauses.
- Replace Conditional with Polymorphism, Introduce Null Object.
- Pull Up / Push Down Method, Extract Superclass, Extract Interface.
- Replace Inheritance with Delegation и обратный приём.

### 8. Рефакторинг унаследованного кода

- Написать характеризационные тесты (characterization tests), фиксирующие
  текущее поведение.
- Найти швы (seams) для разрыва зависимостей.
- Применить Sprout Method / Sprout Class и Wrap Method для добавления логики
  без правки старого кода.
- Изучить паттерн Strangler Fig для постепенной замены модулей.
- Разобрать Branch by Abstraction и фича-флаги для крупных изменений.

## Практический проект

Провести рефакторинг учебного унаследованного модуля (например, расчёта
стоимости заказа или тарификации) объёмом 300–500 строк:

- составить список найденных запахов кода с указанием мест в коде;
- покрыть текущее поведение характеризационными тестами до начала изменений;
- выполнить рефакторинг серией небольших коммитов, каждый из которых
  применяет один приём и проходит тесты;
- заменить ветвления по типу на полиморфизм хотя бы в одном месте;
- сравнить метрики до и после: размер методов, цикломатическая сложность,
  дублирование, замечания линтера;
- описать выводы: какие приёмы дали наибольший эффект и что осталось
  техническим долгом.

## Критерии завершения

- Поведение модуля не изменилось: все характеризационные тесты проходят.
- История коммитов показывает последовательные шаги рефакторинга без
  смешивания с новой функциональностью.
- Каждый найденный запах либо устранён, либо обоснованно оставлен как долг.
- Метрики сложности и дублирования улучшились и зафиксированы в отчёте.
