# Code Review

## Цель

Научиться эффективно проводить и проходить Code Review: проверять изменения
по существу, давать конструктивную обратную связь, готовить удобные для
ревью Merge Request и встраивать ревью в процесс команды.

## План изучения

### 1. Основные понятия

- Разобрать цели Code Review: качество кода, поиск ошибок, распространение
  знаний, единые стандарты.
- Понять, чего Code Review не заменяет: тесты, статический анализ, проверку
  безопасности.
- Изучить форматы ревью: асинхронное в Merge Request, парное
  программирование, совместный разбор.
- Разобрать роли автора, ревьюера и владельца кода (CODEOWNERS).

### 2. Подготовка изменений автором

- Делать небольшие Merge Request, решающие одну задачу.
- Писать описание: что сделано, зачем, как проверить, ссылка на задачу Jira.
- Разделять рефакторинг и изменение поведения в разных коммитах.
- Проводить самопроверку диффа перед отправкой на ревью.
- Добиваться прохождения CI, линтеров и тестов до назначения ревьюера.

### 3. Что проверять

- Корректность: соответствие требованиям, граничные случаи, обработка
  ошибок.
- Дизайн: границы ответственности, связанность, соответствие архитектуре.
- Читаемость: имена, структура, сложность, комментарии.
- Тесты: наличие, полнота, проверка поведения, а не реализации.
- Безопасность: валидация входных данных, секреты, права доступа.
- Эксплуатация: производительность, журналирование, миграции, обратная
  совместимость.

### 4. Процесс ревью

- Сначала понять цель изменения, затем смотреть детали.
- Ограничивать объём одной сессии ревью (около 200–400 строк).
- Использовать чек-лист команды для типовых проверок.
- Соблюдать договорённое время реакции на ревью.
- Разбирать сложные изменения голосом, а не длинной перепиской.

### 5. Обратная связь

- Комментировать код, а не автора.
- Формулировать замечания как вопросы и предложения с объяснением причины.
- Обозначать важность замечаний: блокирующее, желательное, nit, вопрос
  (например, Conventional Comments).
- Отмечать удачные решения, а не только проблемы.
- Не навязывать личные предпочтения, которые не закреплены в стандартах.

### 6. Получение обратной связи

- Воспринимать замечания как обсуждение кода, а не оценку личности.
- Отвечать на каждый комментарий: исправлено, обсуждается или отклонено с
  причиной.
- Разрешать разногласия через стандарты команды или третьего участника.
- Фиксировать повторяющиеся замечания в стайлгайде или линтере.

### 7. Автоматизация

- Перенести проверки стиля и форматирования в линтеры (например, RuboCop).
- Подключить статический анализ, SAST и проверку зависимостей в CI.
- Настроить правила одобрения Merge Request и CODEOWNERS в GitLab.
- Изучить возможности ИИ-ассистентов для предварительного ревью и их
  ограничения.

### 8. Метрики и улучшение процесса

- Отслеживать время до первого ответа и время до слияния Merge Request.
- Анализировать размер Merge Request и количество итераций ревью.
- Разбирать дефекты, пропущенные на ревью, и дополнять чек-лист.
- Избегать метрик, поощряющих формальное одобрение.

## Практический проект

Внедрить и опробовать процесс Code Review в учебной команде или проекте:

- подготовить чек-лист ревью по разделам: корректность, дизайн, тесты,
  безопасность, эксплуатация;
- подготовить шаблон описания Merge Request для GitLab;
- провести ревью не менее пяти реальных Merge Request коллег с
  комментариями по Conventional Comments;
- пройти ревью собственных Merge Request и отработать замечания;
- перенести не менее трёх повторяющихся замечаний в правила линтера или CI;
- собрать метрики времени ревью и размера Merge Request и описать выводы.

## Критерии завершения

- Чек-лист и шаблон Merge Request согласованы с командой и используются.
- Комментарии в проведённых ревью обоснованы, имеют уровень важности и не
  содержат оценок личности автора.
- Собственные Merge Request небольшие, с понятным описанием и проходят CI
  до назначения ревьюера.
- Повторяющиеся замечания автоматизированы, а метрики процесса
  зафиксированы.
