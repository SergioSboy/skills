# 1. Планировщик и статистика

## 1.1. Выбор плана по оценке стоимости

**Планировщик PostgreSQL выбирает способ выполнения запроса по оценке стоимости — cost.** Он рассматривает доступные способы чтения, соединения и обработки данных, оценивая необходимые ресурсы.

**Cost выражается в условных единицах, а не в миллисекундах.** В расчёте участвуют предполагаемые обращения к страницам данных, обработка строк и другие операции. Планировщик не выполняет каждый вариант, чтобы выбрать самый быстрый. [Как читать EXPLAIN](https://www.postgresql.org/docs/current/using-explain.html)

```sql
EXPLAIN
SELECT id, total_cents
FROM orders
WHERE status = 'pending';
```

В выводе узла можно встретить:

```text
cost=0.00..24000.00 rows=100 width=16
```

Это условный пример:

- первое число — стоимость до начала выдачи строк;
- второе — стоимость получения всех строк узла;
- `rows` — ожидаемое число выходных строк;
- `width` — ожидаемая средняя ширина строки в байтах.

При `LIMIT` важна стоимость получения нужной части результата, поэтому план с меньшей полной стоимостью не обязательно предпочтительнее.

**Ошибка оценки количества строк может привести к неудачному плану.** Например, планировщик ожидает 100 заказов, а получает 50 000: многократные обращения через индекс могут оказаться дороже последовательного чтения.

При этом сам по себе `Seq Scan` — последовательное чтение таблицы — не является проблемой: для большой доли строк он часто оправдан. Снижение `cost` тоже не доказывает ускорение — нужны фактические измерения.

## 1.2. Откуда берутся оценки

**Статистика планировщика — приблизительное описание размера таблиц и распределения значений.** Она помогает оценить **селективность — долю строк, удовлетворяющих условию**.

| Источник или показатель | Назначение |
|---|---|
| `pg_class.reltuples` | Оценка числа строк |
| `pg_class.relpages` | Оценка размера в страницах |
| `pg_statistic` | Системный каталог статистики столбцов |
| MCV — most common values | Наиболее частые значения и их частоты |
| Гистограмма | Распределение остальных значений по диапазонам |

`reltuples` не пересчитывается после каждой записи и не заменяет точный `COUNT(*)`. Планировщик может корректировать оценку с учётом текущего физического размера таблицы. Для просмотра статистики столбцов удобнее представление `pg_stats`, чем внутренний каталог `pg_statistic`. [Статистика планировщика](https://www.postgresql.org/docs/current/planner-stats.html)

```sql
SELECT attname, null_frac,
       most_common_vals, most_common_freqs,
       histogram_bounds
FROM pg_stats
WHERE schemaname = 'public'
  AND tablename = 'orders'
  AND attname = 'status';
```

`null_frac` — доля `NULL`. Частоты MCV помогают различить распространённый статус `completed` и редкий `pending`. Гистограмма полезна, например, для оценки диапазона дат; значения из MCV исключаются из её расчёта. Если MCV охватывает всё распределение, гистограмма может отсутствовать. [Поля pg_stats](https://www.postgresql.org/docs/current/view-pg-stats.html)

**Статистика приблизительна даже сразу после обновления:** для больших таблиц она собирается по выборке.

## 1.3. ANALYZE и автоматическое обновление

**`ANALYZE` собирает статистику, которую используют последующие планирования запросов.** После массовой загрузки заказов или существенного изменения распределения данных полезно обновить её явно:

```sql
ANALYZE public.orders;
```

Команда не перестраивает индексы и не изменяет бизнес-данные. Она обычно допускает параллельное чтение и запись, но потребляет ресурсы. **`ANALYZE` и `EXPLAIN ANALYZE` различаются:** первая собирает статистику, вторая действительно выполняет исследуемый запрос и показывает фактические показатели. [Команда ANALYZE](https://www.postgresql.org/docs/current/sql-analyze.html)

**Автоанализ — автоматический запуск ANALYZE механизмом autovacuum.** Для обычной таблицы основание для запуска определяется числом вставок, обновлений и удалений после предыдущего анализа:

```text
порог =
autovacuum_analyze_threshold
+ autovacuum_analyze_scale_factor × reltuples
```

Превышение порога не означает немедленного обновления: учитываются доступность фоновых работников и условия выполнения. Настройки можно переопределять для конкретных таблиц. [Условия автоанализа](https://www.postgresql.org/docs/current/routine-vacuuming.html#AUTOVACUUM)

На большой таблице заметное изменение редкой группы заказов может не достигнуть общего порога. Поэтому наличие автоанализа не гарантирует свежесть статистики для каждого важного запроса.

Отдельное ограничение: autovacuum анализирует обычные партиции, но статистику родительской секционированной таблицы нужно обновлять вручную.

## 1.4. Детализация статистики: default_statistics_target

**`default_statistics_target` задаёт стандартную детализацию статистики столбцов**, если для них не установлено собственное значение. Значение по умолчанию — `100`. Повышение может улучшить оценки, но увеличивает затраты на сбор статистики. [Настройка PostgreSQL](https://www.postgresql.org/docs/current/runtime-config-query.html#GUC-DEFAULT-STATISTICS-TARGET)

Более подробные списки частых значений и гистограммы полезны при неравномерном распределении. Например, у магазина могут быть тысячи продавцов с очень разным количеством заказов.

Вместо повышения настройки для всей базы можно провести эксперимент с конкретным столбцом:

```sql
ALTER TABLE public.orders
  ALTER COLUMN seller_id SET STATISTICS 500;

ANALYZE public.orders;
```

`500` здесь — пример для проверки гипотезы, а не универсальная рекомендация. **Изменение target требует нового ANALYZE**, чтобы собрать статистику с выбранной детализацией.

Сравни оценки и фактические строки, время выполнения и обращения к буферам до и после на одинаковых данных и параметрах запроса, при сопоставимых условиях кеша и нагрузки.

**Больше статистики не исправляет любую ошибку.** Если условия связаны, например страна и город доставки, увеличение детализации отдельных столбцов может не помочь. Для некоторых таких зависимостей применяют расширенную статистику — extended statistics, описывающую несколько столбцов совместно. [Расширенная статистика](https://www.postgresql.org/docs/current/planner-stats.html#PLANNER-STATS-EXTENDED)

**Запомнить:** планировщик выбирает план по приблизительным оценкам; сначала проверяй их качество и актуальность, затем подтверждай улучшение фактическими измерениями.

# 2. Чтение плана выполнения

## 2.1. Получение плана с фактическими показателями

**План выполнения — дерево операций, которыми PostgreSQL получает результат запроса.** Для исследования используют:

```sql
EXPLAIN (ANALYZE, BUFFERS, VERBOSE)
SELECT o.id, oi.product_id
FROM orders o
JOIN order_items oi ON oi.order_id = o.id
WHERE o.customer_id = 42;
```

| Опция | Что добавляет |
|---|---|
| `ANALYZE` | Выполняет запрос и показывает фактические времена, строки и число запусков узлов |
| `BUFFERS` | Показывает обращения к страницам данных и временным файлам |
| `VERBOSE` | Добавляет детали: выходные выражения узлов, схемы объектов и другие сведения |

**`EXPLAIN ANALYZE` действительно выполняет запрос.** Для `UPDATE`, `DELETE` и других изменяющих команд изменения и побочные эффекты реальны. Даже исследуемый `SELECT` создаёт обычную нагрузку. [Команда EXPLAIN](https://www.postgresql.org/docs/current/sql-explain.html)

В `BUFFERS` сначала смотри:

- `shared hit` — страница найдена в общем кеше PostgreSQL;
- `shared read` — страница загружена в этот кеш; она могла находиться в кеше ОС, поэтому это не обязательно физическое чтение диска;
- `temp read/written` — чтение и запись временных рабочих данных, например при сортировке или хешировании.

Для сравнения сохраняй запрос, параметры и условия запуска. Повторный прогон часто быстрее из-за прогретого кеша. Инструментирование также добавляет накладные расходы, а время передачи результата клиенту этот замер не отражает.

## 2.2. Узлы чтения: от источников к результату

**Читай дерево от нижних узлов к родительским:** откуда поступают данные, как отбираются, соединяются и преобразуются. Отступы показывают вложенность.

Это способ анализа зависимостей, а не точная временная последовательность: родитель может запрашивать строки постепенно, а `LIMIT` — остановить обработку раньше завершения дочернего узла.

| Узел | Как читает данные | Когда может быть уместен |
|---|---|---|
| `Seq Scan` | Последовательно читает таблицу и проверяет фильтр | Небольшая таблица или большая доля нужных строк |
| `Index Scan` | Находит записи через индекс и обращается к строкам таблицы | Небольшая выборка, точечные поиски, подходящий порядок индекса |
| `Index Only Scan` | Получает необходимые значения из индекса, проверяя видимость строк | Индекс содержит нужные данные и позволяет избежать большинства обращений к таблице |
| `Bitmap Index Scan` | Строит bitmap — карту расположения подходящих строк | Нужно собрать много совпадений или объединить условия нескольких индексов |
| `Bitmap Heap Scan` | По карте читает страницы таблицы и получает строки | Выгоднее сгруппировать обращения к таблице, чем выполнять их по одному |

Пара bitmap-узлов читается так:

```text
Bitmap Heap Scan on orders
  Recheck Cond: (customer_id = 42)
  -> Bitmap Index Scan on orders_customer_id_idx
       Index Cond: (customer_id = 42)
```

Сначала строится карта, затем читаются страницы таблицы. **Порядок исходного индекса при bitmap-чтении теряется:** для `ORDER BY` может потребоваться сортировка. [Bitmap scans](https://www.postgresql.org/docs/current/indexes-bitmap-scans.html)

**`Index Only Scan` не гарантирует отсутствие обращений к таблице.** Если visibility map — карта видимости — не подтверждает видимость строк страницы, требуется проверка в таблице. Смотри `Heap Fetches`. [Index-only scans](https://www.postgresql.org/docs/current/indexes-index-only-scans.html)

Также различай `Index Cond`, ограничивающий поиск по индексу, и `Filter`, отбрасывающий уже полученные кандидаты.

## 2.3. Алгоритмы соединения

**Join соединяет два входных набора строк.** Важен их размер **после фильтрации**, а не только полный размер таблиц.

| Алгоритм | Принцип | Когда часто выгоден | Что проверить |
|---|---|---|---|
| **Nested Loop** | Для каждой строки внешнего входа ищет совпадения во внутреннем | Внешний набор мал, внутренний поиск дешёвый, например индексный | Число повторов внутреннего узла |
| **Hash Join** | Строит хеш-таблицу одного входа и ищет в ней строки другого | Значительные наборы, соединение по равенству | Размер хеш-таблицы, память и временные файлы |
| **Merge Join** | Сопоставляет входы, упорядоченные по ключам соединения | Большие наборы, особенно когда нужный порядок уже доступен | Стоимость предварительной сортировки |

Механизмы описаны в [документации планировщика](https://www.postgresql.org/docs/current/planner-optimizer.html).

Например, для нескольких заказов покупателя `Nested Loop` с индексным поиском позиций по `order_id` может быть отличным выбором. Для отчёта по большинству заказов многократный поиск может проиграть `Hash Join`.

**Универсального порога количества строк нет.** Влияют ширина строк, число совпадений, доступные индексы, порядок и память. В частности, нехватка памяти для хеширования может привести к обработке партиями с временными файлами.

## 2.4. Оценки, факты и loops

**Оценка описывает ожидания планировщика, факт — конкретное выполнение.**

| Поле | Значение |
|---|---|
| `cost=a..b` | Оценка начальной и полной стоимости в условных единицах |
| `rows` до блока `actual` | Ожидаемое число выходных строк узла |
| `actual time=a..b` | Время до первой строки и до завершения узла, в миллисекундах |
| `rows` внутри блока `actual` | Фактически выданные строки |
| `loops` | Число запусков узла |

При нескольких запусках **фактические время и строки показываются в среднем на один запуск**. [Чтение EXPLAIN ANALYZE](https://www.postgresql.org/docs/current/using-explain.html#USING-EXPLAIN-ANALYZE)

Условный фрагмент внутреннего узла:

```text
Index Scan ... (cost=0.42..8.44 rows=1 width=16)
               (actual time=0.010..0.020 rows=2 loops=1000)
```

Здесь узел выдал примерно `2 × 1000 = 2000` строк и суммарно затратил около `0.020 × 1000 = 20 мс`. Для проверки оценки сравнивай **ожидаемую одну строку с фактическими двумя**, поскольку обе величины относятся к одному запуску.

`rows` — выход узла, а не все просмотренные строки. Отброшенные строки отражаются, например, в `Rows Removed by Filter`.

**Не складывай времена и буферы всех уровней:** показатели родителей включают работу потомков. Счётчики `BUFFERS` уже накоплены за выполнения узла — умножать их на `loops` не нужно. В параллельном плане суммарная работа участников также не равна прошедшему времени запроса.

**Запомнить:** выясни, откуда идут строки, почему выбран способ чтения и соединения, затем сопоставь оценки с фактом, учитывая повторы и вложенность.

# 3. Расхождение оценки и факта

## 3.1. Где искать ошибку оценки

**Ошибка оценки кардинальности — расхождение ожидаемого и фактического числа строк на выходе узла.** Она важна, потому что влияет на выбор чтения, порядка соединений и алгоритмов обработки.

Например, условный фрагмент:

```text
Seq Scan on orders
  (cost=0.00..25000.00 rows=100 width=32)
  (actual time=0.020..80.000 rows=50000 loops=1)
```

Планировщик ожидал 100 строк, получил 50 000 — недооценка в 500 раз. Следующий узел мог быть выбран для маленького входа, хотя фактически получил большой.

**Ищи первое существенное расхождение от листьев дерева к корню.** Ошибка в фильтрации заказов может распространяться на все последующие соединения. При этом учитывай и абсолютный объём: ошибка «1 вместо 10» обычно менее значима, чем «100 вместо миллиона».

При нескольких `loops` сравнивай оценку с **фактическим средним числом строк за один запуск**, а не с произведением `actual rows × loops`. Для общей работы узла произведение полезно, для проверки оценки — нет. [Интерпретация EXPLAIN ANALYZE](https://www.postgresql.org/docs/current/using-explain.html#USING-EXPLAIN-ANALYZE)

Не считай любое различие ошибкой статистики: `LIMIT` может остановить дочерний узел раньше, чем тот выдаст все ожидаемые строки. Для узла с `never executed` фактического измерения вообще нет.

## 3.2. Статистика, типы и выражения

**Сначала проверь, какие данные и выражения планировщик действительно оценивает.** Три распространённые причины требуют разных действий.

| Причина | Что проверить | Возможное действие |
|---|---|---|
| Устаревшая статистика | Массовые изменения, время последнего анализа | Выполнить `ANALYZE` |
| Приведение типов | Тип столбца, параметра и выражения в плане | Согласовать типы без изменения смысла сравнения |
| Функция над столбцом | Соответствует ли условие обычному столбцу или выражению | Рассмотреть статистику выражения, индекс выражения либо корректную переработку условия |

Для проверки истории анализа:

```sql
SELECT last_analyze, last_autoanalyze, n_mod_since_analyze
FROM pg_stat_user_tables
WHERE schemaname = 'public'
  AND relname = 'orders';
```

`n_mod_since_analyze` — приблизительное число изменений после анализа. Недавняя дата анализа сама по себе не гарантирует подходящую статистику для конкретного условия. [Статистика таблиц](https://www.postgresql.org/docs/current/monitoring-stats.html#MONITORING-PG-STAT-ALL-TABLES-VIEW)

Например:

```sql
WHERE lower(customer_email) = 'buyer@example.com'
```

Здесь фильтруется **результат `lower`**, а не исходное значение. Обычный индекс по `customer_email` не обеспечивает тот же индексный поиск, что индекс по `lower(customer_email)`. [Индексы выражений](https://www.postgresql.org/docs/current/indexes-expressional.html)

**Ошибка оценки и невозможность эффективного индексного поиска — разные проблемы.** Статистика выражения может улучшить оценку без создания индекса; индекс выражения добавляет способ доступа и стоимость обслуживания.

Не любое приведение типов мешает индексу. Смотри, что преобразуется: параметр или столбец, какой оператор используется и где условие оказалось — в `Index Cond` или `Filter`. Не убирай преобразование автоматически: это может изменить результат или допустимые входные значения.

## 3.3. Корреляция столбцов и extended statistics

**Корреляция между столбцами означает, что знание одного значения меняет вероятность другого.** При отсутствии подходящей статистики планировщик часто оценивает условия как независимые.

Условный пример: во Францию направлены 10% заказов, в Париж — 5%, причём все парижские заказы относятся к Франции.

Для условий:

```sql
WHERE delivery_country = 'FR'
  AND delivery_city = 'Paris'
```

Независимая оценка даёт `10% × 5% = 0,5%`, хотя фактически подходит 5%.

**То, что два фильтра вместе оставляют меньше строк, ещё не доказывает корреляцию:** так бывает и у независимых условий. Важно расхождение с ожидаемой совместной долей. Связь может приводить как к недооценке, так и к переоценке.

**Extended statistics — расширенная статистика**, учитывающая несколько столбцов или выражений совместно.

| Вид | Для чего полезен |
|---|---|
| `dependencies` | Учёт функциональных зависимостей и избыточных условий |
| `mcv` | Частоты распространённых комбинаций значений |
| `ndistinct` | Оценка числа различных комбинаций, например для `GROUP BY` |

```sql
CREATE STATISTICS orders_delivery_stats (dependencies, mcv)
ON delivery_country, delivery_city
FROM public.orders;

ANALYZE public.orders;
```

`CREATE STATISTICS` создаёт описание собираемой статистики; данные собирает последующий `ANALYZE`. Это **не составной индекс**. [Расширенная статистика](https://www.postgresql.org/docs/current/planner-stats.html#PLANNER-STATS-EXTENDED)

Ограничения существенны: `dependencies` применяется главным образом к равенствам с константами и `IN`, а не ко всем диапазонам и выражениям. В PostgreSQL 18 расширенная статистика не используется для оценки селективности межтабличных соединений. [CREATE STATISTICS](https://www.postgresql.org/docs/current/sql-createstatistics.html)

## 3.4. Повторный замер после ANALYZE

**Обновление статистики — отдельный эксперимент:** сначала проверь его эффект без одновременного изменения SQL и индексов.

Порядок действий:

1. Сохрани исходный план, параметры запроса и показатели.
2. Выполни `ANALYZE` затронутых таблиц.
3. Повтори тот же запрос с теми же параметрами.
4. Сравни оценки строк, фактические строки, план, время и буферы.

```sql
ANALYZE public.orders;

EXPLAIN (ANALYZE, BUFFERS, VERBOSE)
SELECT id
FROM public.orders
WHERE delivery_country = 'FR'
  AND delivery_city = 'Paris';
```

**`ANALYZE` обновляет знания о данных, но не гарантирует ускорение.** Из-за выборки оценки могут немного меняться даже при неизменных данных. [Команда ANALYZE](https://www.postgresql.org/docs/current/sql-analyze.html)

Сравнивай несколько прогонов на одинаковых данных, при сопоставимых нагрузке и прогреве кеша. Один быстрый повтор после анализа может объясняться кешем.

Если расхождение осталось, проверяй детализацию статистики, зависимости, выражения и параметры планирования. Добавляй индекс или меняй запрос после определения причины, подтверждая каждое изменение отдельным замером.

**Запомнить:** найди первое значимое расхождение строк, проверь статистику и смысл выражений, затем повтори замер после `ANALYZE` — и только потом выбирай следующее изменение.

# 4. Подбор индексов

## 4.1. B-tree под WHERE, JOIN и ORDER BY

**B-tree — упорядоченный индекс**, подходящий для сравнений на равенство, диапазонов и получения данных в определённом порядке. Подбирай его под конкретный запрос: какие строки нужны, как они соединяются и в каком порядке возвращаются.

Например, последние ожидающие заказы покупателя:

```sql
SELECT id, created_at, total_cents
FROM orders
WHERE customer_id = 42
  AND status = 'pending'
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

Кандидат для проверки:

```sql
CREATE INDEX orders_customer_status_created_idx
ON orders (customer_id, status, created_at DESC, id DESC);
```

Первые два столбца ограничивают поиск, следующие соответствуют сортировке. `id` обеспечивает однозначный порядок при одинаковом `created_at`.

**Сочетание подходящего порядка и `LIMIT` особенно полезно:** PostgreSQL может получить первые строки без сортировки всего подходящего набора. Однако индекс не гарантирует, что планировщик выберет именно этот путь. [Индексы и ORDER BY](https://www.postgresql.org/docs/current/indexes-ordering.html)

Для соединения `order_items.order_id = orders.id` индекс по `order_items(order_id)` может ускорить поиск позиций каждого выбранного заказа. Но при соединении больших долей таблиц последовательное чтение с `Hash Join` может оказаться дешевле.

## 4.2. Порядок столбцов составного индекса

**Составной индекс содержит несколько ключевых столбцов в заданном порядке. Префикс — его начальная последовательность**, например `(customer_id)` или `(customer_id, status)`.

Для B-tree условия равенства по ведущим столбцам и диапазон по следующему столбцу обычно определяют непрерывный участок поиска. Поэтому порядок выбирают по сочетанию фильтрации, сортировки и реально используемых запросов.

**Правило «самый селективный столбец первым» недостаточно.** Селективный фильтр оставляет небольшую долю строк, но если оба столбца проверяются на равенство, важнее могут быть запросы, использующие только один из них.

Для индекса из примера:

| Запрос | Что учитывать |
|---|---|
| Покупатель + статус + последние заказы | Фильтры и порядок согласованы с индексом |
| Только покупатель | Ведущий столбец полезен для поиска |
| Только покупатель + сортировка по дате | Между покупателем и датой стоит статус: нужный общий порядок не гарантируется |
| Только статус | Эффективного ограничения по ведущему столбцу нет |

**Отсутствие ведущего условия не делает индекс безусловно бесполезным.** PostgreSQL 18 поддерживает B-tree skip scan — повторные поиски по значениям пропущенного ключа. Он может быть выгоден при небольшом числе таких значений, но не заменяет подбор индекса под нагрузку. [Составные индексы](https://www.postgresql.org/docs/current/indexes-multicolumn.html)

Учитывай также направления сортировки и расположение `NULL`. Один индекс не обязан оптимально обслуживать все варианты запросов.

## 4.3. Частичный индекс, выражение и INCLUDE

Эти возможности решают разные задачи:

| Вид | Назначение | Ограничение |
|---|---|---|
| **Частичный индекс — partial index** | Индексирует только строки, удовлетворяющие предикату | Условия запроса должны позволять планировщику доказать применимость предиката |
| **Индекс выражения — expression index** | Индексирует результат вычисления, например `lower(email)` | Выражение запроса должно соответствовать индексируемому |
| **Покрывающий индекс — covering index** | Содержит необходимые запросу данные, включая дополнительные столбцы через `INCLUDE` | Увеличивает размер индекса и стоимость его обслуживания |

Для первого запроса можно проверить альтернативу: индекс только ожидающих заказов, дополнительно содержащий сумму.

```sql
CREATE INDEX orders_pending_cover_idx
ON orders (customer_id, created_at DESC, id DESC)
INCLUDE (total_cents)
WHERE status = 'pending';
```

Если ожидающие заказы составляют небольшую часть таблицы, такой индекс может быть компактнее полного. Но **generic plan с условием `status = $1` не может заранее считать, что `$1` всегда равен `'pending'`**. Проверяй реальную форму запроса приложения. [Частичные индексы](https://www.postgresql.org/docs/current/indexes-partial.html)

Для поиска без учёта регистра другой кандидат:

```sql
CREATE INDEX customers_lower_email_idx
ON customers (lower(email));
```

Он соответствует условию `lower(email) = 'buyer@example.com'`. [Индексы выражений](https://www.postgresql.org/docs/current/indexes-expressional.html)

**Частичный индекс и индекс выражения сами по себе не устраняют обращение к heap — основной области хранения строк таблицы.** Они сокращают поиск или индексируют нужное выражение.

`INCLUDE` добавляет данные, но не делает их ключами поиска и сортировки. Даже покрывающий индекс позволяет избежать чтения heap только при подходящей видимости строк: PostgreSQL проверяет visibility map — карту видимости. Поэтому `Index Only Scan` может иметь ненулевой `Heap Fetches`. [Покрывающие индексы](https://www.postgresql.org/docs/current/indexes-index-only-scans.html)

Примеры — кандидаты для отдельных экспериментов, а не предложение создать все индексы одновременно.

## 4.4. Проверка выбранного плана и эффекта

**Созданный индекс — доступный вариант выполнения, а не доказательство оптимизации.** Повтори исходный запрос:

```sql
EXPLAIN (ANALYZE, BUFFERS, VERBOSE)
SELECT id, created_at, total_cents
FROM orders
WHERE customer_id = 42
  AND status = 'pending'
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

Проверь:

- **Имя индекса:** появился ли он в `Index Scan`, `Index Only Scan` или `Bitmap Index Scan`.
- **`Index Cond`:** какие условия ограничивают поиск, а какие остались в `Filter`.
- **Сортировку:** исчезла ли лишняя операция `Sort`, если это было целью.
- **Работу:** уменьшились ли обращения к буферам, отфильтрованные строки и `Heap Fetches`.
- **Результат:** сократилось ли время при сопоставимых данных, параметрах, кеше и нагрузке.

Планировщик может обоснованно оставить `Seq Scan`. Не добивайся нужного названия узла любой ценой: **цель — уменьшить стоимость реальной работы**, учитывая дополнительное место и нагрузку на запись. [Проверка через EXPLAIN](https://www.postgresql.org/docs/current/using-explain.html)

**Запомнить:** индекс подбирают под фильтры, соединения, порядок и набор запросов; пользу подтверждают планом и измерениями, а отсутствие чтения heap проверяют отдельно.

# 5. Переписывание запроса

## 5.1. Лишние столбцы и соединения

**Переписывание запроса — изменение способа получения результата с сохранением его смысла.** До оптимизации зафиксируй необходимые столбцы, правила отбора, дубликаты и порядок строк.

Вместо `SELECT *` запрашивай данные, которые действительно нужны экрану или обработчику:

```sql
SELECT id, total_cents
FROM orders
WHERE customer_id = 42;
```

Это уменьшает передачу данных, создание объектов приложения и иногда объём промежуточных результатов сортировки или соединения. Узкий набор столбцов также может позволить использовать покрывающий индекс.

**Меньше столбцов не обязательно означает меньше прочитанных страниц таблицы:** PostgreSQL хранит обычные строки построчно. Выигрыш зависит от плана, возможности index-only scan и необходимости загружать большие значения. [Index-only scans](https://www.postgresql.org/docs/current/indexes-index-only-scans.html)

Соединение можно убрать, если оно не предоставляет нужных данных, не фильтрует строки и не меняет их количество.

Например, `JOIN order_items` способен размножить заказ по числу позиций. Его удаление изменит результат, даже если столбцы позиций не выбираются. Аналогично, `INNER JOIN customers` может исключать заказы без подходящего покупателя.

**«Столбцы таблицы не используются» — недостаточное основание для удаления JOIN.** Сначала проверь ограничения целостности и кардинальность связи — сколько строк может соответствовать одной строке другой таблицы.

## 5.2. Условия, пригодные для индексного поиска

**Условие, пригодное для индексного поиска, позволяет ограничить область чтения индекса.** Функция или преобразование над столбцом могут помешать использовать обычный индекс по исходному значению.

Например, для `created_at` типа `timestamp without time zone`:

```sql
-- Исходное условие
WHERE created_at::date = DATE '2026-11-14'

-- Эквивалентный диапазон
WHERE created_at >= TIMESTAMP '2026-11-14 00:00:00'
  AND created_at <  TIMESTAMP '2026-11-15 00:00:00'
```

Диапазон позволяет рассмотреть обычный B-tree по `created_at`. Верхняя граница исключающая: не приходится подбирать «последнюю микросекунду дня».

Для `timestamptz` сначала определи часовой пояс бизнес-дня. Его границы нельзя всегда заменять фиксированным интервалом в 24 часа.

**Не убирай функцию, если она нужна по смыслу.** Условия `lower(email) = ...` и `email = ...` обычно различаются. Можно сохранить функцию и рассмотреть индекс выражения. [Индексы выражений](https://www.postgresql.org/docs/current/indexes-expressional.html)

Для параметров согласовывай тип с типом столбца. Но не любое неявное приведение мешает индексу: проверяй конкретный оператор и `Index Cond` в плане. Переписывание должно сохранять правила сравнения, обработку `NULL` и допустимых значений.

## 5.3. OR, UNION ALL и отдельные запросы

**Разделение ветвей позволяет планировщику выбрать разные способы доступа для разных условий.** Оно иногда полезно, когда одна ветвь возвращает мало строк, а другая — много.

При этом PostgreSQL умеет обрабатывать `OR` через объединение результатов индексного поиска, например `BitmapOr`. Поэтому сам `OR` не является признаком плохого запроса. [Объединение индексов](https://www.postgresql.org/docs/current/indexes-bitmap-scans.html)

| Вариант | Возможное преимущество | Ограничение |
|---|---|---|
| `OR` | Один запрос, пересечение условий не дублирует исходную строку | Общий план может оказаться неудачным |
| `UNION ALL` | Отдельное планирование ветвей без удаления дубликатов | Пересекающиеся ветви повторяют строки |
| Отдельные запросы | Независимые планы и управление выполнением | Дополнительные обращения, объединение результатов в приложении |

Исходный запрос:

```sql
SELECT id, total_cents
FROM orders
WHERE customer_id = 42 OR status = 'pending';
```

Вариант без повторного включения одного заказа:

```sql
SELECT id, total_cents
FROM orders
WHERE customer_id = 42

UNION ALL

SELECT id, total_cents
FROM orders
WHERE status = 'pending'
  AND (customer_id = 42) IS NOT TRUE;
```

`IS NOT TRUE` исключает уже выбранные заказы и корректно учитывает `NULL` в `customer_id`.

**Обычный `UNION` удаляет дубликаты по всем выбранным столбцам.** Это дополнительная работа и потенциальное изменение результата, если разные исходные строки дают одинаковые выбранные значения. [Семантика UNION](https://www.postgresql.org/docs/current/queries-union.html)

Общий `ORDER BY` и `LIMIT` нужно применять к объединённому результату. Отдельные запросы также могут видеть разные снимки данных. Сравнивай полное время получения результата, включая сеть и обработку приложением.

## 5.4. Keyset вместо большого OFFSET

**Keyset-пагинация выбирает следующую страницу относительно ключа последней показанной строки.** В отличие от неё, большой `OFFSET` требует вычислить и пропустить предыдущие строки. [LIMIT и OFFSET](https://www.postgresql.org/docs/current/queries-limit.html)

Для списка заказов покупателя:

```sql
SELECT id, created_at, total_cents
FROM orders
WHERE customer_id = 42
  AND (created_at, id) < ($1, $2)
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

`$1` и `$2` — точные значения `created_at` и `id` последнего заказа предыдущей страницы. Для первой страницы условие курсора отсутствует.

Сравнение пары выполняется последовательно: сначала дата, при равенстве — идентификатор. [Сравнение строковых конструкторов](https://www.postgresql.org/docs/current/functions-comparisons.html#ROW-WISE-COMPARISON)

Подходящий кандидат индекса — `(customer_id, created_at DESC, id DESC)`.

**Порядок должен быть однозначным и стабильным.** В примере предполагаются уникальный `id`, отсутствие `NULL` в ключах и неизменность `created_at`. Сохраняй полную точность даты в курсоре. Для смешанных направлений сортировки условие перехода нужно составлять отдельно.

Keyset хорошо подходит для последовательного просмотра, но не обеспечивает прямой переход на произвольную страницу. Он также не фиксирует снимок всей выдачи: изменения данных между запросами по-прежнему влияют на результат.

**Запомнить:** переписывай запрос под измеренную причину затрат, сохраняя строки, дубликаты и порядок; ускорение подтверждай сравнением планов и фактических показателей.

# 6. Цена индекса для записи

## 6.1. Влияние на INSERT, UPDATE и DELETE

**Индекс — дополнительная структура данных, которую PostgreSQL должен поддерживать.** Ускорение чтения оплачивается местом, работой при записи и последующим обслуживанием.

| Операция | Дополнительная работа |
|---|---|
| `INSERT` | Добавление записей в соответствующие индексы, проверки уникальности |
| `UPDATE` | Создание новой версии строки и, если обновление не HOT, новых индексных записей |
| `DELETE` | Старая версия строки становится удалённой; очистка связанных индексных записей выполняется позднее |

Индекс также может **ускорить поиск строк для UPDATE и DELETE**. Поэтому итоговое время операции зависит и от выигрыша поиска, и от цены обслуживания.

**HOT — Heap-Only Tuple, оптимизация обновления без создания новых записей в обычных индексах.** Она возможна, когда не изменяются столбцы, используемые такими индексами, и новая версия строки помещается на той же странице. Для суммирующих индексов, например BRIN, действуют особые правила. [HOT-обновления](https://www.postgresql.org/docs/current/storage-hot.html)

Например, добавление B-tree по часто меняющемуся `orders.status` может лишить обновления статуса возможности HOT. Изменение столбца из `INCLUDE` тоже может препятствовать HOT.

**Нет фиксированной цены «один индекс = минус 10% скорости».** Сравнивай одинаковую нагрузку до и после: пропускную способность, p95 задержки записи, загрузку CPU, операции ввода-вывода и объём **WAL — журнала предзаписи**, используемого для восстановления.

Учитывай и отложенную работу: дополнительные индексы увеличивают нагрузку на очистку старых версий.

## 6.2. Размер и раздувание

**Bloat — раздувание структуры из-за накопившихся неиспользуемых записей и избыточно свободных страниц.** После массовых обновлений или удалений индекс может оставаться большим, хотя актуальных данных стало меньше.

Для первоначальной проверки:

```sql
SELECT indexrelname,
       pg_size_pretty(pg_relation_size(indexrelid)) AS size,
       idx_scan,
       last_idx_scan
FROM pg_stat_user_indexes
WHERE relid = 'public.orders'::regclass
ORDER BY pg_relation_size(indexrelid) DESC;
```

Здесь размер отдельного индекса получен через `pg_relation_size`. [Функции размера объектов](https://www.postgresql.org/docs/current/functions-admin.html#FUNCTIONS-ADMIN-DBSIZE)

**Большой размер сам по себе не доказывает bloat.** Причиной могут быть рост таблицы, широкие ключи, столбцы `INCLUDE` или предусмотренное свободное место.

Для более подробного исследования B-tree можно использовать `pgstatindex` из расширения `pgstattuple`: оно показывает плотность листовых страниц, пустые страницы и другие характеристики. Расширение должно быть установлено, а у пользователя должны быть права вызова. Проверка читает страницы и тоже создаёт нагрузку. [pgstattuple и pgstatindex](https://www.postgresql.org/docs/current/pgstattuple.html)

`VACUUM` освобождает место для повторного использования, но обычно не уменьшает физический размер файлов. Не запускай перестроение после каждого массового изменения: сначала оцени возможность повторного использования места. Если раздувание мешает работе, рассматривай `REINDEX` с учётом его нагрузки и блокировок. [Обслуживание индексов](https://www.postgresql.org/docs/current/sql-reindex.html)

## 6.3. CREATE INDEX CONCURRENTLY

**`CREATE INDEX CONCURRENTLY` строит индекс, позволяя продолжать обычные вставки, обновления и удаления.** Это полезно для заполненной таблицы, которую нельзя надолго закрывать для записи.

```sql
CREATE INDEX CONCURRENTLY orders_customer_created_idx
ON public.orders (customer_id, created_at DESC, id DESC);
```

Обычный `CREATE INDEX` блокирует запись на время построения. Конкурентное построение выполняет больше работы, включая два прохода по таблице, и может ждать завершения транзакций. **`CONCURRENTLY` не означает отсутствие блокировок, ожиданий или влияния на производительность.** [Конкурентное создание индексов](https://www.postgresql.org/docs/current/sql-createindex.html#SQL-CREATEINDEX-CONCURRENTLY)

Основные ограничения:

- команду нельзя выполнять внутри блока транзакции;
- на одной таблице одновременно выполняется только одно конкурентное построение;
- нужны свободное место и запас ресурсов;
- для родительской секционированной таблицы этот способ напрямую не поддерживается — требуется отдельный порядок работы с партициями.

Если используется система миграций, учитывай её автоматическую транзакционную обёртку.

**После ошибки может остаться индекс `INVALID`:** он не используется для запросов, но способен продолжать создавать расходы на запись. Проверь результат через `\d public.orders`; не считай наличие имени признаком успешного завершения. Такой индекс нужно осознанно удалить и создать заново либо восстановить поддерживаемым способом.

## 6.4. Удаление ненужных индексов

**Неиспользуемый индекс — кандидат на удаление, если его стоимость не оправдана чтением, ограничениями или другими обязанностями системы.**

Начни с `idx_scan` и `last_idx_scan` из `pg_stat_user_indexes`. **`idx_scan = 0` не является достаточным основанием:** окно наблюдения могло быть коротким, статистика — сброшенной, а важный отчёт — запускаться раз в месяц. Учитывай также нагрузку на читающих репликах. [Статистика использования индексов](https://www.postgresql.org/docs/current/monitoring-stats.html#MONITORING-PG-STAT-ALL-INDEXES-VIEW)

Перед удалением проверь:

- обслуживание `PRIMARY KEY`, `UNIQUE` и других ограничений;
- самостоятельное обеспечение уникальности индексом;
- использование для идентификации строк при репликации;
- редкие запросы и проверки внешних ключей;
- наличие действительно равноценной замены.

Например, более длинный составной индекс не всегда полностью заменяет короткий: различаются размер, предикат, порядок и уникальность.

Для проверенного обычного индекса на рабочей таблице возможен вариант:

```sql
DROP INDEX CONCURRENTLY public.orders_legacy_idx;
```

Он также выполняется вне блока транзакции. Индекс, обслуживающий `PRIMARY KEY` или `UNIQUE`-ограничение, таким способом удалить нельзя. [DROP INDEX](https://www.postgresql.org/docs/current/sql-dropindex.html)

Сохрани определение удаляемого индекса и после изменения проверь важные запросы и запись: повторное создание большого индекса потребует времени.

**Запомнить:** оценивай индекс по суммарной пользе: чтение, запись, место и обслуживание; создавай и удаляй его с учётом нагрузки, ограничений и реального использования.

# 7. Сравнение показателей до и после

## 7.1. Исходный замер

**Исходный замер — baseline: сохранённые показатели запроса до изменения.** Без него нельзя уверенно определить, помог ли индекс или переписывание SQL.

Сохрани запрос с конкретными параметрами и полный план:

```sql
EXPLAIN (ANALYZE, BUFFERS, VERBOSE, FORMAT JSON)
SELECT id, created_at, total_cents
FROM orders
WHERE customer_id = 42
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

`FORMAT JSON` удобен для автоматического сохранения и сравнения. Для ручного чтения можно оставить текстовый формат. [Форматы EXPLAIN](https://www.postgresql.org/docs/current/sql-explain.html)

Зафиксируй:

| Показатель | Зачем нужен |
|---|---|
| План и используемые индексы | Объяснить изменение способа выполнения |
| `Execution Time` | Сравнить время выполнения на сервере |
| `Planning Time` | Отдельно оценить затраты планирования |
| `shared hit`, `shared read` | Понять обращения к буферам |
| Фактические строки | Проверить объём результата и промежуточной работы |
| `loops` значимых узлов | Обнаружить многократно повторяющиеся операции |

**Для общих буферов бери показатели корневого узла выполнения, не сумму всех уровней:** родители уже включают потомков. Буферы планирования учитывай отдельно.

`actual rows` и время при нескольких `loops` являются средними на запуск. Сохраняй исходные значения, чтобы можно было восстановить общий объём работы. [Чтение фактического плана](https://www.postgresql.org/docs/current/using-explain.html#USING-EXPLAIN-ANALYZE)

Для переписанного запроса проверь также сами данные: одинаковое количество строк не гарантирует одинаковый результат.

## 7.2. Одинаковые условия и состояние кеша

**Сравнимый эксперимент меняет исследуемый фактор, сохраняя остальные существенные условия.** Если одновременно добавить индекс и увеличить память, вклад каждого изменения останется неизвестным.

Сохраняй одинаковыми:

- данные и их распределение, а не только количество строк;
- значения параметров и способ вызова, включая подготовленные запросы;
- настройки, версию PostgreSQL и ресурсы сервера;
- сопоставимую конкурентную нагрузку.

Например, одинаковое число заказов мало что говорит, если в одном наборе у покупателя 10 заказов, а в другом — миллион.

Проверь настройки памяти:

```sql
SHOW work_mem;
SHOW hash_mem_multiplier;
```

**`work_mem` — базовый лимит памяти отдельной операции**, например сортировки, а не всего запроса. Для хеширования учитывается и `hash_mem_multiplier`. Их изменение может убрать временные файлы и ускорить запрос независимо от нового индекса. [Настройки памяти](https://www.postgresql.org/docs/current/runtime-config-resource.html#GUC-WORK-MEM)

**Тёплый запуск** выполняется после предварительного чтения нужных данных. Прогрей каждый вариант отдельно, затем начинай измеряемую серию.

**Холодный запуск** требует явно описанного состояния кешей. Первый запуск в новой сессии не обязательно холодный: страницы могли остаться в PostgreSQL или кеше ОС. Создание индекса тоже читает данные и влияет на кеш.

`shared read` означает загрузку страницы в общий кеш PostgreSQL, а не обязательно физическое чтение накопителя. Если состояние кешей не контролировалось, честно обозначь результат как «первый наблюдаемый запуск», а не как гарантированно холодный.

## 7.3. Таблица результатов

**Таблица сравнения связывает конкретное изменение с измеренным эффектом.** Укажи единицы, режим запуска и способ объединения результатов серии.

Пример ниже полностью условный. Времена и счётчики представлены медианами отдельных показателей по сериям запусков.

| Запрос | Изменение | Время до, мс | После, мс | `shared read` до | После |
|---|---|---:|---:|---:|---:|
| Q1, тёплый | Индекс по покупателю и порядку выдачи | 120 | 12 | 0 | 0 |
| Q1, холодный | Тот же индекс | 400 | 35 | 9000 | 60 |

Рядом сохрани параметры Q1, описание данных, настройки, число повторов и планы обеих версий.

**Нулевой `shared read` не означает отсутствие работы.** В условном тёплом сценарии `shared hit` мог уменьшиться с 12 000 до 80: обе версии читают из кеша, но выполняют разный объём обращений.

Счётчики буферов отражают обращения, а не обязательно количество уникальных страниц. Не называй их объёмом физического дискового чтения. [Показатели BUFFERS](https://www.postgresql.org/docs/current/sql-explain.html)

Если есть `temp read/written`, добавь их отдельно. Исчезновение записи временных данных может объяснять ускорение лучше, чем изменение `shared read`.

## 7.4. Повторное подтверждение

**Один удачный запуск — наблюдение, а не устойчивый вывод.** На время влияют кеш, фоновые процессы, блокировки и конкурирующие запросы.

Практический порядок:

1. Выполни прогрев каждой версии.
2. Собери серию измерений, например 5–10 для первичной проверки.
3. Сравни медиану и разброс, сохрани все результаты.
4. Повтори серию, если эффект нестабилен или сопоставим с разбросом.
5. Проверь другие характерные параметры: редкого и крупного покупателя, разные диапазоны дат.

Не выбирай только лучшие результаты и не исключай медленные запуски без объяснения. Для выводов о редких задержках нужна существенно большая выборка.

**Сопоставь ускорение с планом:** стало ли меньше повторных поисков, чтений или сортировок? Затем проверь обычное выполнение приложения: `EXPLAIN ANALYZE` добавляет измерительные расходы и не отражает передачу результата клиенту.

Вывод формулируй с границами: «На этом наборе данных и параметрах медиана тёплого выполнения уменьшилась; для крупных покупателей нужна отдельная проверка».

**Запомнить:** сохраняй baseline, сравнивай одинаковые условия, разделяй режимы кеша и подтверждай эффект серией измерений вместе с объяснением изменения плана.
