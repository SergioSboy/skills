# Redis / Valkey

## Цель

Спроектировать кеширование на Redis или Valkey: схему ключей, TTL, инвалидацию
и поведение сервиса, когда кеш недоступен.

## План изучения

### 1. Место кеша в системе

- Определять, какие данные допустимо отдавать устаревшими и на какой срок.
- Отделять кеш от источника истины: кеш ускоряет чтение и не хранит
  единственную копию данных, без которых сервис не восстановится.
- Оценивать соотношение чтений и записей и размер рабочего набора.
- Фиксировать, какой ответ считает правильным продукт при устаревших данных.

### 2. Структуры данных

- Выбирать тип под задачу: string, hash, set, sorted set, list, stream.
- Использовать hash для объекта с полями, set для членства, sorted set для
  ранжирования и ограничения по времени.
- Задавать схему имён ключей: префикс сервиса, сущность, идентификатор,
  версия формата.
- Ограничивать размер значения и не кешировать ответ, который зависит от
  прав конкретного пользователя, без учёта этого в ключе.

### 3. Стратегии чтения и записи

- Разобрать cache-aside: чтение из кеша, при промахе чтение из БД и запись в
  кеш.
- Разобрать write-through и write-behind и цену расхождения с БД.
- Выбирать cache-aside как базовый вариант для данных, источник которых —
  PostgreSQL.
- Не писать в кеш и в БД как в два независимых источника истины.

### 4. TTL и защита от лавины

- Назначать TTL по допустимой устареваемости, а не одним значением на все
  ключи.
- Добавлять случайный разброс TTL, чтобы ключи не истекали одновременно.
- Защищаться от cache stampede: блокировка на время пересчёта, singleflight
  или вероятностное раннее обновление.
- Задавать короткий TTL для данных, которые часто меняются, и более длинный
  для справочников.

### 5. Инвалидация

- Удалять или обновлять ключ в той же операции, которая меняет источник
  истины.
- Версионировать ключ, если точечно удалить все зависимые записи трудно.
- Учитывать гонку: чтение успевает записать старое значение после
  инвалидации.
- Проверять, что после записи API отдаёт новое значение и при попадании в
  кеш, и при промахе.

### 6. Недоступность кеша

- Задавать короткий таймаут соединения и команды, чтобы ожидание кеша не
  занимало пул приложения.
- При ошибке или таймауте читать источник истины и не класть в кеш ответ,
  полученный в момент сбоя, если это усиливает нагрузку.
- Ограничивать число одновременных обращений в БД при массовом промахе.
- Описывать деградацию: какие операции продолжают работать, какие отвечают
  ошибкой, какой рост нагрузки допустим на БД.

### 7. Память и вытеснение

- Задавать `maxmemory` и политику вытеснения под тип данных.
- Понимать разницу между вытеснением с учётом TTL и вытеснением любых ключей.
- Следить за числом вытеснений, фрагментацией и долей попаданий.
- Не использовать кеш как очередь задач и как постоянное хранилище в одном
  экземпляре без отдельного решения.

### 8. Наблюдаемость

- Снимать долю попаданий, задержку команд, число ошибок, вытеснения и
  занятую память.
- Различать промах из-за TTL, инвалидации и нехватки памяти.
- Задавать алерт на недоступность, рост ошибок и падение доли попаданий.
- Сверять метрики кеша с метриками БД: рост чтений БД при отказе кеша.

### 9. Redis и Valkey

- Понять, что Valkey — ответвление Redis с совместимым протоколом команд для
  типового кеширования.
- Проверять на выбранной версии команды, политику вытеснения и параметры
  персистентности, которые использует проект.
- Фиксировать в проекте конкретный сервер и версию, на которых проверена
  схема.

## Практический проект

Спроектировать и поднять кеш для чтения одной сущности, например карточки
товара или профиля:

- схема ключей, TTL и правило инвалидации при изменении записи;
- защита от одновременного пересчёта одного ключа;
- таймаут и поведение приложения при остановленном Redis или Valkey;
- проверка четырёх случаев: попадание, промах, инвалидация после записи,
  недоступный кеш;
- оценка, насколько вырастает нагрузка на БД, пока кеш недоступен.

## Критерии завершения

- Для кешируемых данных заданы ключ, TTL и способ инвалидации.
- После изменения источника истины клиент не получает прежнее значение дольше
  оговорённого окна.
- При остановленном кеше сервис читает БД и не зависает на таймауте кеша.
- Описано, какие операции деградируют и какой рост нагрузки на БД допустим.
- Схема проверена на Redis или Valkey указанной версии.
