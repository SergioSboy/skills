# CQRS

## Цель

Научиться разделять модели записи и чтения (Command Query Responsibility
Segregation), определять, когда такое разделение оправдано, и поддерживать
согласованность read-моделей с источником истины.

## План изучения

### 1. Основные понятия

- Разобрать принцип CQS: метод либо изменяет состояние, либо возвращает
  данные.
- Понять, чем CQRS отличается от CQS: разделяются модели, а не только методы.
- Разобрать команду как намерение изменить состояние и запрос как чтение без
  побочных эффектов.
- Отличать CQRS от Event Sourcing и понимать, что они применяются независимо.

### 2. Модель записи

- Проектировать команды: имя в повелительном наклонении, данные, инициатор,
  идентификатор для идемпотентности.
- Валидировать команду и проверять инварианты в агрегате.
- Возвращать из команды результат принятия, а не данные для отображения.
- Обрабатывать конкурентные изменения через оптимистичную блокировку.

### 3. Модель чтения

- Проектировать read-модель под конкретный экран или API, а не под домен.
- Денормализовать данные и заранее вычислять агрегаты.
- Выбирать хранилище для чтения: та же БД, отдельные таблицы, поисковый
  индекс, кеш.
- Не размещать бизнес-правила в обработчиках запросов.

### 4. Уровни разделения

- Разобрать CQRS внутри одного сервиса и одной базы данных.
- Разобрать отдельные таблицы или схемы для чтения в той же базе.
- Разобрать отдельные хранилища для записи и чтения.
- Оценивать, какую сложность добавляет каждый уровень.

### 5. Синхронизация read-моделей

- Обновлять проекции синхронно в той же транзакции и асинхронно по событиям.
- Публиковать изменения через outbox или CDC.
- Делать проекции идемпотентными и устойчивыми к повторной доставке.
- Перестраивать проекцию с нуля при изменении её структуры.

### 6. Итоговая согласованность

- Измерять задержку обновления read-модели.
- Проектировать интерфейс с учётом задержки: оптимистичное отображение,
  read-your-writes, статус «обрабатывается».
- Определять сценарии, где задержка недопустима, и читать их из модели записи.
- Обнаруживать и исправлять расхождение проекции с источником истины.

### 7. CQRS и Event Sourcing

- Разобрать хранение состояния как последовательности событий.
- Строить проекции по журналу событий.
- Учитывать снимки (snapshots), версионирование событий и рост журнала.
- Понять, когда Event Sourcing избыточен для задачи.

### 8. Границы применимости

- Определять, когда CQRS оправдан: разные профили нагрузки на чтение и запись,
  сложные отчёты, несколько представлений одних данных.
- Определять, когда он избыточен: простой CRUD, небольшая нагрузка, требование
  немедленной согласованности везде.
- Учитывать стоимость: больше кода, инфраструктуры и мониторинга.
- Фиксировать решение и альтернативу в ADR.

## Практический проект

Применить CQRS к сервису заказов:

- команды `PlaceOrder`, `CancelOrder`, `ConfirmPayment` с валидацией и
  идемпотентностью;
- агрегат заказа с инвариантами и оптимистичной блокировкой;
- две read-модели: список заказов покупателя и сводный отчёт оператора;
- асинхронное обновление проекций через outbox и брокер сообщений;
- перестроение одной проекции с нуля скриптом или командой;
- метрика задержки обновления read-модели и тесты на повторную доставку;
- ADR с обоснованием выбранного уровня разделения.

## Критерии завершения

- Команды не возвращают данные для отображения, запросы не меняют состояние.
- Read-модели спроектированы под сценарии чтения и не содержат бизнес-правил.
- Повторная доставка события не искажает проекцию.
- Проекцию можно перестроить без потери данных.
- Задержка согласованности измеряется и учтена в интерфейсе.
- Выбор CQRS и уровня разделения обоснован в ADR.
