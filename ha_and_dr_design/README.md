# Проектирование решений с учётом HA и DR

## Цель

Подготовить общий план отказов и восстановления для компонентов решения
и их зависимостей, а не отдельную схему только для базы или только для
приложения.

## План изучения

### 1. Граница решения

- Выделять компоненты решения: приложение, база, кэш, брокер,
  балансировщик, внешние API, DNS, хранилище секретов.
- Для каждого указывать владельца и то, может ли команда сама выполнить
  переключение.
- Отделять зависимости, отказ которых решение обязано пережить, от
  зависимостей, при отказе которых сценарий останавливается.
- Фиксировать один основной пользовательский сценарий, по которому
  считается доступность.

### 2. Цели по компонентам

- Задавать для компонента класс отказа: процесс, узел, площадка.
- Назначать RPO и RTO там, где есть состояние. Для компонента без
  состояния задавать время возврата экземпляра, а не RPO.
- Не ставить всем компонентам одинаковые цифры без причины.
- Согласовывать цель сценария с самым медленным обязательным звеном.

### 3. Отказ узла и потеря площадки

- Для каждого компонента описывать поведение при отказе одного узла и
  отдельно при потере площадки.
- Помечать, где есть только высокая доступность внутри площадки и где
  есть катастрофоустойчивость.
- Проверять, что резерв приложения и резерв базы лежат согласованно:
  живое приложение не пишет в базу потерянной площадки.
- Учитывать общий отказ стойки и сети, а не только остановку одного
  процесса.

### 4. Зависимости и порядок восстановления

- Строить порядок: сеть и DNS, хранилище секретов, база, брокер,
  приложение, проверка сценария.
- Называть зависимость, без которой следующий шаг невозможен.
- Описывать деградацию на время, пока зависимость ещё не восстановлена.
- Проверять циклы: компонент ждёт другой, а тот ждёт первый.

### 5. Переключение клиентов

- Описывать, как клиенты и соседние системы узнают новый адрес.
- Учитывать кэш DNS, пулы соединений и регистрацию в балансировщике.
- Задавать окно, в котором допустимы ошибки, и правило повтора.
- Проверять, что старая площадка не принимает запись после перевода.

### 6. Общий план

- Сводить в одну таблицу: компонент, отказ, обнаружение, действие, RPO,
  RTO, зависимость, проверка.
- Писать действия так, чтобы их выполнил дежурный без устных пояснений.
- Отмечать автоматические шаги и шаги, которые запускает человек.
- Опираться на планы высокой доступности и катастрофоустойчивости базы,
  не копируя их целиком.

### 7. Проверка плана

- Выбирать два сценария: отказ одного узла приложения или базы и потеря
  зависимости или площадки.
- Проходить план по шагам и отмечать то, что на проверке не сходится.
- Записывать фактическое время и расхождение с целью.
- Обновлять таблицу по результату проверки.

## Практический проект

Собрать общий план для решения, в котором есть хотя бы приложение, база
и одна внешняя зависимость:

- таблица компонентов с целями отказа узла и потери площадки;
- порядок восстановления и зависимости между шагами;
- деградация на время недоступности внешней зависимости;
- сценарий отказа одного узла, согласованный с резервированием
  приложения и высокой доступностью базы;
- список ручных шагов и условие запуска плана площадки.

## Критерии завершения

- У каждого компонента есть сценарий отказа узла и отдельно сценарий
  потери площадки либо явная пометка, что второго сценария нет.
- RPO и RTO заданы для состояния и не противоречат плану базы.
- Порядок восстановления учитывает зависимости и не содержит цикла.
- Описано, как клиенты переходят на резерв и как старый узел перестаёт
  принимать запись.
- План проверен хотя бы одним сценарием отказа и поправлен по результату.
