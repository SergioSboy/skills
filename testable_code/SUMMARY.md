# Тестируемый код и юнит-тесты

# 1. Основные понятия

## 1.1. Юнит-тест и другие виды тестов

**Юнит-тест проверяет небольшую единицу поведения быстро и в контролируемых условиях.** Обычно без реальной сети, БД и других медленных внешних ресурсов.

Единица тестирования — не обязательно один метод или класс. Несколько объектов могут вместе реализовывать одно поведение.

| Вид теста | Что проверяет | Пример |
|---|---|---|
| **Юнит** | Отдельное правило или поведение | Пустой заказ нельзя подтвердить |
| **Интеграционный** | Совместную работу частей, включая реальные технические зависимости | Репозиторий правильно сохраняет заказ в PostgreSQL |
| **Контрактный** | Совместимость ожиданий сторон взаимодействия | API платежей возвращает поля, необходимые заказам |
| **End-to-end — E2E** | Полный сценарий через основные слои системы | Покупатель оформляет заказ через браузер и видит результат |

Пример юнит-теста на Ruby с RSpec:

```ruby
it "не позволяет подтвердить пустой заказ" do
  order = Order.new(items: [])

  expect { order.confirm }
    .to raise_error(EmptyOrder)
end
```

**Названия категорий могут различаться между командами.** Важно договориться о границах: какие части запускаются реально, а какие заменяются.

Контрактные тесты не доказывают корректность полного процесса, а юнит-тесты не проверяют реальную настройку БД и сети.

## 1.2. Пирамида тестирования и Testing Trophy

**Пирамида тестирования** предлагает иметь много быстрых проверок и меньше дорогих сквозных тестов.

```text
          / E2E — немного \
         / Интеграционные \
        / Юнит-тесты — много \
```

Идея: большинство ошибок обнаруживать быстро и близко к их причине. E2E сохраняют для критических пользовательских сценариев.

**Testing Trophy — «трофей тестирования»** делает больший акцент на интеграционных тестах, проверяющих поведение нескольких частей вместе.

Его уровни снизу вверх:

| Уровень | Назначение |
|---|---|
| **Статические проверки** | Находить ошибки без выполнения сценариев: типизация, линтеры |
| **Юнит-тесты** | Проверять отдельную сложную логику |
| **Интеграционные тесты** | Давать основную уверенность в совместной работе частей |
| **E2E** | Проверять ключевые сквозные сценарии |

**Это ориентиры, а не обязательные пропорции.** Для расчётной библиотеки особенно полезны юнит-тесты; для приложения, соединяющего множество компонентов, существенную роль играют интеграционные.

Контрактные тесты дополняют набор проверок на границах систем и не имеют обязательного места в этих схемах.

## 1.3. Свойства хорошего теста: FIRST

| Свойство | Смысл |
|---|---|
| **Fast — быстрый** | Выполняется достаточно быстро для частого запуска |
| **Independent — независимый** | Не зависит от других тестов и порядка выполнения |
| **Repeatable — повторяемый** | При одинаковых условиях даёт одинаковый результат |
| **Self-validating — самопроверяющийся** | Сам сообщает об успехе или ошибке через проверки |
| **Timely — своевременный** | Пишется вовремя, когда ещё может помочь проектированию |

Практические следствия:

- каждый тест сам подготавливает необходимые данные;
- тесты не оставляют общее изменяемое состояние;
- время и случайность контролируются, если влияют на результат;
- результат проверяется автоматически, без просмотра логов;
- тесты пишут до или вместе с реализацией, пока правила понятны.

**Independent не означает «заменить все соседние объекты моками».** Это прежде всего независимость тестов друг от друга.

Дополнительно хороший тест имеет понятное название, проверяет значимое поведение и не ломается от рефакторинга, который сохраняет это поведение.

## 1.4. Классическая и лондонская школы

Школы различаются прежде всего тем, **как изолируют проверяемое поведение и используют зависимости**.

| | Классическая, или детройтская | Лондонская |
|---|---|---|
| Соседние объекты | Обычно реальные, если быстрые и управляемые | Часто заменяются тестовыми двойниками |
| Основной акцент | Результат и состояние | Взаимодействия с зависимостями |
| Единица проверки | Может включать несколько связанных объектов | Часто отдельный объект |
| Основной риск | Более сложная подготовка и локализация ошибки | Привязка тестов к внутренней структуре вызовов |

**Классический подход:** создать настоящий заказ и позиции, добавить товар, проверить итоговую сумму.

**Лондонский подход:** передать сценарию двойник хранилища и проверить, что сценарий поручил ему сохранить заказ.

```ruby
repository = double("Repository")
order = Order.new(items: [item])

expect(repository).to receive(:save).with(order)

ConfirmOrder.new(repository: repository).call(order)
```

Этот тест проверяет взаимодействие с хранилищем. Он **не доказывает**, что реальный репозиторий сохраняет данные правильно.

Обе школы используют тестовые двойники, но с разной интенсивностью. Практический ориентир:

- чистую бизнес-логику проверяй на реальных объектах;
- внешние ресурсы заменяй там, где нужна быстрая контролируемая проверка;
- проверяй вызовы, когда само взаимодействие является важным требованием;
- реальные адаптеры проверяй интеграционными тестами.

**Запомнить:** тест должен защищать нужное поведение и давать понятную обратную связь. Изоляция — средство для этого, а не цель сама по себе.

# 2. Структура теста

## 2.1. Arrange–Act–Assert и Given–When–Then

**Тест удобно разделять на подготовку, действие и проверку.**

| Arrange–Act–Assert | Given–When–Then | Смысл |
|---|---|---|
| **Arrange** | **Given** | Подготовить исходные условия |
| **Act** | **When** | Выполнить проверяемое действие |
| **Assert** | **Then** | Проверить результат |

Пример на Ruby с RSpec:

```ruby
it "подтверждает заказ с позициями" do
  # Arrange
  order = Order.new(items: [item])

  # Act
  order.confirm

  # Assert
  expect(order.status).to eq(:confirmed)
end
```

Given–When–Then чаще формулируют как сценарий:

> **Дано:** заказ содержит позицию.  
> **Когда:** заказ подтверждают.  
> **Тогда:** он переходит в состояние «Подтверждён».

Комментарии необязательны, если структура понятна без них. Сложную подготовку можно вынести в помощники, сохранив важные условия видимыми в тесте.

## 2.2. Одно поведение в одном тесте

**Один тест проверяет один связный сценарий, а не обязательно содержит одну проверку.**

Например, отклонение операции может требовать двух утверждений:

```ruby
it "не позволяет подтвердить пустой заказ" do
  order = Order.new(items: [])

  expect { order.confirm }.to raise_error(EmptyOrder)
  expect(order.status).to eq(:draft)
end
```

Оба утверждения относятся к одному поведению: подтверждение отклонено, состояние не изменилось.

Не стоит объединять создание, подтверждение, оплату и отмену в один юнит-тест. При ошибке будет трудно понять, какое правило нарушено.

Разделяй существенные случаи:

- допустимое действие;
- нарушение бизнес-правила;
- граничное значение;
- недопустимый переход состояния.

Общую подготовку можно переиспользовать, но тесты должны выполняться независимо.

## 2.3. Имена, описывающие поведение

**Название объясняет условие и ожидаемый результат.**

Хорошие примеры:

```ruby
it "отклоняет позицию с нулевым количеством"
it "не позволяет менять подтверждённый заказ"
it "возвращает прежний результат при повторе ключа"
```

Неудачные:

```ruby
it "тестирует confirm"
it "работает правильно"
it "вызывает private_validate_items"
```

Последний пример привязывает тест к внутреннему устройству. Внутренний метод можно заменить, сохранив поведение, — такой рефакторинг не должен ломать тест.

RSpec позволяет распределить условие и результат между блоками:

```ruby
describe "#confirm" do
  context "когда заказ пустой" do
    it "отклоняет подтверждение" do
      # ...
    end
  end
end
```

**Проверка названия:** можно ли понять нарушенное правило из отчёта, не открывая тест?

## 2.4. Фабрики, билдеры и фикстуры

**Подготовка данных должна показывать условия сценария, а не заставлять читателя разбирать большую заготовку.**

| Инструмент | Назначение |
|---|---|
| **Фабрика** | Создать корректный объект с разумными значениями по умолчанию |
| **Билдер** | Пошагово собрать объект, явно задавая важные особенности |
| **Фикстура** | Предоставить заранее подготовленные данные, например записи или JSON |

Пример идеи билдера:

```ruby
order = OrderBuilder.new
  .with_item(quantity: 2, price: 100)
  .build
```

В тесте видно существенное условие: заказ содержит два товара по указанной цене.

**FactoryBot** часто используют в Rails для создания тестовых объектов:

```ruby
order = build(:order, status: :draft)
```

Различай операции:

- `build` создаёт объект без сохранения;
- `create` сохраняет его в БД;
- `build_stubbed` имитирует сохранённый объект без обычной записи в БД.

`build_stubbed` не заменяет проверку реального сохранения. Также следи за ассоциациями и callbacks: подготовка может неожиданно создавать дополнительные данные или выполнять побочные действия.

Для юнит-теста предпочитай простой конструктор, билдер или фабрику без БД. Для интеграционного теста реальные сохранённые записи могут быть необходимы.

**Фикстуры не запрещены:** небольшой пример ответа внешнего API удобно хранить как JSON. Проблема — громоздкие общие наборы, от которых тест зависит неявно.

**Запомнить:** подготовка объясняет условия, действие выделяет проверяемую операцию, проверки подтверждают одно поведение, название сообщает его смысл.

# 3. Признаки нетестируемого кода

## 3.1. Скрытые зависимости

**Скрытая зависимость — ресурс или объект, который код использует, но не получает явно.** Тесту трудно управлять такой зависимостью.

Пример:

```ruby
class PayOrder
  def call(order)
    client = BankClient.new
    client.charge(order.total)
  end
end
```

Сценарий сам выбирает клиент банка. Чтобы проверить его без сети, приходится вмешиваться в создание объекта.

Явная зависимость:

```ruby
class PayOrder
  def initialize(payment_client:)
    @payment_client = payment_client
  end

  def call(order)
    @payment_client.charge(order.total)
  end
end
```

В приложении передают настоящий клиент, в тесте — управляемый двойник.

Другие источники скрытых зависимостей:

- глобальные переменные;
- изменяемые настройки, общие для всех тестов;
- синглтоны с состоянием;
- глобальные реестры объектов.

**Сам по себе `new` не является проблемой.** Создать `Money.new(...)` внутри расчёта нормально. Особого внимания требует создание инфраструктурных зависимостей с побочными эффектами.

## 3.2. Время, случайность и внешние ресурсы

Прямые обращения к окружению затрудняют повторяемую проверку:

| Зависимость | Что мешает тесту | Как сделать управляемой |
|---|---|---|
| **Время** | Результат зависит от момента запуска | Передать время или часы |
| **Случайность** | Результаты меняются между запусками | Передать генератор или готовое значение |
| **Файловая система** | Нужны файлы, права и очистка | Отделить чтение от обработки данных |
| **Сеть** | Возможны задержки и недоступность | Использовать адаптер с явным интерфейсом |
| **БД** | Нужны инфраструктура и подготовка записей | Отделить бизнес-правила от хранения |

Пример проверки срока резерва:

```ruby
class Reservation
  def initialize(expires_at:)
    @expires_at = expires_at
  end

  def expired?(now:)
    now >= @expires_at
  end
end
```

Тест задаёт точное время без ожидания:

```ruby
it "считает резерв истёкшим в момент окончания срока" do
  deadline = Time.utc(2026, 1, 1, 12)
  reservation = Reservation.new(expires_at: deadline)

  expect(reservation.expired?(now: deadline)).to be true
end
```

**Внешние ресурсы всё равно нужно проверять**, но отдельно интеграционными тестами. Их изоляция в юнит-тесте не доказывает правильность реального подключения.

## 3.3. Длинные методы и смешанные обязанности

Метод становится трудным для проверки, когда одновременно:

```text
Читает запрос
    ↓
Загружает данные из БД
    ↓
Рассчитывает скидку
    ↓
Вызывает платёжный API
    ↓
Сохраняет результат
    ↓
Отправляет письмо
```

Чтобы проверить одну скидку, тест вынужден подготовить весь сценарий.

**Отделяй вычисления от побочных эффектов:**

- расчёт получает данные и возвращает результат;
- прикладной сценарий координирует действия;
- адаптеры работают с БД, сетью и файлами.

Например:

```ruby
class DiscountCalculator
  def calculate(total:, customer_category:)
    customer_category == :regular ? total * 0.1 : 0
  end
end
```

Этот расчёт можно проверить без платежей и БД.

**Длина метода — сигнал, а не доказательство проблемы.** Важнее количество обязанностей, ветвлений и зависимостей. Простое разбиение на приватные методы не устраняет смешение ответственности.

## 3.4. Статические вызовы и «божественные» объекты

В Ruby аналог статических вызовов — методы класса или модуля:

```ruby
BankClient.charge(...)
GlobalSettings.current
Time.now
```

**Такие вызовы не обязательно плохие.** Чистая функция с явными аргументами легко тестируется. Проблема возникает, если вызов скрывает изменяемое состояние, инфраструктуру или выбор конкретной реализации.

**«Божественный» объект** объединяет много несвязанных обязанностей: заказы, оплату, отчёты, письма и настройки.

Признаки:

- много зависимостей в конструкторе;
- для простого теста нужны многочисленные заглушки;
- объект меняется по разным причинам;
- тесты ломаются при изменениях несвязанной функции.

Помогает разделение по ответственности: доменная модель защищает правила, сценарий координирует процесс, адаптеры выполняют технические операции.

Не нужно превращать каждую функцию в отдельный класс. Цель — понятные границы и управляемые зависимости.

**Запомнить:** трудности подготовки теста часто показывают проблемы дизайна. Если для проверки одного правила приходится запускать полсистемы или подменять множество внутренних вызовов, стоит пересмотреть границы кода.

# 4. Приёмы проектирования тестируемого кода

## 4.1. Внедрение зависимостей

**Внедрение зависимостей — передача необходимых объектов снаружи вместо их скрытого создания внутри логики.**

Через конструктор передают зависимости, которые используются на протяжении жизни объекта:

```ruby
class PlaceOrder
  def initialize(repository:, clock:)
    @repository = repository
    @clock = clock
  end

  def call(items:)
    order = Order.new(
      items: items,
      created_at: @clock.now
    )

    @repository.save(order)
  end
end
```

Через параметры метода передают данные и зависимости конкретной операции:

```ruby
reservation.expired?(now: clock.now)
```

В приложении используют настоящие реализации, в тесте — контролируемые.

**Не нужно внедрять каждое создание объекта.** Конструирование обычного объекта-значения внутри бизнес-логики обычно не мешает тестированию.

## 4.2. Зависимость от абстракций

**Бизнес-коду нужна возможность выполнить действие, а не знание конкретной технологии.**

Например, сценарию требуется контракт:

```text
repository.save(order)
Сохраняет заказ или сообщает об ошибке.
```

Его могут реализовать:

```ruby
PostgresOrderRepository
InMemoryOrderRepository
```

В Ruby используют **duck typing**: объект подходит, если предоставляет необходимые методы с ожидаемым поведением. Отдельный класс-интерфейс необязателен.

```ruby
class InMemoryOrderRepository
  attr_reader :orders

  def initialize
    @orders = []
  end

  def save(order)
    @orders << order
    order
  end
end
```

**Контракт включает не только название метода**, но и аргументы, результат, ошибки и смысл операции. Совпадения имени `save` недостаточно, если реализации ведут себя по-разному.

## 4.3. Functional Core, Imperative Shell

**Функциональное ядро вычисляет результат. Императивная оболочка получает данные и выполняет побочные эффекты.**

```text
Оболочка: получить данные
             ↓
Ядро: проверить правила и вычислить решение
             ↓
Оболочка: сохранить результат или вызвать внешний сервис
```

Пример ядра:

```ruby
def payable_amount(subtotal:, discount:)
  raise ArgumentError if subtotal.negative?
  raise ArgumentError unless discount.between?(0, subtotal)

  subtotal - discount
end
```

Пример оболочки:

```ruby
subtotal = repository.subtotal(order_id)
discount = discounts.for(order_id)

amount = payable_amount(
  subtotal: subtotal,
  discount: discount
)

payment_client.charge(order_id: order_id, amount: amount)
```

Ядро проверяется обычными входами и ожидаемыми результатами, без БД и сети. Оболочка проверяется на правильную координацию, а реальные адаптеры — интеграционными тестами.

**Это принцип разделения, а не требование писать всё функционально.** Доменные объекты тоже могут содержать хорошо изолированные правила.

## 4.4. Чистые функции и неизменяемые значения

**Чистая функция:**

- при одинаковых аргументах возвращает одинаковый результат;
- не изменяет внешнее состояние;
- не выполняет скрытых обращений к окружению.

Расчёт суммы по переданным позициям может быть чистым. Чтение `Time.now`, запись в БД или изменение глобальной переменной нарушают эти свойства.

**Неизменяемый Value Object** нельзя изменить после создания. Для нового значения создают новый объект.

```ruby
class Money
  attr_reader :cents, :currency

  def initialize(cents:, currency:)
    @cents = Integer(cents)
    @currency = String(currency).dup.freeze
    freeze
  end

  def +(other)
    raise ArgumentError, "Разные валюты" unless currency == other.currency

    Money.new(
      cents: cents + other.cents,
      currency: currency
    )
  end
end
```

Сложение создаёт новое значение и не меняет исходные объекты. Это уменьшает риск, что одна часть программы неожиданно повлияет на другую.

**В Ruby `freeze` не замораживает вложенные объекты автоматически.** Строки, массивы и другие изменяемые значения нужно защищать отдельно. Полный Value Object также определяет равенство по значениям.

## 4.5. Clock, IdGenerator и Config

**Источники времени, идентификаторов и настроек делают явными зависимостями**, если они влияют на поведение.

| Объект | Контракт | Что даёт тесту |
|---|---|---|
| **Clock** | `now` | Фиксированное время |
| **IdGenerator** | `generate` | Предсказуемый идентификатор |
| **Config** | Именованные настройки | Контролируемые параметры без изменения глобального окружения |

Пример часов:

```ruby
class SystemClock
  def now
    Time.now
  end
end

class FixedClock
  def initialize(time:)
    @time = time
  end

  def now
    @time
  end
end
```

Тест передаёт фиксированные часы:

```ruby
clock = FixedClock.new(time: Time.utc(2026, 1, 1, 12))
```

Настройки из `ENV` читают и проверяют при сборке приложения, затем передают нужные значения компонентам. Генератор случайности изолируют аналогично.

**Добавляй такие объекты там, где они полезны.** Если функции достаточно аргумента `now:`, отдельный Clock внутри неё не нужен.

**Запомнить:** явные зависимости позволяют управлять условиями теста, чистое ядро изолирует правила, неизменяемые значения уменьшают неожиданные побочные эффекты.

# 5. Тестовые двойники

## 5.1. Dummy, stub, spy, mock и fake

**Тестовый двойник — объект, который заменяет зависимость в тесте.** Вид определяется его ролью, а не названием класса.

| Вид | Назначение | Пример |
|---|---|---|
| **Dummy** | Заполняет обязательный параметр, но не используется | Объект логгера в сценарии, который ничего не логирует |
| **Stub** | Возвращает заранее заданные ответы | Клиент платежей всегда возвращает успешный результат |
| **Spy** | Запоминает обращения для последующей проверки | Проверяем после действия, что письмо было отправлено |
| **Mock** | Проверяет заранее заданные ожидания взаимодействия | Ожидаем один вызов `refund` с нужной суммой |
| **Fake** | Имеет работающую, но упрощённую реализацию | Репозиторий, хранящий заказы в памяти |

Примеры на Ruby с RSpec:

```ruby
# Stub: задаём ответ зависимости
allow(clock).to receive(:now).and_return(fixed_time)

# Mock: заранее задаём ожидаемый вызов
expect(notifier).to receive(:send_confirmation).with(order.id)
order_service.confirm(order)

# Spy: проверяем вызов после действия
order_service.confirm(order)
expect(notifier).to have_received(:send_confirmation).with(order.id)
```

В примере со spy метод должен быть заранее подготовлен для записи вызовов — например, через `spy` или `allow(...).to receive(...)`.

**Один двойник может выполнять несколько ролей:** возвращать заданный ответ и записывать вызовы.

## 5.2. Когда использовать реальные объекты и двойники

**По умолчанию используй реальные объекты, если они быстрые, предсказуемые и не требуют внешних ресурсов.**

| Ситуация | Подход |
|---|---|
| Проверка расчёта или инварианта | Реальные доменные объекты |
| Нужно получить конкретный ответ зависимости | Stub |
| Важно само взаимодействие: отправка, публикация | Mock или spy |
| Нужны сохранение и последующее чтение без БД | Fake |
| Проверяется реальная работа БД или внешнего адаптера | Интеграционный тест |

Пример fake:

```ruby
class InMemoryOrderRepository
  def initialize
    @orders = {}
  end

  def save(order)
    @orders[order.id] = order
  end

  def find(id)
    @orders.fetch(id)
  end
end
```

**Fake не равен настоящей БД:** он может не воспроизводить ограничения, транзакции и конкурентный доступ. В этом примере также хранится ссылка на объект, поэтому его изменение будет видно без повторного `save`.

Общие ожидания от fake и реальной реализации полезно проверять одним набором тестов контракта. Особенности БД проверяют отдельно.

## 5.3. Собственные интерфейсы и внешние адаптеры

**Предпочитай подменять собственный интерфейс, а внешнюю библиотеку скрывать за адаптером.**

```text
Бизнес-сценарий → Наш PaymentGateway → SDK провайдера
```

Сценарий использует бизнес-понятную операцию:

```ruby
gateway.charge(order_id: order.id, amount: order.total)
```

Адаптер переводит её в формат конкретного SDK, а ответ — в собственный результат.

В юнит-тесте сценария:

```ruby
gateway = double("PaymentGateway")

allow(gateway).to receive(:charge)
  .with(order_id: order.id, amount: order.total)
  .and_return(payment_result)
```

Так тест не зависит от цепочки внутренних вызовов внешней библиотеки.

**Сам адаптер тоже проверяют:** преобразование параметров, статусов и ошибок, а затем реальную совместимость — интеграционными проверками или sandbox провайдера.

Это ориентир, а не абсолютный запрет: в тесте адаптера подмена SDK может быть уместна. Главное — не распространять детали SDK по тестам бизнес-логики.

## 5.4. Опасность чрезмерного мокирования

**Чрезмерное мокирование заставляет тест повторять устройство реализации вместо проверки результата.**

Сигналы:

- для простого поведения нужны десятки заглушек;
- проверяются приватные методы;
- задаётся порядок вызовов, хотя бизнесу он не важен;
- используются длинные цепочки подмен;
- обычный рефакторинг ломает множество тестов.

Например, тесту расчёта суммы обычно не нужно знать, какие внутренние методы вызваны. Ему важен итог:

```ruby
expect(order.total).to eq(expected_total)
```

Но проверка отправки уведомления уместна, если это требуемый внешний эффект:

```ruby
expect(notifier).to have_received(:send_confirmation).with(order.id)
```

Чтобы снизить хрупкость:

- проверяй результат и наблюдаемое поведение;
- используй реальные простые объекты;
- подменяй зависимости на устойчивых границах;
- проверяй взаимодействия только там, где они существенны;
- при возможности используй проверяющие двойники — `instance_double`, которые контролируют наличие методов и сигнатуры.

**Проверяющий двойник не доказывает смысловую корректность контракта.** Метод может существовать, но реальная реализация возвращать другой результат.

**Запомнить:** stub задаёт ответы, mock и spy проверяют взаимодействия, fake предоставляет упрощённое поведение. Выбирай минимальную подмену, достаточную для проверки сценария.

# 6. Test-Driven Development

## 6.1. Цикл Red–Green–Refactor

**TDD — разработка короткими циклами, в которых тест на новое поведение пишется до его реализации.**

```text
RED → GREEN → REFACTOR → следующий небольшой сценарий
```

- **Red:** написать тест и убедиться, что он падает по ожидаемой причине.
- **Green:** добавить достаточно кода, чтобы тест прошёл.
- **Refactor:** улучшить структуру, сохраняя все тесты зелёными.

Пример первого требования: сумма пустого заказа равна нулю.

```ruby
it "возвращает ноль для пустого заказа" do
  order = Order.new(items: [])

  expect(order.total).to eq(0)
end
```

Если `total` отсутствует, тест падает — это ожидаемый Red. Если он падает из-за случайной ошибки настройки, сначала исправляют настройку.

**Важно проходить все три шага.** Без рефакторинга временные решения начинают накапливаться.

## 6.2. Минимальный код для прохождения теста

Для первого теста допустима простейшая реализация:

```ruby
def total
  0
end
```

Она ещё не решает все будущие задачи. Следующий тест задаёт новое поведение:

```ruby
it "суммирует стоимость позиций" do
  order = Order.new(
    items: [
      Item.new(quantity: 2, price: 100),
      Item.new(quantity: 1, price: 50)
    ]
  )

  expect(order.total).to eq(250)
end
```

Теперь реализацию расширяют:

```ruby
def total
  @items.sum { |item| item.quantity * item.price }
end
```

**Минимальный код — без преждевременных возможностей и абстракций.** Если общее решение очевидно, не обязательно сначала писать константу.

Новые тесты добавляют по правилам и рискам: пустой набор, несколько позиций, недопустимое количество. Не нужно перечислять все возможные числа.

## 6.3. Проектирование «снаружи внутрь»

**Outside-in TDD начинается с поведения, нужного пользователю или вызывающему коду, и постепенно раскрывает внутренние зависимости.**

Например, сначала определяют удобный интерфейс сценария:

```ruby
result = place_order.call(items: items)

expect(result.order_id).not_to be_nil
```

Затем уточняют, что нужно сценарию:

```text
Оформить заказ
    ↓
Проверить бизнес-правила
    ↓
Сохранить заказ
    ↓
Запланировать уведомление
```

На границах могут появиться контракты `repository.save` и `notifier.schedule`. Для быстрого теста их можно заменить двойниками, затем реализовать и проверить настоящие адаптеры.

**Тест помогает увидеть неудобный интерфейс до реализации:** слишком много аргументов, скрытые зависимости или смешение обязанностей.

При этом outside-in — один из подходов к TDD. Можно начинать с доменной модели и двигаться наружу. Большое количество моков не является обязательным признаком TDD.

## 6.4. Когда TDD полезен

| Ситуация | Возможная польза |
|---|---|
| Чёткие бизнес-правила и граничные случаи | Правила сразу превращаются в проверяемые примеры |
| Сложные переходы состояния | Помогает двигаться небольшими шагами |
| Проектирование нового интерфейса | Позволяет сначала проверить удобство использования |
| Исправление ошибки | Воспроизводящий тест защищает от повторения |
| Изолированная логика | Даёт быструю обратную связь без инфраструктуры |

**Тесты после кода могут быть достаточны**, когда реализация проста, подход уже известен и риски невелики. Для исследовательского прототипа иногда сначала нужно выяснить, как вообще работает технология, а затем определить поведение и написать устойчивые проверки.

Для визуального интерфейса или интеграции с неизвестным API одного юнит-TDD недостаточно: нужны просмотр результата, эксперименты и интеграционные тесты.

**TDD не гарантирует хорошую архитектуру или полноту проверок.** Можно заранее написать тесты, которые проверяют не те требования или слишком привязаны к реализации.

**Запомнить:** TDD — короткая обратная связь: описать следующее поведение, реализовать его, улучшить код. Его ценность — в управляемых шагах и влиянии тестов на дизайн.

# 8. Тестирование унаследованного кода

## 8.1. Характеризационные тесты перед изменениями

**Характеризационный тест фиксирует фактическое поведение существующего кода.** Он помогает заметить случайное изменение при рефакторинге.

Перед правкой:

1. Определи затронутый сценарий.
2. Зафиксируй входные данные и наблюдаемый результат.
3. Добавь важные ветки и граничные случаи.
4. Убедись, что тесты проходят на исходной реализации.

Пример: в старом расчёте используется целочисленное деление.

```ruby
it "округляет десятипроцентную скидку вниз до целого" do
  calculator = LegacyDiscountCalculator.new

  expect(calculator.discount(105)).to eq(10)
end
```

Тест фиксирует существующее округление, но **не доказывает, что оно соответствует требованиям**.

Если обнаружено подозрительное поведение, его обсуждают отдельно. Изменение бизнес-правила и рефакторинг лучше разделять: сначала получить защиту, затем осознанно изменить ожидания.

Начинать можно с интеграционного теста, если изолировать участок пока сложно. Важнее защитить поведение, чем немедленно получить идеальный юнит-тест.

## 8.2. Швы для подмены зависимостей

**Шов — точка, в которой можно изменить поведение зависимости, не переписывая основную логику.**

В Ruby швом могут стать параметр, конструктор, отдельный метод или адаптер.

Было:

```ruby
class LegacyCheckout
  def call(order)
    BankClient.new.charge(order.total)
  end
end
```

Небольшое изменение создаёт управляемую границу:

```ruby
class LegacyCheckout
  def initialize(payment_client: BankClient.new)
    @payment_client = payment_client
  end

  def call(order)
    @payment_client.charge(order.total)
  end
end
```

Существующий вызов `LegacyCheckout.new` продолжает работать. В тесте передают двойник:

```ruby
client = double("PaymentClient")
allow(client).to receive(:charge).and_return(:paid)

checkout = LegacyCheckout.new(payment_client: client)
```

Такой конструктор — **переходный шаг**. Позже выбор реальной зависимости можно перенести в место сборки приложения.

Если менять код пока нельзя, временно подменяют существующий вызов. Но такие тесты сильнее зависят от реализации; шов с явным интерфейсом обычно устойчивее.

**Не нужно сразу устранять все зависимости.** Создай минимальный шов вокруг того участка, который предстоит менять.

## 8.3. Постепенное выделение тестируемой логики

**Выноси код небольшими шагами, сохраняя поведение после каждого шага.**

```text
Защитить сценарий тестом
          ↓
Выделить одну ответственность
          ↓
Проверить её отдельно
          ↓
Переключить старый код на новый объект
          ↓
Проверить прежний сценарий
```

Пример: расчёт стоимости находится в контроллере.

```ruby
# Было внутри контроллера
total = items.sum { |item| item.price * item.quantity }
total -= total / 10 if customer.regular?
```

Выделяем расчёт:

```ruby
class OrderTotal
  def calculate(items:, regular_customer:)
    total = items.sum { |item| item.price * item.quantity }
    regular_customer ? total - total / 10 : total
  end
end
```

Контроллер получает данные и вызывает объект. Расчёт проверяется отдельно без HTTP-запроса и БД.

При переносе учитывают исходное место логики:

| Откуда выносим | Что важно сохранить |
|---|---|
| **Контроллер** | Параметры, проверку доступа, HTTP-статус и формат ответа |
| **Callback** | Условия запуска, порядок, границы транзакции и количество выполнений |
| **ActiveRecord-модель** | Валидации, сохранение, блокировки и используемые точки входа |

**Не всю логику нужно выносить из модели.** Бизнес-правило, естественно принадлежащее сущности, может оставаться её поведением. Обычно отделяют внешние вызовы, сложную координацию и несвязанные обязанности.

Особенно осторожно работают с callbacks: простое перемещение отправки события из `after_commit` в обычный метод может изменить гарантию «отправлять только после успешного сохранения».

**Запомнить:** сначала зафиксируй поведение, затем найди небольшой шов и выделяй по одной ответственности. Цель — безопасные изменения, а не полная переделка за один раз.
