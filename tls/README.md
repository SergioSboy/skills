# Криптографические основы

## Симметричное шифрование

Сервер и клиент иммеют одинаковые ключи для расшифровки данных переданных по сети.

Клиентский ключ <-> Данные <-> Серверный ключ

Алгоритмы:
- AES
- ChaCha20-Poly1305
- 3DES (устаревший)

## Ассиметричное шифрование

Для того чтобы расшифровать сообщение применяется закрытый ключ,
для того чтобы зашифровать сообщение применяется откытый ключ.
Один ключ может только зашифровать другой только расшифровать данные

Клиентский ключ (открытый) <-> Данные <-> Серверный ключ (Закрытый)

Алгоритмы:
- RSA
- Diffie-Hellman
- Elliptic Curve Diffie-Hellman (ECDH)

## Симметричное VS Ассимитричное шифрование

Ассиметричное
- Открытый ключ может распространятся без ограничений
- Работает медленно

Симметричное
- Ключ должен хранится в тайне
- Работает быстро

Поэтому в TLS/SSL используется гибридное шифрование
- Симметричное шифрование для передачи данных
- Ассиметричное шифрование для передачи ключа симметричного шифрования

## Алгоритм обмена ключами RSA
1. Сервер хранит `открытый ключ` и `закрытый ключ`
2. Клиент отправляет запрос на установку защищеннего соединения с сервером
3. Сервер в ответ отправляет свой `закрытый ключ`
4. Клиент генерирует `ключ симметрично шифрования` используя полученный `открытый ключ`
5. Клиент передает зашифроанный `симметричный ключ шифрования` серверу
6. Сервер применяет `закрытый ключ` чтобы расшифровать `зашифрованный симметричный ключ`
7. Сервер и ключ имеют `симметричный ключ` и могут перейти к передаче данных

Недостатки:
- Не обеспечивается совершеная прямая секретность (perfect forward secrecy)
  Доступ к закрытому ключу сервера позволит расшифровать все передаваемые данные
- Уязвимости. Атака миллиона сообщений. ROBOT.
- RSA запрещено использовать начиная с версии TLS 1.3

## Алгоритм обмена ключами Диффи-Хеллмана
1. Сервер и ключ выбирают два числа `p` и `g`. Они могут быть открыты.
2. Для отправки ключей сервер и клиент выбирают секретные числа.
3. Клиент и сервер проводят расчеты с помощью модульной арифметики (`g` pow секретное число mod `p`)
4. Результаты от клиента серверу и наоборот
5. Клиент и сервер проводят расчеты с помощью модульной арифметики (`g` pow полученный результат mod `p` )
6. В результате клиент и сервер получают значение для `ключа симметричного шифрования`

Условия:
- p - большое простое число
- g - первообразный корень по модулю p, небольшое число
- Невозможно вычислить ключ даже на современных суперкомпьютерах

## Diffie-Hellman Ephemeral
- Вариант алгоритма обмена ключами
- Ключ симметричного шифрования генерируется для каждого соединения
- Совершенно прямая секретность
- Невозможно раскодировать зашифрованные данные, даже если есть доступ к серверу

## Алгоритм обмена ключами ECDHE

1. Сервер и клиент выбирают эллиптическую кривую и базовую точку `G`.
   Эти параметры могут быть открыты.

2. Для обмена ключами сервер и клиент генерируют
   случайные секретные числа.

3. Клиент и сервер вычисляют свои открытые ключи
   с помощью операций над эллиптической кривой:

   Клиент:
   `A = a × G`

   Сервер:
   `B = b × G`

   где:
  - `a` — секретное число клиента
  - `b` — секретное число сервера
  - `G` — общая базовая точка
  - `A` и `B` — открытые ключи

4. Клиент и сервер обмениваются открытыми ключами:

   Клиент → сервер: `A`
   Сервер → клиент: `B`

5. Клиент и сервер проводят расчёты с использованием
   своего секретного числа и полученного открытого ключа:

   Клиент:
   `S = a × B`

   Сервер:
   `S = b × A`

6. В результате клиент и сервер получают одинаковое
   общее секретное значение `S`.

7. Из этого общего секрета с помощью процедур TLS
   получают ключи симметричного шифрования,
   которыми затем шифруются данные соединения.


Условия:
- используется эллиптическая кривая;
- `G` — базовая точка кривой;
- `a` и `b` — секретные временные числа;
- `A` и `B` — открытые ключи;
- вычислить секретное число по открытому ключу
  вычислительно сложно (задача дискретного логарифмирования
  на эллиптической кривой).

Преимущества:
- меньшие ключи при высокой криптографической стойкости;
- секретные ключи генерируются заново для каждого соединения;
- обеспечивает Perfect Forward Secrecy (PFS).

## Криптографические хэш функции
Функции которые используют криптографию чтобы сгенерировать хэш
- MD5
- SHA-1, SHA-224, SHA-256, SHA-384, SHA-512

## Алгоритм Message Authentication Code (MAC)
1. Клиент расчитывает хэш не только с помощью данных но и с помощью `симметричного ключа шифрования` - MAC
2. Сервер получает данные и также расчитывает MAC с помощью `симметричного ключа шифрования`


## Цифровая подпись
1. Используются `открытый ключ` и `закрытый ключ`
2. Сервер генерирует используя `закрытый ключ` подпись с помощью данных, которые были представлены в виде хэша
3. Клиент получает сообщение к котром содежится подпись и данные
4. Клиент рассчитывает хэш используя полученные данные и расшифровывает хэш из полученной подписи

### X.509 и PKI

* **X.509** — стандарт формата цифровых сертификатов.
* **Сертификат** связывает **владельца** с его **открытым ключом**.
* Сертификат содержит: владелец, открытый ключ, срок действия, издатель (CA), цифровую подпись CA.
* **CA (удостоверяющий центр)** проверяет владельца и подписывает его сертификат своим **закрытым ключом**.
* Клиент проверяет подпись CA с помощью **открытого ключа CA**.
* **PKI (Public Key Infrastructure)** — инфраструктура для выпуска, хранения, проверки и отзыва сертификатов.
* Цепочка доверия:

```text
Root CA
   ↓
Intermediate CA
   ↓
Сертификат сайта
   ↓
Открытый ключ сайта
```

## Набор шифров TLS/SSL
- Алгоритм цифровой подписи в сертификате RSA, DSA (Digital Signature Algorithm)
- Алгоритмы обмена ключами RSA, Diffie-Hellman Ephemeral
- Алгоритмы симметричного шифрования AES, ChaCha20-Poly1305 и др.
- Хэш-функции для вычислния MAC SHA-256, SHA-384
- Шифры AEAD (Authenticated Encryption with Associated Data).
  Обеспечивают одноврменно шифрование и MAC AES-GCM, ChaCha20-Poly1305 (RFC7539)

# Эволюция SSL/TLS

## Сравнение SSLv3, TLS 1.2 и TLS 1.3

- **SSLv3** — устарел и небезопасен, использовать нельзя.
- **TLS 1.2** — безопасная и широко используемая версия.
- **TLS 1.3** — современная версия, быстрее и безопаснее TLS 1.2.
- TLS 1.3 использует **ECDHE/DHE** и обязательно обеспечивает **Perfect Forward Secrecy (PFS)**.
- В TLS 1.3 убраны устаревшие и небезопасные алгоритмы.

## Отличия handshake, набора шифров и согласования ключей

- **SSLv3** — старый и небезопасный handshake, поддерживает устаревшие алгоритмы и не обеспечивает обязательный PFS.
- **TLS 1.2** — handshake сложнее и может использовать RSA или DH/ECDHE для обмена ключами. Набор шифров содержит алгоритмы обмена ключами, аутентификации, шифрования и хеширования.
- **TLS 1.3** — handshake упрощён и требует меньше обменов. Использует только современные механизмы **ECDHE/DHE**, обеспечивая PFS. Набор шифров значительно сокращён и содержит только современные AEAD-шифры.
- **Согласование ключей:** SSLv3/TLS 1.2 могут использовать разные механизмы (например, RSA или ECDHE), а TLS 1.3 использует **(EC)DHE** для получения общего секрета.

## Perfect Forward Secrecy и 0-RTT

## Perfect Forward Secrecy (PFS)

- **PFS** — свойство TLS, при котором компрометация закрытого ключа сервера не позволяет расшифровать ранее записанные соединения.
- Достигается использованием **временных ключей DHE/ECDHE** для каждого соединения.
- После завершения соединения временный ключ удаляется.

```text
Соединение 1 → временный ключ 1
Соединение 2 → временный ключ 2
Соединение 3 → временный ключ 3
```

## 0-RTT

- Механизм TLS 1.3 для быстрого повторного подключения.
- Клиент может отправить первые данные **одновременно с ClientHello**, не дожидаясь завершения handshake.
- Уменьшает задержку.
- Недостаток — возможность **Replay Attack** (повторной отправки 0-RTT данных).
- Поэтому 0-RTT не следует использовать для операций, которые нельзя безопасно повторить.

## Причины отказа от устаревших версий TLS

- **SSLv3** — небезопасен, подвержен известным атакам (например, **POODLE**).
- **TLS 1.0 и TLS 1.1** — устарели, имеют слабые криптографические алгоритмы и больше не рекомендуются к использованию.
- Устаревшие версии могут поддерживать **слабые шифры и алгоритмы обмена ключами**.
- Современные браузеры и серверы постепенно **прекратили их поддержку**.
- Использование старых версий увеличивает риск **перехвата, расшифровки или подмены данных**.
- Поэтому рекомендуется использовать **TLS 1.2 и TLS 1.3**, приоритетно TLS 1.3.

# OpenSSL

## Генерация приватного и публичного ключа

```bash
# Открытый ключ
openssl genrsa -out private.key 2048
```

```bash
# Закрытый ключ
openssl rsa -in private.key -pubout -out public.key
```

## Создание CSR и подписание сертификата

private key → CSR → сертификат, подписанный CA

Основной код можно найти в роли `openssl`

```bash
# Создаем private key

openssl genrsa -out server.key 2048
```

```bash
# Создаем CSR

openssl req -new \
  -key server.key \
  -out server.csr \
  -subj "/CN=example.com"
```

```bash
# Создаем private key CA

openssl genrsa -out ca.key 4096
```

```bash
# Создаём сертификат самого CA

openssl req -x509 -new \
  -key ca.key \
  -sha256 \
  -days 3650 \
  -out ca.crt \
  -subj "/CN=My Lab CA"
```

```bash
# CA подписывает CSR

openssl x509 -req \
  -in server.csr \
  -CA ca.crt \
  -CAkey ca.key \
  -CAcreateserial \
  -out server.crt \
  -days 365
```

## Инструмент openssl s_client

Консольный инструмент для ручной диагностики TLS-соединения.
Он позволяет посмотреть сертификат, цепочку доверия,
версию TLS, шифр и ошибки проверки.

```bash
openssl s_client -connect 192.168.64.100:443
```

Если сертификат подписан собственным СА
```bash
openssl s_client \
  -connect 192.168.64.100:443 \
  -CAfile ./certificates/ca.crt
```

# TLS Handshake

## TLS 1.2: Handshake

1. **ClientHello**
   - Клиент сообщает поддерживаемые версии TLS, cipher suites, random и другие параметры.

2. **ServerHello**
   - Сервер выбирает версию TLS и cipher suite и отправляет свой random.

3. **Certificate**
   - Сервер отправляет свой X.509 сертификат.
   - Клиент проверяет цепочку сертификатов, срок действия, имя сервера и подпись CA.

4. **Согласование ключей**
   - Клиент и сервер используют выбранный механизм, например **ECDHE**, чтобы получить общий секрет.
   - Private key сервера используется для аутентификации/подписи handshake, а не для шифрования всего трафика.

5. **Finished**
   - Стороны подтверждают, что handshake завершён и параметры согласованы.
   - После этого HTTPS-данные передаются с использованием симметричного ключа.

```text
Client                              Server
  │                                  │
  │────── ClientHello ──────────────→│
  │←───── ServerHello ───────────────│
  │←───── Certificate ───────────────│
  │                                  │
  │←───── ServerKeyExchange ─────────│
  │                                  │
  │────── ClientKeyExchange ────────→│
  │                                  │
  │────── Finished ─────────────────→│
  │←───── Finished ──────────────────│
  │                                  │
  │══════ Encrypted HTTPS data ══════│

```

## TLS 1.3: сокращённый Handshake

1. **ClientHello** — клиент отправляет поддерживаемые параметры и свой ECDHE public key.
2. **ServerHello** — сервер выбирает параметры и отправляет свой ECDHE public key.
3. **Certificate** — сервер отправляет сертификат, клиент проверяет его.
4. **CertificateVerify** — сервер доказывает владение private key.
5. **Finished** — стороны подтверждают успешное завершение handshake.
6. После этого передаются **зашифрованные HTTPS-данные**.

### Протокол оповещений

Протокол оповещений (Alert Protocol)
- Сообщения об ошибках в работе TLS

Фатальная ошибка - сессия TLS должна быть разорвана немедленно
- Ошибка MAC (bad_record_mac)
- Неизвестный удостоверяющий центр (unknown_ca)
- Ошибка расшифровки (decrypt_error)

Предупреждения - сессия может продолжать работать
- Срок действия сертификата завершен (certificate_expired)
- Сертификат отозван (certificate_revoked)
- Неизвестный формат сертификата (unsupported_certificate)

## Cipher Suites

### Что такое Cipher Suite

**Cipher Suite** — набор криптографических алгоритмов, используемых TLS для защиты соединения.

В TLS 1.2 название обычно содержит:

* **Key Exchange** — обмен ключами, например ECDHE;
* **Authentication** — аутентификация, например RSA/ECDSA;
* **Encryption** — шифрование, например AES-256;
* **Mode** — режим, например GCM;
* **Hash** — хеш-функция, например SHA-384.

Пример TLS 1.2:

```text
ECDHE-RSA-AES256-GCM-SHA384
```

### TLS 1.3

В TLS 1.3 cipher suite содержит в основном:

```text
TLS_AES_256_GCM_SHA384
```

Здесь:

* `AES-256` — шифрование;
* `GCM` — AEAD, обеспечивает шифрование и целостность;
* `SHA-384` — хеш-функция.

**Обмен ключами и аутентификация в TLS 1.3 согласуются отдельно.**

В нашем захвате:

```text
Cipher Suite: TLS_AES_256_GCM_SHA384
Key Share: X25519MLKEM768
Protocol: TLS 1.3
```

### Mozilla configurations

**Intermediate**

* хороший баланс безопасности и совместимости;
* подходит для большинства production-серверов;
* поддерживает современные клиенты и часть более старых.

**Modern**

* более строгая конфигурация;
* рассчитана на современные клиенты;
* меньше совместимость, но выше требования к безопасности.

### Рекомендация для production

* Использовать **TLS 1.3** как основной протокол.
* TLS 1.2 оставлять только при необходимости совместимости.
* Отключить SSLv3, TLS 1.0 и TLS 1.1.
* Использовать современные AEAD-наборы:

   * `TLS_AES_256_GCM_SHA384`
   * `TLS_AES_128_GCM_SHA256`
   * `TLS_CHACHA20_POLY1305_SHA256`
* В качестве базовой конфигурации обычно подходит **Mozilla Intermediate**.

## Известные атаки

## 7. Известные атаки

* **MITM** — злоумышленник перехватывает трафик между клиентом и сервером.
  **Защита:** проверка сертификатов, TLS, mTLS.

* **BEAST** — атака на **TLS 1.0 + CBC**.
  **Защита:** TLS 1.2/1.3, AEAD.

* **POODLE** — атака на **SSL 3.0 + CBC**.
  **Защита:** отключить SSL 3.0.

* **Heartbleed** — ошибка в OpenSSL, позволявшая читать данные из памяти.
  **Защита:** обновление OpenSSL, замена скомпрометированных ключей.

## Проверка цепочки доверия

## Проверка цепочки доверия

* **Цепочка доверия** строится от сертификата сервера через промежуточные **Intermediate CA** до доверенного **Root CA**:

```text
Server Certificate
       ↓
Intermediate CA
       ↓
Root CA (доверенный)
```

* Клиент проверяет подписи, срок действия, назначение сертификатов и доверие к Root CA.
* Если цепочка невалидна → появляется ошибка сертификата.

### CRL

**CRL (Certificate Revocation List)** — список отозванных сертификатов.

* CA публикует список отозванных сертификатов.
* Клиент проверяет, не был ли сертификат отозван.

### OCSP

**OCSP (Online Certificate Status Protocol)** — запрос к CA для проверки статуса конкретного сертификата.

```text
Client → OCSP Server: статус сертификата?
OCSP Server → Client: good / revoked / unknown
```

### OCSP Stapling

Сервер сам получает OCSP-ответ и отправляет его клиенту вместе с TLS handshake.

```text
Server → OCSP Server → получает статус
        ↓
Client ← OCSP response
```

В конфигурации nginx можно добавить

```text
ssl_stapling on; # включает OCSP Stapling.
ssl_stapling_verify on; # проверяет полученный OCSP-ответ.
```

Проверка OCSP Stapling

```bash
openssl s_client \
  -connect example.com:443 \
  -servername example.com \
  -status
```

Успешный статус: OCSP Response Status: successful + Cert Status: good
