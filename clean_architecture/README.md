# Clean Architecture

## Цель

Научиться строить приложения, в которых бизнес-правила не зависят от
фреймворков, базы данных и внешних интерфейсов: разделять код на слои,
соблюдать правило зависимостей и проверять архитектурные границы.

## План изучения

### 1. Основные понятия

- Разобрать цели архитектуры: снижение стоимости изменений, независимость
  от деталей, тестируемость.
- Изучить разницу между политикой (бизнес-правилами) и деталями
  (фреймворк, БД, UI, внешние сервисы).
- Сравнить Clean Architecture с Hexagonal Architecture (Ports and Adapters)
  и Onion Architecture.
- Понять, когда Clean Architecture избыточна для простых CRUD-приложений.

### 2. Слои и правило зависимостей

- Изучить слои: Entities, Use Cases, Interface Adapters, Frameworks and
  Drivers.
- Разобрать правило зависимостей: зависимости в коде направлены только
  внутрь, к бизнес-правилам.
- Научиться передавать данные через границы простыми структурами (DTO),
  а не моделями ORM.
- Разобрать типичные нарушения правила зависимостей и способы их поиска.

### 3. Принципы проектирования компонентов

- Повторить принципы SOLID на уровне классов.
- Изучить принципы связности компонентов: REP, CCP, CRP.
- Изучить принципы сочетаемости компонентов: ADP, SDP, SAP.
- Разобрать метрики стабильности и абстрактности компонентов.

### 4. Сущности и сценарии использования

- Выделять сущности как носителей критических бизнес-правил.
- Описывать Use Case (Interactor) как отдельный объект со входом и выходом.
- Определять Input Port и Output Port для сценария.
- Обрабатывать ошибки бизнес-логики без исключений фреймворка.

### 5. Адаптеры и границы

- Реализовать контроллеры, презентеры и шлюзы (Gateway) как адаптеры.
- Скрывать хранилище за интерфейсом Repository.
- Изолировать внешние API через адаптеры и Anticorruption Layer.
- Применять инверсию зависимостей для пересечения границ слоёв.

### 6. Детали и сборка приложения

- Рассматривать базу данных, веб-фреймворк и очереди как подключаемые
  детали.
- Собирать зависимости в одной точке (Composition Root, Main).
- Изучить «кричащую архитектуру» (Screaming Architecture): структура
  каталогов отражает предметную область, а не фреймворк.
- Разобрать варианты упаковки: по слоям, по фичам, по компонентам.

### 7. Применение в Rails-приложениях

- Разобрать конфликт Clean Architecture и подхода Active Record.
- Выносить бизнес-логику из моделей и контроллеров в Use Case-объекты.
- Изучить подходы и инструменты сообщества (например, dry-rb, Hanami)
  — обзорно.
- Постепенно внедрять границы в существующее приложение без переписывания.

### 8. Проверка архитектуры

- Покрывать Use Case юнит-тестами без базы данных и фреймворка.
- Автоматически проверять зависимости между слоями (например, packwerk).
- Фиксировать архитектурные решения в ADR.
- Проверять соблюдение границ на Code Review.

## Практический проект

Реализовать учебный сервис управления подписками по Clean Architecture:

- сущности «Подписка» и «Тариф» с бизнес-правилами продления и отмены;
- Use Case для оформления, продления и отмены подписки с явными входными и
  выходными портами;
- два адаптера доставки: HTTP API и CLI, использующие одни и те же Use Case;
- два адаптера хранения: in-memory для тестов и PostgreSQL для запуска;
- адаптер внешнего платёжного сервиса за интерфейсом шлюза;
- схема слоёв и направлений зависимостей, ADR с ключевыми решениями;
- автоматическая проверка запрещённых зависимостей между слоями в CI.

## Критерии завершения

- Слой бизнес-правил не импортирует код фреймворка, ORM и HTTP-клиентов.
- Замена хранилища или способа доставки не требует изменений в Use Case.
- Use Case покрыты юнит-тестами, которые выполняются без базы данных.
- Проверка зависимостей между слоями проходит в CI и падает при нарушении.
