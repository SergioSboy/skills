# DDD (Domain Driven Design)

# 1. Основные понятия DDD

## 1.1. Назначение и область применения

**DDD — Domain-Driven Design, предметно-ориентированное проектирование.** Это подход, при котором модель и код строятся вокруг бизнес-понятий, правил и процессов.

**Домен — предметная область**, в которой система решает задачи. Например, продажи, страхование или логистика.

Пример: оформление заказа — не просто запись в таблицу. Нужно учитывать резерв товара, оплату, отмену и допустимые переходы между состояниями.

```text
Черновик → Ожидает оплаты → Оплачен → Отправлен
```

Модель должна выражать правила: например, отправленный заказ нельзя отменить обычной операцией — требуется процесс возврата.

DDD особенно полезен, когда:

- много взаимосвязанных бизнес-правил;
- правила меняются и требуют обсуждения с экспертами;
- одинаковые термины имеют разный смысл в разных частях бизнеса;
- ошибка в понимании процесса приводит к неправильному поведению системы.

**DDD не требует микросервисов.** Его можно применять внутри модульного монолита.

## 1.2. Стратегическое и тактическое проектирование

| | Стратегическое | Тактическое |
|---|---|---|
| Главный вопрос | Как разделить предметную область и модели? | Как выразить правила внутри модели? |
| Масштаб | Части бизнеса и отношения между ними | Объекты, операции и ограничения |
| Основные понятия | Поддомены, bounded contexts, context map | Entity, Value Object, Aggregate, Repository, Domain Service |

**Стратегическое проектирование** помогает определить границы. Например, каталог, склад и доставка могут по-разному моделировать товар.

**Bounded context — ограниченный контекст:** область, внутри которой модель и термины имеют согласованный смысл.

**Тактическое проектирование** помогает реализовать модель внутри контекста:

- **Entity:** объект с устойчивой идентичностью, например заказ.
- **Value Object:** объект, определяемый значениями, например сумма с валютой.
- **Aggregate:** граница согласованного изменения связанных объектов, например заказ с его позициями.
- **Repository:** интерфейс получения и сохранения агрегатов.
- **Domain Service:** бизнес-операция, которая не относится естественным образом к одной сущности или объекту-значению.

**Не путай:** поддомен — часть бизнес-проблемы; bounded context — граница модели, с помощью которой её решают. Они не обязаны соответствовать один к одному.

## 1.3. Роль доменных экспертов

**Доменный эксперт — человек, который понимает реальные процессы, правила и исключения предметной области.** Это может быть сотрудник склада, специалист по платежам или страхованию.

Разработчики и эксперты совместно:

- разбирают реальные сценарии и исключения;
- уточняют смысл терминов;
- выявляют ограничения — что всегда должно оставаться истинным;
- проверяют модель на конкретных примерах.

Так формируется **Ubiquitous Language — единый язык** команды внутри контекста. Его используют в обсуждениях, документации, тестах и коде.

Пример: если бизнес различает «отмену заказа» и «возврат товара», в модели тоже должны быть разные операции.

**Модель уточняется постоянно.** Одного интервью и первоначальной схемы недостаточно: новые сценарии могут изменить понимание области.

## 1.4. Когда DDD избыточен

**CRUD — создание, чтение, обновление и удаление данных.** Если система преимущественно хранит записи и содержит мало бизнес-правил, сложная доменная модель может не окупиться.

Пример: небольшой справочник офисов с названием, адресом и телефоном. Простых проверок и обычной организации приложения может быть достаточно.

Признаки избыточного применения:

- появляются многочисленные абстракции без полезных правил;
- обычное изменение поля требует проходить через много слоёв;
- модель усложняет работу, но не помогает объяснять бизнес-поведение.

**Наличие CRUD-операций не делает систему простой.** Изменение статуса заказа может выглядеть как обновление поля, но требовать сложных проверок и действий.

DDD можно применять выборочно: общий язык и понятные границы полезны даже там, где не нужны все тактические паттерны.

**Запомнить:** DDD помогает управлять сложностью бизнеса. Глубина моделирования должна соответствовать сложности правил.

# 2. Единый язык (Ubiquitous Language)

## 2.1. Общий словарь с бизнесом

**Ubiquitous Language — общий язык разработчиков и доменных экспертов, основанный на модели предметной области.** Это не просто список терминов: язык описывает действия, состояния и правила.

Словарь формируют при разборе реальных сценариев. Для каждого понятия уточняют:

- что оно означает;
- чем отличается от похожих понятий;
- какие действия и ограничения с ним связаны;
- в каком контексте используется.

Пример:

| Термин | Значение |
|---|---|
| **Резерв товара** | Количество товара, закреплённое за заказом и недоступное для других заказов |
| **Отмена заказа** | Прекращение выполнения заказа по правилам его текущего состояния |
| **Возврат товара** | Отдельный процесс после передачи товара покупателю |

**Проверяйте определения примерами:** можно ли отменить уже отправленный заказ? Когда истекает резерв? Ответы помогают обнаружить неоднозначность.

## 2.2. Термины в коде, API, тестах и документации

**Один и тот же смысл должен выражаться согласованными названиями во всех частях системы.**

Если бизнес говорит «зарезервировать товар», это должно быть видно в реализации:

```ruby
inventory.reserve(product_id, quantity)
```

Название вроде `update_count` скрывает бизнес-смысл: непонятно, идёт речь о резерве, продаже или исправлении остатков.

Пример согласованного использования:

| Где | Как выражено понятие |
|---|---|
| Код | `reserve` |
| API | Операция создания резерва |
| Событие | `StockReserved` |
| Тест | «Резерв уменьшает доступное количество товара» |
| Документация | Правила резервирования |

Если код написан на английском, а обсуждения идут на русском, фиксируют однозначное соответствие: **«резерв» → `reservation`**.

**Важно сохранять не только название, но и смысл.** Метод `cancel_order` не должен незаметно выполнять процесс возврата товара.

## 2.3. Омонимы и разные контексты

**Омоним — одинаковое название с разным смыслом.** В DDD это часто сигнал, что понятия относятся к разным bounded contexts.

Пример термина «клиент»:

| Контекст | Что означает «клиент» |
|---|---|
| Продажи | Покупатель с историей заказов |
| Биллинг | Плательщик с реквизитами и обязательствами |
| Поддержка | Обратившийся пользователь с обращениями |

Эти модели могут относиться к одному человеку, но содержать разные данные и правила.

**Не нужно принудительно объединять их в одну универсальную модель.** Значение термина должно быть однозначным внутри своего контекста.

На границе контекстов явно описывают соответствие: например, как `Customer` в продажах связан с `Payer` в биллинге. При необходимости используют слой перевода моделей.

Также выявляют **синонимы**: если «покупатель», «заказчик» и «клиент» обозначают одно понятие внутри контекста, выбирают согласованный термин.

## 2.4. Актуальность словаря

**Словарь развивается вместе с пониманием бизнеса.** Изменение требований может потребовать изменения определения, модели и названий.

Практический процесс:

1. Обнаружить новое понятие или изменение смысла.
2. Обсудить его с доменным экспертом.
3. Обновить определение и примеры.
4. Привести код, тесты и документацию в соответствие.
5. Проверить влияние на внешние контракты.

Например, бизнес разделил «отмену оплаты» на отмену незавершённой операции и возврат уже списанных средств. В модели должны появиться отдельные понятия и правила.

Словарь удобно хранить рядом с документацией проекта и обновлять при тех же изменениях, что и код. Для термина полезно указывать контекст, определение, примеры и соответствующее название в коде.

**Изменение языка не оправдывает внезапную поломку API:** публичные контракты обновляют с учётом совместимости.

**Запомнить:** единый язык работает, когда им ежедневно пользуются. Словарь, обсуждения и код должны отражать одну модель внутри контекста.

# 3. Домены и поддомены

## 3.1. Core, supporting и generic

**Домен — предметная область бизнеса. Поддомен — отдельная часть этой области со своими задачами и правилами.**

В DDD поддомены классифицируют по их роли для конкретного бизнеса:

| Тип | Значение | Пример для интернет-магазина |
|---|---|---|
| **Core — ключевой** | Создаёт конкурентное преимущество | Уникальный подбор товаров, если именно он отличает магазин |
| **Supporting — поддерживающий** | Необходим бизнесу, но не делает его уникальным; содержит специфические правила | Внутренний процесс согласования ассортимента |
| **Generic — типовой** | Решает распространённую задачу, для которой существуют готовые решения | Стандартная аутентификация или отправка писем |

**Тип определяется контекстом бизнеса.** Доставка может быть поддерживающей для магазина и ключевой для логистической компании.

Поддомен — часть бизнес-задачи, а не обязательно отдельный модуль или сервис.

## 3.2. Где находится конкурентное преимущество

Чтобы найти core domain, спрашивают:

- За что клиенты выбирают именно этот бизнес?
- Какие возможности трудно повторить конкурентам?
- Какие правила и знания уникальны для компании?
- Улучшение какой части сильнее всего влияет на ценность продукта?

Пример: для обычного магазина рекомендации могут быть дополнительной функцией. Для сервиса персонального подбора одежды качество рекомендаций может составлять основу продукта.

**Core не равен «самая сложная часть» или «самая критичная часть».** Аутентификация важна для безопасности, но стандартная аутентификация обычно не отличает бизнес от конкурентов.

Классификация может меняться: типовая функция становится ключевой, если компания строит вокруг неё новую стратегию.

## 3.3. Разрабатывать или использовать готовое

| Тип поддомена | Обычный ориентир |
|---|---|
| **Core** | Разрабатывать и контролировать ключевую модель, правила и знания |
| **Supporting** | Выбирать между собственной реализацией и адаптацией готового решения |
| **Generic** | Предпочитать готовые продукты, библиотеки или внешние сервисы |

Это ориентиры, а не обязательные правила.

При выборе оценивают:

- соответствие бизнес-правилам;
- полную стоимость разработки, интеграции и поддержки;
- ограничения по безопасности и размещению данных;
- возможность менять решение и переносить данные;
- зависимость от поставщика;
- стоимость адаптации при изменении требований.

**Собственная разработка core не означает разработку всей инфраструктуры с нуля.** Уникальный алгоритм можно реализовать самостоятельно, используя готовую БД, брокер и библиотеки.

Если готовый продукт требует постоянных обходных решений, его адаптация может оказаться дороже собственной реализации.

## 3.4. Распределение усилий команды

**Больше усилий по моделированию и развитию направляют туда, где они создают больше бизнес-ценности.**

- **Core:** тесная работа с экспертами, глубокая модель, проверка гипотез и постоянное развитие.
- **Supporting:** достаточная модель для специфических правил; прагматичная реализация без лишних абстракций.
- **Generic:** выбор, интеграция и надёжная эксплуатация готовых решений вместо повторного изобретения.

При этом качество безопасности, данных и надёжности определяется рисками, а не только типом поддомена. Типовой компонент тоже может требовать серьёзной защиты и контроля.

Классификацию полезно периодически пересматривать вместе с бизнесом и учитывать при планировании работ.

**Запомнить:** core отличает бизнес, supporting помогает ему работать, generic решает типовые задачи. Собственные усилия особенно ценны там, где создаётся конкурентное преимущество.

# 4. Bounded Context

## 4.1. Граница модели и языка

**Bounded Context — ограниченный контекст, внутри которого модель, термины и бизнес-правила имеют согласованный смысл.**

Один объект реального мира может иметь разные модели:

| Контекст | Что означает «товар» |
|---|---|
| Каталог | Описание, характеристики и фотографии |
| Склад | Остаток, резерв и место хранения |
| Доставка | Вес, габариты и ограничения перевозки |

Не нужно объединять всё в универсальный `Product`. Контексты могут связывать свои модели через идентификатор товара, сохраняя разные данные и правила.

Границу ищут там, где меняются:

- значение терминов;
- бизнес-правила и ответственность;
- процессы и потребности пользователей;
- причины изменения модели.

**Поддомен описывает часть бизнес-проблемы, bounded context — границу модели решения.** Их соответствие не обязательно один к одному.

## 4.2. Связь с командами и сервисами

**Bounded context — логическая граница модели. Сервис — граница выполнения и развёртывания.**

Контекст можно реализовать:

- модулем внутри монолита;
- отдельным сервисом;
- несколькими сервисами, если разделение оправдано.

Для каждого контекста нужна понятная ответственность за модель, язык и контракты. Хорошо, когда команда может развивать его без постоянного согласования внутренних изменений с другими командами.

Одна команда может владеть несколькими контекстами. Если один контекст поддерживают несколько команд, им нужно согласованно управлять общей моделью.

**Правило «один контекст = один сервис = одна команда» не обязательно.** Но случайное смешение моделей в общем коде или таблицах разрушает границы.

## 4.3. Context Map и паттерны взаимодействия

**Context Map — карта контекстов и отношений между ними.** Она показывает не только передачу данных, но и влияние команд и моделей друг на друга.

**Upstream** задаёт модель или контракт, от которых зависит **downstream**. Это направление влияния, а не обязательно направление сетевого запроса.

| Паттерн | Смысл |
|---|---|
| **Shared Kernel** | Контексты совместно используют небольшую часть модели и согласуют её изменения |
| **Customer/Supplier** | Upstream выступает поставщиком и учитывает потребности downstream-заказчика |
| **Conformist** | Downstream принимает модель upstream без собственного слоя перевода и существенного влияния на неё |
| **Anticorruption Layer — ACL** | Downstream переводит внешнюю модель в собственную, защищая её от чужих понятий |
| **Open Host Service — OHS** | Контекст предоставляет устойчивый, понятный интерфейс интеграции для множества потребителей |
| **Published Language — PL** | Участники используют явно описанный язык обмена: значения, форматы и схемы сообщений |

Важные различия:

- **Shared Kernel** создаёт связанность, поэтому общую модель делают небольшой. Общая библиотека технических утилит сама по себе не является Shared Kernel.
- **Customer/Supplier** — отношения сотрудничества, а не просто наличие вызова API.
- **ACL** переводит смысл модели, а не только переименовывает поля.
- **OHS и PL** часто используются вместе: открытый интерфейс плюс документированный язык обмена.

Паттерны могут сочетаться: сервис предоставляет OHS с PL, а потребитель использует ACL для перевода в свою модель.

## 4.4. Карта контекстов интернет-магазина

Возьмём учебную область **интернет-магазина**:

| Контекст | Ответственность |
|---|---|
| **Каталог** | Описание и характеристики товаров |
| **Заказы** | Состав заказа, цена на момент покупки и жизненный цикл |
| **Склад** | Остатки и резервы |
| **Платежи** | Оплата, возвраты и связь с платёжным провайдером |
| **Доставка** | Отправления и процесс доставки |

Карта — стрелки показывают влияние upstream на downstream:

```text
Каталог ── OHS + PL ──→ Заказы
Склад ── Customer/Supplier ──→ Заказы
Платежи ── Customer/Supplier ──→ Заказы
Заказы ── OHS + PL ──→ Доставка

Внешний платёжный провайдер ──→ [ACL] ──→ Платежи
```

**Как читать карту:**

- Каталог публикует контракт данных о товарах. Заказы сохраняют необходимые сведения как снимок покупки.
- Команды склада и платежей согласуют свои контракты с потребностями заказов.
- Доставка получает данные подтверждённого заказа и строит собственную модель отправления.
- Платежи переводят статусы внешнего провайдера в собственные понятия через ACL.

Это один возможный вариант: отношения зависят от реального устройства бизнеса и команд. Использовать все паттерны на одной карте не требуется.

**Запомнить:** bounded context защищает смысл модели, а Context Map делает явными зависимости между моделями и правила сотрудничества команд.

# 5. Event Storming

## 5.1. Big Picture Event Storming

**Event Storming — совместное исследование предметной области через события бизнес-процесса.** Разработчики и доменные эксперты строят общую картину на доске, обсуждая реальные сценарии.

**Big Picture** помогает увидеть процесс целиком: от начала до результата, включая альтернативы и ошибки. Его цель — понять бизнес, а не сразу спроектировать классы или сервисы.

Пример оформления заказа:

```text
Заказ оформлен → Товар зарезервирован → Оплата получена
                                        ↓
                      Заказ передан в доставку → Заказ доставлен
```

Как провести:

1. Собрать людей, которые знают разные части процесса.
2. Выписать важные события и расположить их в примерном временном порядке.
3. Добавить альтернативные пути: отказ оплаты, отсутствие товара, отмену.
4. Обсудить пробелы, разные трактовки и границы ответственности.
5. Зафиксировать вопросы, которые требуют дальнейшего исследования.

Параллельные действия и ветвления не нужно искусственно превращать в одну линейную цепочку.

## 5.2. События, команды, акторы и политики

| Элемент | Значение | Пример |
|---|---|---|
| **Доменное событие** | Значимый для бизнеса факт, который уже произошёл | «Товар зарезервирован» |
| **Команда** | Намерение выполнить действие; может быть отклонено | «Зарезервировать товар» |
| **Актор** | Человек или роль, инициирующие действие | Покупатель, сотрудник склада |
| **Политика** | Правило реакции на событие | «После получения оплаты начать подготовку к отправке» |
| **Внешняя система** | Участник вне рассматриваемых границ | Платёжный провайдер |

Пример связи:

```text
Покупатель
    ↓
Оформить заказ — команда
    ↓
Заказ оформлен — событие
    ↓
«Когда заказ оформлен, нужно зарезервировать товар» — политика
    ↓
Зарезервировать товар — следующая команда
```

**Команда не гарантирует событие:** резервирование может быть отклонено из-за отсутствия товара.

События называют в прошедшем времени и на языке бизнеса. «Оплата получена» полезнее для модели процесса, чем «Строка обновлена в БД».

В Big Picture основное внимание уделяют событиям. Команды, политики и другие детали добавляют по мере необходимости, особенно при дальнейшем разборе отдельных сценариев.

## 5.3. Горячие точки и противоречия

**Hot spot — отмеченное место, где есть вопрос, конфликт или неопределённость.** Его фиксируют на доске, чтобы не потерять и не остановить всё обсуждение.

Примеры:

- Когда заказ считается оформленным: до оплаты или после?
- Можно ли оплатить заказ без подтверждённого резерва?
- Что делать, если оплата пришла после отмены?
- Кто отвечает за освобождение просроченного резерва?

Разные ответы могут указывать на:

- неоднозначные термины;
- исключения, о которых знают не все;
- неявные бизнес-правила;
- разные модели в разных контекстах;
- реальные проблемы существующего процесса.

**Не нужно сразу выбирать удобный технический ответ.** Сначала выясняют фактическое или желаемое правило вместе с бизнесом. Для нерешённых вопросов назначают ответственного за уточнение.

## 5.4. От процесса к контекстам и агрегатам

**Кандидатов в bounded contexts** ищут по группам связанных событий, общему языку, правилам и ответственности.

Пример:

| Группа событий | Возможный контекст |
|---|---|
| Заказ оформлен, подтверждён, отменён | Заказы |
| Товар зарезервирован, резерв освобождён | Склад |
| Оплата получена, возврат выполнен | Платежи |
| Отправление создано, доставлено | Доставка |

Это гипотезы границ, которые нужно проверить на других сценариях.

**Кандидатов в агрегаты** определяют при более детальном разборе команд и ограничений:

- какое состояние нужно проверить перед выполнением команды;
- какие правила должны соблюдаться всегда;
- какие данные должны изменяться атомарно.

Пример: заказ и его позиции могут составлять агрегат, если изменение состава и пересчёт суммы должны согласованно выполняться вместе.

**Агрегат не равен цепочке событий или всему процессу.** Оформление, резервирование и оплата обычно затрагивают несколько агрегатов и координируются отдельно.

Результат Big Picture — общая картина, словарь, вопросы и гипотезы границ. Для проектирования агрегатов обычно требуется дальнейший разбор конкретных сценариев.

**Запомнить:** Event Storming делает знания и разногласия видимыми. Модель появляется из обсуждения бизнес-правил, а не из механического переноса стикеров в код. 

# 6. Тактические паттерны

## 6.1. Entity и Value Object

**Entity — сущность с устойчивой идентичностью.** Её свойства могут изменяться, но она остаётся тем же объектом предметной области.

Пример: заказ с идентификатором `42` остаётся тем же заказом после изменения статуса.

**Value Object — объект-значение, определяемый своими значениями, а не идентификатором.**

Пример: `Money(100, "RUB")`. Два объекта с одинаковой суммой и валютой считаются равными по значению.

| | Entity | Value Object |
|---|---|---|
| Главное | Идентичность | Значения |
| Равенство | По идентичности | По составляющим значениям |
| Изменение | Состояние может меняться | Обычно создают новое значение вместо изменения старого |
| Примеры | Заказ, платёж | Деньги, период дат, адрес |

Value Object объединяет данные и правила: например, запрещает складывать суммы в разных валютах без явного преобразования.

**Выбор зависит от модели:** адрес доставки может быть объектом-значением, а адресная запись с собственной историей и идентификатором — сущностью.

## 6.2. Aggregate и Aggregate Root

**Aggregate — группа сущностей и объектов-значений, образующая границу согласованного изменения.**

**Aggregate Root — корневая сущность, через которую выполняются изменения агрегата.** Она защищает его инварианты — правила, которые должны сохраняться.

```text
Order — Aggregate Root
├── OrderItem
├── OrderItem
└── Money — итоговая сумма
```

Например, правило «подтверждённый заказ нельзя редактировать» проверяется при изменении позиций через заказ:

```ruby
order.add_item(product_id, quantity, price)
order.confirm
```

Внешний код не должен обходить корень и произвольно менять внутренние позиции.

Основные ориентиры:

- агрегат делают настолько небольшим, насколько позволяют инварианты;
- изменения внутри него сохраняют одной транзакцией;
- другие агрегаты обычно связывают через идентификаторы;
- согласование между агрегатами часто выполняют через события и отдельные процессы.

**Агрегат не равен таблице, сервису или всем связанным данным.** Заказ, складской резерв и платёж обычно имеют разные границы согласованности.

## 6.3. Domain Service, Repository и Factory

| Паттерн | Назначение | Пример |
|---|---|---|
| **Domain Service** | Выражает бизнес-операцию, которая не принадлежит естественным образом одной Entity или Value Object | Выбор подходящего тарифа доставки по бизнес-правилам |
| **Repository** | Предоставляет получение и сохранение агрегатов, скрывая детали хранения | Найти заказ по идентификатору |
| **Factory** | Создаёт сложный объект или агрегат сразу в допустимом состоянии | Создать заказ из согласованного предложения |

**Domain Service не должен забирать всю логику у сущностей.** Если правило естественно принадлежит заказу, оно должно оставаться в заказе.

Различай:

- **Domain Service:** принимает бизнес-решения.
- **Application Service:** координирует сценарий — загрузить агрегат, вызвать его поведение, сохранить результат.

Пример прикладного сценария:

```ruby
order = orders.find(order_id)
order.confirm
orders.save(order)
```

**Repository обычно организуют вокруг корней агрегатов**, а не создают отдельный репозиторий для каждой внутренней сущности.

**Factory нужна при сложном создании.** Для простого объекта достаточно конструктора. Фабрика помогает обеспечить начальную корректность, но дальнейшие изменения контролирует сам агрегат.

## 6.4. Domain Events и публикация

**Domain Event — значимый факт предметной области, который уже произошёл.**

Примеры:

```text
OrderConfirmed — заказ подтверждён
PaymentReceived — оплата получена
ReservationExpired — резерв истёк
```

Агрегат может зарегистрировать событие после успешного изменения состояния. Обработчики используют его для реакции других частей системы.

**Не публикуй внешний факт об изменении, которое ещё может откатиться.** Иначе потребители получат сообщение о несуществующем результате.

Для надёжной внешней публикации используют **Transactional Outbox**:

```text
Одна транзакция:
изменение агрегата + запись события в outbox
                         ↓
               публикация после фиксации
```

Доставка может повториться, поэтому обработчики должны быть идемпотентными. Если порядок важен, полезно передавать идентификатор агрегата и его версию.

Различай:

- **Domain Event:** выражает факт внутри доменной модели.
- **Integration Event:** стабильный контракт для других контекстов или систем.

Внутреннее событие можно преобразовать в интеграционное, передавая только необходимые данные и сохраняя независимость внутренней модели.

**Запомнить:** Entity хранит идентичность, Value Object — значение, Aggregate защищает инварианты. Остальные паттерны помогают создавать, сохранять и связывать модель, не размывая её ответственность.

# 7. Проектирование агрегатов

## 7.1. Инварианты агрегата

**Инвариант — бизнес-правило, которое должно сохраняться после каждой завершённой операции.** Границу агрегата выбирают вокруг данных, необходимых для атомарного соблюдения этих правил.

Пример для заказа:

- количество каждой позиции положительное;
- подтверждение возможно только при наличии позиций;
- состав подтверждённого заказа нельзя менять;
- итоговая сумма соответствует позициям и правилам расчёта.

**Aggregate Root контролирует изменения**, чтобы внешний код не обходил проверки:

```ruby
order.add_item(product_id, quantity, price)
order.confirm
```

Вместо произвольного присваивания `order.status = "confirmed"` вызывают операцию, которая проверяет допустимость перехода.

Если правило должно учитывать актуальное состояние нескольких объектов, выясни: нужна ли немедленная атомарность или допустимо согласование отдельным процессом? Ответ влияет на границу агрегата.

## 7.2. Небольшие агрегаты и ссылки по идентификатору

**Агрегат содержит только то, что необходимо для его инвариантов.** Связь между объектами сама по себе не требует включать их в один агрегат.

```text
Order
├── OrderItem
│   ├── product_id
│   ├── quantity
│   └── price_at_purchase
└── customer_id
```

Заказ хранит идентификаторы товара и покупателя, а не включает целиком их модели. Цена на момент покупки может быть собственным историческим значением заказа.

Преимущества небольших агрегатов:

- меньше данных нужно загружать и сохранять;
- ниже конкуренция за одну границу изменения;
- проще понимать ответственность и проверять правила.

**Слишком маленький агрегат тоже может быть ошибкой:** если обязательный инвариант постоянно требует согласованного изменения нескольких агрегатов, стоит пересмотреть границу.

Ссылка по идентификатору не означает обязательный сетевой вызов. Агрегаты могут находиться в одном приложении и одной БД.

## 7.3. Один агрегат в одной транзакции

**Обычный ориентир DDD: одна транзакция изменяет один агрегат.** Все изменения его внутреннего состояния фиксируются вместе.

```text
Добавить позицию + пересчитать сумму → COMMIT
Ошибка                              → ROLLBACK
```

Это позволяет агрегату самостоятельно защищать свои правила и уменьшает связанность с другими агрегатами.

При одновременных изменениях нужна защита от потерянных обновлений. Например, **оптимистическая блокировка** проверяет версию:

```text
Два запроса загрузили заказ версии 5.
Первый сохранил версию 6.
Второму отказано: версия 5 уже устарела.
```

После конфликта состояние перечитывают и повторно проверяют бизнес-правила.

**Это принцип проектирования, а не абсолютный запрет.** Если несколько агрегатов постоянно требуют общей атомарной транзакции, нужно проверить модель. В отдельных случаях общая транзакция может быть осознанным решением.

## 7.4. Согласованность через доменные события

Когда немедленная атомарность не обязательна, агрегаты согласуют через события:

```text
Заказ оформлен
       ↓
Складской агрегат резервирует товар
       ↓
Товар зарезервирован → Заказ подтверждается
Товара недостаточно → Заказ отклоняется или ждёт решения
```

Каждый шаг меняет свой агрегат в собственной транзакции. Между шагами возможны промежуточные состояния, например «Ожидает резервирования».

Для надёжной обработки нужны:

- сохранение события вместе с изменением — например, через Outbox;
- идемпотентность обработчиков;
- учёт порядка или версий, если они важны;
- повторы и контроль зависших процессов;
- компенсации, если предыдущие действия нужно отменить.

Многошаговый процесс может координировать Saga или process manager.

**Событие само по себе не гарантирует согласованность:** её обеспечивают доставка, обработка и бизнес-правила восстановления. Если временное нарушение правила недопустимо, асинхронная схема без дополнительной координации не подходит.

**Запомнить:** внутри агрегата защищают инварианты атомарно; между агрегатами явно проектируют согласование, промежуточные состояния и обработку ошибок.

# 8. DDD в коде

## 8.1. Изоляция доменной модели

**Доменная модель выражает бизнес-правила и не должна зависеть от HTTP, брокера сообщений, конкретной БД или внешнего API.**

В Hexagonal Architecture приложение взаимодействует с внешним миром через **порты — интерфейсы**, которые реализуют **адаптеры**. В Clean Architecture зависимости направлены к внутренним слоям с бизнес-правилами.

| Часть | Ответственность |
|---|---|
| **Домен** | Сущности, объекты-значения, агрегаты и бизнес-правила |
| **Прикладной слой** | Координация сценария: загрузить, выполнить операцию, сохранить |
| **Инфраструктура** | БД, HTTP-клиенты, брокеры и реализации хранилищ |
| **Входные адаптеры** | Контроллеры, обработчики сообщений, команды CLI |

```text
Контроллер → Прикладной сценарий → Домен
                    ↓
           Порт хранилища заказов
                    ↑
             Адаптер конкретной БД
```

Домену важно понятие «сохранить заказ», а не детали SQL или ORM. Интерфейс хранилища определяют внутренние слои, а инфраструктура подстраивается под него.

**Цель — возможность понимать и проверять бизнес-правила без запуска всей инфраструктуры.** Не обязательно создавать отдельный интерфейс для каждого класса.

## 8.2. Богатая и анемичная модель

**Анемичная модель** хранит данные, но почти не содержит поведения. Все правила находятся во внешних сервисах:

```ruby
# Любой код может обойти правила подтверждения
order.status = :confirmed
```

В **богатой доменной модели** объект сам контролирует допустимые изменения:

```ruby
class Order
  def confirm
    raise InvalidState unless @status == :draft
    raise EmptyOrder if @items.empty?

    @status = :confirmed
  end
end
```

Прикладной сервис координирует сценарий:

```ruby
order = orders.find(order_id)
order.confirm
orders.save(order)
```

**Бизнес-правило находится в заказе, а загрузка и сохранение — снаружи.**

Не всю логику нужно помещать в сущности. Если бизнес-операция не принадлежит естественным образом одной сущности или объекту-значению, подходит Domain Service.

Для простого CRUD приложения простая модель данных может быть достаточной. Богатая модель полезна там, где есть существенные правила и переходы состояния.

## 8.3. Модульные тесты инвариантов

**Тестируют наблюдаемое бизнес-поведение**, а не внутреннее устройство агрегата.

Пример на Ruby с RSpec:

```ruby
it "не позволяет подтвердить пустой заказ" do
  order = Order.new

  expect { order.confirm }
    .to raise_error(EmptyOrder)
end
```

Основные группы проверок:

- допустимая операция успешно меняет состояние;
- нарушение инварианта отклоняется;
- недопустимый переход состояния запрещён;
- после отказа агрегат остаётся в корректном состоянии;
- граничные значения обрабатываются правильно.

Например, после подтверждения заказа нельзя добавить позицию, а нулевое количество товара отклоняется.

**Доменные тесты обычно выполняются без БД и сети.** Реальную работу репозиториев, транзакций и внешних адаптеров проверяют отдельно интеграционными тестами.

Часы, генерацию идентификаторов и другие источники недетерминированности передают явно, если они влияют на правила.

## 8.4. Anticorruption Layer для внешней системы

**ACL — слой, который переводит понятия внешней системы в собственную модель.** Он защищает домен от чужих форматов, статусов и правил.

Например, платёжный провайдер возвращает:

```json
{
  "result_code": "00",
  "transaction_ref": "ext-123"
}
```

ACL преобразует ответ в понятный приложению результат:

```ruby
PaymentResult.new(
  status: :succeeded,
  external_id: "ext-123"
)
```

```text
Собственная модель
        ↕
Порт платежей → ACL / адаптер → Внешний провайдер
```

В ACL находятся:

- преобразование данных и статусов;
- сопоставление внешних и внутренних идентификаторов;
- перевод ошибок;
- обработка неподдерживаемых ответов.

**Перевод должен сохранять смысл.** Если внешний статус означает «принято в обработку», нельзя превращать его в «оплата завершена». Неизвестный результат или таймаут также не следует автоматически считать отказом платежа.

ACL проверяют на примерах внешних ответов. При смене провайдера меняется интеграционный слой, а внутренние бизнес-понятия остаются устойчивыми.

**Запомнить:** домен защищает правила, прикладной слой координирует действия, инфраструктура выполняет техническую работу, ACL переводит внешний мир в язык модели.
