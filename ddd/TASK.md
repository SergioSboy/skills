# DDD (Domain Driven Design)

## Цель

Научиться моделировать предметную область с помощью DDD: выделять домены,
bounded contexts и агрегаты, а также формировать общий словарь с бизнесом.

## План изучения

### 1. Основные понятия

- Разобрать назначение DDD и область его применения.
- Отличать стратегическое проектирование от тактического.
- Понять роль доменных экспертов в проектировании.
- Изучить, когда DDD избыточен для простых CRUD-систем.

### 2. Единый язык (Ubiquitous Language)

- Формировать общий словарь терминов вместе с бизнесом.
- Использовать термины словаря в коде, API, тестах и документации.
- Выявлять омонимы: один термин с разным смыслом в разных контекстах.
- Поддерживать словарь в актуальном состоянии при изменении требований.

### 3. Домены и поддомены

- Выделить core, supporting и generic поддомены.
- Определить, где сосредоточено конкурентное преимущество бизнеса.
- Решать, какие поддомены разрабатывать самостоятельно, а какие покупать
  или брать готовыми.
- Распределить усилия команды в соответствии с типом поддомена.

### 4. Bounded Context

- Определить границы, внутри которых модель и термины однозначны.
- Разобрать связь bounded context с командами и сервисами.
- Изучить Context Map и паттерны взаимодействия: Shared Kernel,
  Customer/Supplier, Conformist, Anticorruption Layer, Open Host Service,
  Published Language.
- Построить карту контекстов для учебной предметной области.

### 5. Event Storming

- Провести Big Picture Event Storming по ключевому бизнес-процессу.
- Выявить доменные события, команды, акторов, политики и внешние системы.
- Найти горячие точки и противоречия в понимании процесса.
- Использовать результаты для выделения bounded contexts и агрегатов.

### 6. Тактические паттерны

- Разобрать Entity и Value Object.
- Изучить Aggregate и Aggregate Root.
- Разобрать Domain Service, Repository и Factory.
- Изучить Domain Events и их публикацию.

### 7. Проектирование агрегатов

- Определять инварианты, которые агрегат защищает.
- Проектировать небольшие агрегаты и ссылаться на другие по идентификатору.
- Изменять один агрегат в одной транзакции.
- Обеспечивать согласованность между агрегатами через доменные события.

### 8. DDD в коде

- Изолировать доменную модель от инфраструктуры (Hexagonal / Clean
  Architecture).
- Избегать анемичной модели, где вся логика вынесена в сервисы.
- Покрыть инварианты агрегатов модульными тестами.
- Реализовать Anticorruption Layer для интеграции с внешней системой.

## Практический проект

Описать предметную область системы заказов по DDD:

- общий словарь терминов (заказ, позиция, резерв, оплата, отгрузка и т. п.)
  с определениями для каждого контекста;
- классификация поддоменов на core, supporting и generic;
- результаты Event Storming по процессу оформления и выполнения заказа;
- bounded contexts и Context Map с типами отношений между ними;
- агрегаты с корнями, инвариантами и доменными событиями;
- пример реализации агрегата «Заказ» с тестами инвариантов.

## Критерии завершения

- Термины словаря однозначны внутри каждого bounded context и используются
  в коде.
- Поддомены классифицированы, и выбор core-поддомена обоснован.
- Context Map отражает все интеграции и типы отношений между контекстами.
- Каждый агрегат защищает явно описанные инварианты и изменяется в одной
  транзакции.
