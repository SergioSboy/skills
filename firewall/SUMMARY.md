# Сетевой стек Linux

## TCP/IP

Модель OSI полезна как концептуальная модель, но Linux работает не с абстрактными «уровнями OSI»,
а с конкретными сетевыми протоколами и структурами ядра.

| Уровень     | Примеры             | Что важно для firewall                    |
| ----------- | ------------------- | ----------------------------------------- |
| Application | HTTP, DNS, SSH      | порт/протокол, иногда содержимое          |
| Transport   | TCP, UDP, ICMP      | source/destination port, connection state |
| Internet    | IPv4, IPv6          | source/destination IP, routing            |
| Link        | Ethernet, VLAN, ARP | interface, MAC, VLAN                      |


## Путь пакета через Linux

Пакет приходит на Linux через интерфейс, например eth0, дальше Linux определяет куда отправить этот пакет для
этого используется routing decision.

INPUT

Пакет предназначен самому Linux-хосту.

FORWARD

Пакет проходит через Linux, а не предназначен ему.

OUTPUT

Пакет создаётся самим Linux.

INPUT/FORWARD/OUTPUT определяются не тем, какой интерфейс используется, а направлением обработки пакета относительно самого Linux-хоста.

## Stateful filtering

Stateless firewall рассматривает каждый пакет независимо.
Stateful firewall дополнительно учитывает состояние соединения.

## Conntrack

Она хранит состояние потоков/соединений.

Firewall получает возможность использовать состояния:

```
NEW
ESTABLISHED
RELATED
INVALID
```

NEW

Пакет относится к соединению, которое firewall ещё не видел как установленное.

ESTABLISHED

Соединение уже существует.

RELATED

Есть новое соединение, связанное с уже существующим соединением.

INVALID

Пакет не удаётся корректно сопоставить с ожидаемым состоянием conntrack.


## Почему асимметричная маршрутизация важна

Если stateful firewall находится только на Router A, он может увидеть:

SYN

но не увидеть ответ:

SYN/ACK

В результате conntrack и firewall state могут не соответствовать реальному состоянию соединения.


## Таблицы, цепочки, правила и policy

Теперь можно перейти к концепции firewall configuration.

Rule

Конкретное условие и действие:

```
if source = 10.10.10.0/24
and destination port = 443
then ACCEPT
```

Chain

Набор правил, обрабатываемых последовательно.

```
INPUT
 ├── allow loopback
 ├── allow established
 ├── allow SSH
 ├── allow HTTPS
 └── drop
```

Table

Логическая область/набор правил для определённого типа обработки.

В iptables таблицы исторически группируют функциональность:

```
filter
nat
mangle
...
```

В nftables модель несколько другая, и к ней мы подробно придём в пункте 3.


### Default policy

Что делать, если ни одно правило явно не сработало.

Концептуально:

```
default ACCEPT
```

```
default DROP
```

Для production firewall это фундаментальный architectural decision.


## Почему порядок правил критичен

```
1. DROP all
2. ACCEPT TCP/443
```

Поэтому firewall configuration нужно читать не как набор независимых строк,
а как программу, которая обрабатывает поток пакетов.


Firewall ruleset — это маленькая программа принятия решений над сетевыми пакетами.

Если система использует модель first match, правило №2 никогда не будет достигнуто.


## Практический production-like пример

```
Internet → Web:443       allowed
Web → API:8080           allowed
API → DB:5432            allowed
Internet → DB:5432       denied
Internet → API:8080      denied
```

Где физически/логически находится firewall и какие из этих потоков проходят через INPUT, а какие через FORWARD?

Здесь архитектор сначала должен построить traffic matrix, а не сразу писать firewall rules.

Один и тот же порт 443 может использовать совершенно разные firewall paths в зависимости от архитектуры.


# iptables

## Основная идея

iptables — это интерфейс управления Linux firewall на базе netfilter.

Важно разделять:

- netfilter — инфраструктура firewall hooks внутри Linux kernel;
- iptables — исторический userspace-инструмент для управления правилами netfilter;
- conntrack — механизм отслеживания connection state;
- NAT — отдельная функциональность netfilter, управляемая соответствующими правилами.

То есть iptables — не сам firewall kernel.

## Модель iptables

В классической модели iptables есть:

```
Table
  │
  └── Chain
        │
        ├── Rule
        ├── Rule
        ├── Rule
        └── ...
```

Например

```
filter
 ├── INPUT
 │    ├── allow loopback
 │    ├── allow ESTABLISHED
 │    ├── allow SSH
 │    └── DROP
 │
 ├── OUTPUT
 │    └── ...
 │
 └── FORWARD
      ├── allow established
      ├── allow HTTPS
      └── DROP
```

Table

Определяет функциональную область.

Chain

Определяет точку/контекст обработки.

Rule

Определяет конкретное условие и действие.

## Основные таблицы

| Table    | Назначение                                             |
| -------- | ------------------------------------------------------ |
| `filter` | фильтрация                                             |
| `nat`    | Network Address Translation                            |
| `mangle` | изменение/маркировка пакетов                           |
| `raw`    | специальные операции, в частности влияние на conntrack |

### filter

Главная таблица для обычного firewall policy.

Здесь находятся:

```
INPUT
OUTPUT
FORWARD
```

### nat

Используется для NAT.

Например:

```
SNAT
DNAT
MASQUERADE
```

Типичные chains:

```
PREROUTING
POSTROUTING
OUTPUT
```

NAT не является обычной packet-filtering policy.

Его задача — изменить addressing/translation behavior, а не решить основной вопрос security policy.

### mangle

Исторически используется для специальных изменений и маркировки пакетов.

Для обычного enterprise firewall чаще всего не стоит начинать архитектуру с mangle.


### raw

raw существует для случаев, когда требуется воздействовать на обработку до обычного conntrack path.


## Основные chains

В классическом iptables наиболее важны:

```
INPUT
OUTPUT
FORWARD
```

А для NAT также:

```
PREROUTING
POSTROUTING
```

## Почему PREROUTING и POSTROUTING важны

До routing decision существует PREROUTING.

После того как Linux решил, что пакет будет отправлен через eth1, существует POSTROUTING.

Это особенно важно для NAT.

## Чтение существующего ruleset

```
iptables-save
```

выдаёт ruleset в формате, удобном для сохранения и восстановления.

Пример:

```
*filter
:INPUT DROP [0:0]
:FORWARD DROP [0:0]
:OUTPUT ACCEPT [0:0]

-A INPUT -i lo -j ACCEPT
-A INPUT -m conntrack --ctstate ESTABLISHED,RELATED -j ACCEPT
-A INPUT -p tcp --dport 22 -s 10.10.10.0/24 -j ACCEPT

-A FORWARD -m conntrack --ctstate ESTABLISHED,RELATED -j ACCEPT
-A FORWARD -p tcp --dport 443 -j ACCEPT

COMMIT
```



## Правило iptables

Рассмотрим:

```
iptables -A INPUT \
  -p tcp \
  -s 10.10.10.0/24 \
  --dport 22 \
  -j ACCEPT
```

-A INPUT

Добавить правило в INPUT.

-p tcp

Только TCP.

-s 10.10.10.0/24

Source network.

--dport 22

Destination port 22.

-j ACCEPT

Action:

ACCEPT

## Порядок правил

Правила в chain обрабатываются последовательно.

```
1. -A INPUT -p tcp --dport 22 -j DROP
2. -A INPUT -p tcp --dport 22 -s 10.10.10.0/24 -j ACCEPT
```

SSH из 10.10.10.0/24 всё равно будет заблокирован.

Почему?

Пакет сначала совпал:

rule #1

и получил:

DROP

до того, как дошёл до rule #2.

## Terminating и non-terminating actions

Не каждое правило обязательно заканчивает обработку chain.

```
ACCEPT
DROP
REJECT
```

обычно завершают текущую обработку.

## Counters

iptables хранит packet/byte counters.

Это уже observability.

## Stateful rule

```
iptables -A INPUT \
  -m conntrack \
  --ctstate ESTABLISHED,RELATED \
  -j ACCEPT
```

## INPUT пример

```
INPUT policy = DROP

1. loopback             → ACCEPT
2. ESTABLISHED,RELATED  → ACCEPT
3. management → TCP/22  → ACCEPT
4. any → TCP/443        → ACCEPT
5. everything else      → DROP
```


```
iptables -P INPUT DROP

iptables -A INPUT -i lo -j ACCEPT

iptables -A INPUT \
  -m conntrack \
  --ctstate ESTABLISHED,RELATED \
  -j ACCEPT

iptables -A INPUT \
  -p tcp \
  -s 10.10.10.0/24 \
  --dport 22 \
  -j ACCEPT

iptables -A INPUT \
  -p tcp \
  --dport 443 \
  -j ACCEPT
```

## FORWARD пример

```
Client network
10.10.10.0/24
       │
       ▼
 Linux firewall
       │
       ▼
Server network
10.20.20.0/24
```


```
iptables -P FORWARD DROP

iptables -A FORWARD \
  -m conntrack \
  --ctstate ESTABLISHED,RELATED \
  -j ACCEPT

iptables -A FORWARD \
  -s 10.10.10.0/24 \
  -d 10.20.20.0/24 \
  -p tcp \
  --dport 443 \
  -j ACCEPT
```

полезнее

```

```

# nftables

## Основная идея

nftables — современный framework для настройки packet filtering, NAT и связанных с этим механизмов Linux.

```
iptables:
tables → chains → rules
```

но разные таблицы имеют исторически разные semantics.

В nftables модель более унифицированная:

```
family
  │
  └── table
        │
        ├── chain
        │     ├── rule
        │     ├── rule
        │     └── ...
        │
        ├── set
        ├── map
        └── ...
```


## Family

Первый уровень — family.

```
ip
ip6
inet
arp
bridge
netdev
```

## Table

Создадим таблицу:

```
nft add table inet firewall
```

```
inet
└── firewall
```

Table — это логический контейнер для:

- chains;
- sets;
- maps;
- counters;
- других объектов.

В nftables таблица — прежде всего логический namespace/контейнер объектов.

## Chain

Chain содержит правила.

Например:
```
nft add chain inet firewall input
```

```
inet firewall
└── input
```

Но здесь появляется очень важное отличие от обычной пользовательской chain в iptables.

Regular chain

Обычная цепочка, в которую можно переходить из других chains.

Base chain

Chain, непосредственно привязанная к kernel hook.

## Base chain

```
nft add chain inet firewall input \
  '{ type filter hook input priority 0; policy drop; }'
```

```
type   = filter
hook   = input
priority = 0
policy = drop
```

```
Kernel
  │
  ▼
INPUT hook
  │
  ▼
inet firewall/input
  │
  ├── rule
  ├── rule
  └── rule
```

В nftables можно создавать свои base chains и явно определять:

hook;
priority;
policy.

Это даёт значительно больше контроля.

## Hooks

Основные hooks, которые нужно знать:

```
prerouting
input
forward
output
postrouting
```


Они соответствуют различным этапам packet processing.

```
                  packet
                    │
                    ▼
               prerouting
                    │
                    ▼
                 routing
               /         \
              /           \
             ▼             ▼
          input         forward
             │             │
             │             ▼
             │          postrouting
             │             │
             ▼             ▼
          local          egress
```


## Priority

```
hook input priority -100
hook input priority 0
hook input priority 100
```

```
INPUT hook

priority -100
     ↓
chain A

priority 0
     ↓
chain B

priority 100
     ↓
chain C
```

Они будут выполняться в определённом порядке.


## Создание базового firewall

```
nft add table inet firewall
```

Создаём input chain:

```
nft add chain inet firewall input \
  '{ type filter hook input priority 0; policy drop; }'
```

Создаём output:

```
nft add chain inet firewall output \
  '{ type filter hook output priority 0; policy accept; }'
```

И forward:

```
nft add chain inet firewall forward \
  '{ type filter hook forward priority 0; policy drop; }'
```

## Sets

Принадлежит ли значение множеству?

```
nft add set inet firewall ssh_sources \
    '{ type ipv4_addr; }'
```

```
nft add element inet firewall ssh_sources \
    '{ 10.10.10.0/24, 10.20.10.0/24, 192.0.2.10, 192.0.2.11 }'
```

## Maps

Какому значению соответствует этот ключ?

Maps позволяют выразить более сложную policy logic без большого количества дублирующих rules.

## Counters

```
nft add counter inet firewall https_counter
```

# Базовая политика хоста

Базовая политика хоста (Host-based Firewall) первый рубеж защиты самого сервера.
Её главная задача закрыть все точки входа по умолчанию и оставить доступ только для авторизованного и необходимого легитимного трафика.

## Default deny (Запрещено всё, что не разрешено)

Закрываем всё, что явно не разрешено. Это снижает поверхность атаки.

По умолчанию сетевой стек сервера должен отбрасывать любые входящие пакеты (INPUT DROP).

## Разрешение Loopback и состояния соединения

Перед блокировкой необходимо прописать два базовых исключения:

- Loopback (lo / 127.0.0.1): Запросы внутри самого сервера (например, веб-сервер обращается к локальной базе данных MySQL).
Если заблокировать loopback, перестанет работать большинство локальных сервисов.

- Established / Related: Разрешает входящие пакеты, которые принадлежат уже установленным соединениям или связанным с ними (например, ответ сервера на ваш исходящий запрос apt update или curl).

## Открытие только сервисных портов

- 22/TCP — SSH (администрирование)

- 80/TCP, 443/TCP — HTTP/HTTPS (веб-трафик)

- Дополнительные порты открываются по мере необходимости с ограничением по IP (если возможно).


Каждый открытый порт — потенциальная точка проникновения. Открываются строго определенные порты с целевым назначением:

## Безопасная настройка SSH

Главная опасность при настройке фаервола на удаленном сервере — случайно заблокировать себе доступ.

Правильный порядок:

- Разрешить входящий трафик на порт SSH (по умолчанию 22/TCP).
- Включить политику DROP для остальных входящих пакетов.
- Не закрывая текущую сессию SSH, открыть второе окно терминала и проверить подключение.


# Фильтрация маршрутизатора

Фильтрация на уровне маршрутизатора (Router/Gateway Firewall) применяется,
когда хост выступает шлюзом между двумя и более сетями (например, LAN и WAN, или между разными VLAN в DMZ).
В отличие от базовой политики хоста, где фильтруется трафик до самого сервера (INPUT), здесь ключевая цепочка — FORWARD.

- IP Forwarding: Базовая функция ядра Linux/роутера, превращающая его из изолированного узла в маршрутизатор транзитного трафика.
- Цепочка FORWARD: Весь транзитный трафик обрабатывается в FORWARD, а не в INPUT/OUTPUT. Для нее также применяется принцип Default Deny (policy DROP).
- Минимальные привилегия (Least Privilege): Межсетевое экранирование строится на явном разрешении только необходимых направлений (например, LAN -> WAN разрешено, DMZ -> LAN запрещено).
- Контроль состояний и аномалий: Дроп пакетов со статусом INVALID и защита от асимметричного маршрута — критическая часть устойчивости stateful-фаервола.

## Включение IP Forwarding (Маршрутизации пакетов)

По умолчанию ядро Linux работает как конечный хост и отбрасывает пакеты, предназначенные другим IP-адресам. Для выполнения функций роутера эту опцию нужно активировать.

Изменение переменной ядра net.ipv4.ip_forward = 1 через sysctl. Без этой настройки правила FORWARD работать не будут, так как ядро просто не передаст пакеты дальше.

## Настройка правил FORWARD между сетями

Маршрутизатор разделяет сети на зоны доверия 
(например: LAN — локальная сеть, DMZ — демилитаризованная зона с серверами, WAN — внешний интернет).

- Политика по умолчанию: `iptables -P FORWARD DROP` или аналоги в nftables.
- Разрешение состояний: Как и на хосте, транзитные ответы на уже установленные соединения пропускаются автоматически:
    ```
    ct state established,related accept
    ```
  
## Принцип минимальных привилегий (Least Privilege)

Разрешаются только четко определенные направления и порты. Любой другой транзит блокируется.

Пример матрицы доступов:

- LAN → WAN: Разрешено (сотрудникам нужен интернет: HTTP/HTTPS, DNS).
- WAN → DMZ: Разрешено только на публичные порты (например, 80/443 к веб-серверу).
- DMZ → LAN: Строго запрещено (если взломают веб-сервер в DMZ, злоумышленник не должен попасть во внутреннюю сеть).

## Обработка INVALID и асимметричного трафика

Stateful-фаервол отслеживает состояние каждого соединения в таблице conntrack.

### Статус INVALID:
Пакеты, которые не соответствуют ни одному известному соединению и не являются корректным началом нового соединения
(например, поврежденные TCP-пакеты, сканирование или поддельные ACK/FIN флаги). 

Пакеты с ct state invalid должны сразу отбрасываться (DROP), чтобы не тратить ресурсы системы и не пропускать сетевые аномалии.

### Асимметричный трафик (Asymmetric Routing):
Ситуация, когда исходящий пакет идет через Роутер А, а обратный ответ возвращается через Роутер Б

Роутер Б не видел начала сессии (SYN-пакета) и пометит входящий ответ как INVALID или отбросит его, разрушая соединение.

Настройка правильной метрической маршрутизации, использование SNAT/MASQUERADE для принудительного симметричного пути либо отключение строгой проверки состояний для определенных каналов (если асимметрия неизбежна).


# NAT
NAT (Network Address Translation)
это механизм преобразования IP-адресов и портов в заголовках IP-пакетов при их прохождении через маршрутизатор.
Он решает задачи экономии IPv4-адресов, скрытия внутренней топологии сети и предоставления доступа к внутренним ресурсам из внешней сети.

- SNAT / Masquerading: Изменяет Source IP (адрес источника). Используется для выхода устройств из частной сети (LAN/DMZ) в интернет.
- DNAT (Port Forwarding): Изменяет Destination IP (адрес назначения). Используется для публикации внутренних сервисов во внешнюю сеть.
- Hairpin NAT (NAT Loopback): Специальная настройка DNAT + SNAT, позволяющая узлам из локальной сети обращаться к внутренним сервисам по их внешнему (публичному) IP-адресу.
- Диагностика: Изменения заголовков и состояния сессий проверяются сочетанием утилит tcpdump (анализ сырых пакетов на интерфейсах) и conntrack (просмотр таблицы трансляций ядра).

## Виды трансляции адресов: SNAT, DNAT, Masquerading

| Тип | Где применяется | Что меняет | Назначение |
|-----|----------------|------------|------------|
| **SNAT** (Source NAT) | Цепочка `POSTROUTING` | IP-адрес отправителя | Используется, если у маршрутизатора статический внешний IP. |
| **Masquerading** | Цепочка `POSTROUTING` | IP-адрес отправителя | Разновидность SNAT для динамических IP (DHCP/PPPoE). Автоматически подставляет текущий IP интерфейса. |
| **DNAT** (Destination NAT) | Цепочка `PREROUTING` | IP-адрес и порт получателя | Перенаправляет входящий трафик с внешнего IP роутера на внутренний IP сервера. |

## Публикация внутреннего сервиса (DNAT / Port Forwarding)

Чтобы сервис из локальной сети (например, веб-сервер 10.0.2.10:80) стал доступен из интернета по внешнему IP роутера (1.2.3.4:80), настраивается правило DNAT

1. Пакет от клиента из WAN приходит на 1.2.3.4:80.

2. В цепочке PREROUTING адрес назначения перезаписывается на 10.0.2.10:80.

3. Пакет передается в цепочку FORWARD и уходит на локальный сервер.

4. Ответный пакет от сервера автоматически подвергается обратной трансляции на роутере.

## Hairpin NAT (NAT Loopback) и ограничения трансляции

Если клиент из локальной сети (10.0.1.50) пытается подключиться к внутреннему веб-серверу (10.0.2.10),
используя публичный IP роутера (1.2.3.4), возникает сбой асимметричной маршрутизации:

1. Клиент отправляет пакет: Src: 10.0.1.50 -> Dst: 1.2.3.4.

2. Роутер делает DNAT: Src: 10.0.1.50 -> Dst: 10.0.2.10 и отправляет пакет веб-серверу.

3. Веб-сервер видит, что отправитель — 10.0.1.50 (сосед по сети), и отвечает напрямую, минуя роутер: Src: 10.0.2.10 -> Dst: 10.0.1.50.

4. Клиент ждал ответ от 1.2.3.4, а получил от 10.0.2.10. Сессия сбрасывается (RST).

На роутере добавляется правило SNAT для трафика, который одновременно приходит из LAN и направляется в LAN:

- При отправке пакета на веб-сервер роутер подменяет Src IP на свой локальный IP (10.0.1.1).
- Веб-сервер отвечает роутеру, роутер делает обратную трансляцию и корректно передает ответ клиенту.

## Диагностика и проверка: tcpdump и conntrack

### conntrack

Позволяет смотреть текущее состояние таблицы трансляций в реальном времени.

```
# Просмотр активных трансляций для конкретного IP

conntrack -L -p tcp --orig-dst 1.2.3.4
```

Вывод показывает оригинальное направление (src=198.51.100.5 dst=1.2.3.4) и то, как фаервол ожидает обратный пакет (src=10.0.2.10 dst=198.51.100.5).

### tcpdump

Используется для проверки подмены адресов на разных интерфейсах

```
# Дамп на внешнем интерфейсе (видим подмену входящего IP при DNAT или исходящего при SNAT)
tcpdump -nn -i eth1 port 80

# Дамп на внутреннем интерфейсе (видим уже транслированный IP)
tcpdump -nn -i eth0 port 80
```

# Защита и ограничения

- Нельзя полностью отключать ICMP: Полный блок ICMP ломает механизмы PMTUD (Path MTU Discovery) и диагностику (ping/traceroute). Нужно ограничивать лишь его частоту (rate limiting).
- Списки доступов через Sets: Вместо создания сотен дублирующихся правил фильтрации используются множества (sets), которые обрабатываются ядром со скоростью $O(1)$.
- Ограничение частоты соединений: Защищает от переполнения таблицы conntrack при SYN-флуде и брутфорсе авторизации.
- Границы возможностей Фаервола: L3/L4-фаервол бессилен против объёмного DDoS (который забивает сам аплинк) и против L7-атак (HTTP-флуд), так как не анализирует содержимое прикладных пакетов.

## Ограничение частоты ICMP и новых соединений (Rate Limiting)

ICMP необходим для нормальной работы IP-сетей. Например, сообщение ICMP Type 3 Code 4 (Fragmentation Needed) критично для согласия размера MTU между узлами.

Открытие нового TCP-соединения (SYN) требует выделения памяти в таблице conntrack. Модули limit / meter позволяют задавать "burst" (всплеск) и допустимую частоту новых подключений.

## Защита административных портов и использование Sets

Жесткое ограничение IP-адресов, с которых разрешен доступ к SSH (22), RDP (3389) или веб-панелям управления — наилучший вариант защиты от брутфорса.

## Границы защиты Firewall от DDoS-атак

Настоящий Volumetric DDoS отражается только на уровне провайдера / специализированных систем очистки трафика (BGP Anycast / Scrubbing Centers).

| Тип DDoS-атаки | Принцип атаки | Эффективен ли Stateful Firewall? | Почему? |
|----------------|---------------|----------------------------------|---------|
| **Volumetric (L3/L4)** (UDP/ICMP Flood) | Забивание полосы пропускания гигабайтами мусорного трафика. | **НЕТ** | Канал связи или сетевая карта забиваются до того, как фаервол успеет обработать и отбросить пакеты. |
| **State Exhaustion** (SYN Flood) | Переполнение таблицы conntrack миллионами полуоткрытых сессий. | **ЧАСТИЧНО** | Помогают правила NOTRACK, SYN Cookies на уровне ядра и строгий Rate Limit. |
| **Application Layer (L7)** (HTTP Flood, Slowloris) | Легитимные HTTPS-запросы к тяжелым эндпоинтам (поиск, авторизация). | **НЕТ** |  |


# Совместимость и миграция

Миграция с устаревшего стека iptables на современный nftables — важный шаг при эксплуатации Linux-систем. nftables пришел на смену iptables, ip6tables, arptables и ebtables, объединяя их в единый API и обеспечивая более высокую производительность обработки сетевых пакетов.

## Различия iptables legacy и iptables-nft

| Критерий | iptables-legacy | iptables-nft | nftables (native) |
|----------|-----------------|--------------|-------------------|
| **API ядра** | Netfilter Legacy API | nf_tables API (через слой трансляции) | nf_tables API |
| **Таблицы/Цепочки** | Фиксированные (filter, nat, mangle) | Фиксированные (эмулируются) | Произвольные (создаются вручную) |
| **Обработка правил** | Линейная O(N) | Линейная O(N) через утилиту | O(1) при использовании sets и maps |
| **Атомарность** | Нет (правила заменяются поштучно) | Да (через слой nft) | Да (полный сброс и загрузка за 1 транзакцию) |

## Трассировка

Трассировка позволяет пошагово отследить прохождение конкретного пакета через все таблицы, цепочки и правила nftables.

1. Включение трассировки для целевого трафика
  ```
  # Добавляем правило с меткой trace в цепочку raw/prerouting
  nft add table inet raw
  nft add chain inet raw prerouting { type filter hook prerouting priority -300 \; }
  nft add rule inet raw prerouting ip saddr 192.168.1.50 trace
  ```
2. Мониторинг событий трассировки в реальном времени
  ```
  nft monitor trace
  ```
3. Отключение трассировки (удаление правила)
  ```
  nft flush table inet raw
  ```

## Анализ трафика с помощью tcpdump

tcpdump захватывает сетевые пакеты до или после их обработки фильтрами (в зависимости от интерфейса и направления).

Полезные флаги:

-i <iface> — указать интерфейс (any для всех).

-n — не разрешать IP в имена хостов.

-nn — не разрешать IP и порты.

-v / -vv / -vvv — уровень детализации.

-e — отображение MAC-адресов (L2-заголовков).

-e -X — дамп содержимого в HEX и ASCII.

Практические примеры фильтров:

```
# Захват SYN-пакетов (попытки установки соединений):

tcpdump -nn -i eth0 'tcp[tcpflags] & (tcp-syn) != 0'
```

```
# Мониторинг конкретного хоста и порта

tcpdump -nn -i any host 10.0.0.5 and port 80
```

```
# Захват ICMP (ping / ошибки unreachable)

tcpdump -nn -i eth0 icmp or icmp6
```

# Эксплуатация

Надёжная эксплуатация nftables в продакшене требует строгого соблюдения регламентов: правила должны применяться без потери существующих соединений, перед загрузкой обязательна валидация синтаксиса, а конфигурация должна корректно восстанавливаться после перезагрузки узла.

## Атомарная загрузка правил
Главное преимущество nftables перед устаревшим iptables — возможность обновить всю конфигурацию фаервола в рамках одной атомарной транзакции. Это означает, что фаервол либо полностью переходит в новое состояние, либо (в случае ошибки) не применяется вовсе, не оставляя систему в промежуточном «полуоткрытом» состоянии.

Для атомарной перезагрузки используется команда nft -f. При этом файл конфигурации обязательно должен начинаться с полной очистки старого набора правил через flush ruleset


```
nft -f /etc/nftables.conf
```

## Проверка конфигурации до применения

Флаг -c (--check) проверяет синтаксис и валидность файла конфигурации без загрузки правил в ядро:

```
nft -c -f /etc/nftables.conf
```

## Настройка постоянной загрузки после перезагрузки

```
systemctl enable nftables
systemctl restart nftables
```

```
systemctl status nftables
```


```
nft list ruleset > /etc/nftables.conf
```

## Документирование и регулярная гигиена правил

Со временем наборы правил фаервола замусориваются временными исключениями, что снижает безопасность и усложняет отладку.

Использование комментариев прямо в nftables
nftables поддерживает встроенные комментарии к отдельным правилам. Они сохраняются в ядре и видны при выводе nft list ruleset.

```
table inet filter {
    chain input {
        type filter hook input priority filter; policy drop;

        # [TICKET-1042] Временный доступ для внешнего аудита (Удалить после 2026-12-01)
        ip saddr 203.0.113.45 tcp dport 443 accept comment "Temp access for SecOps audit"

        # [INFRA-55] Мониторинг Prometheus
        ip saddr 10.100.0.15 tcp dport 9100 accept comment "Prometheus exporter"
    }
}
```

Конфигурация /etc/nftables.conf должна храниться в Git-репозитории проекта/инфраструктуры (IaC via Ansible/Puppet). Изменения должны проходить через Merge Request с обязательным шагом валидации nft -c -f.
