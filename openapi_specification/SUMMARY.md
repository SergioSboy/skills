# Основные понятия

# 1. Основные понятия OpenAPI

## 1.1. Спецификация и инструменты Swagger

**OpenAPI Specification — стандарт машиночитаемого описания HTTP API.** Он определяет, как описывать операции, параметры, тела запросов, ответы и требования безопасности независимо от языка реализации.

Документ обычно записывают в YAML или JSON.

| Понятие | Назначение |
|---|---|
| **OpenAPI Specification — OAS** | Правила и структура описания API |
| **OpenAPI-документ** | Контракт конкретного API, записанный по этим правилам |
| **Swagger UI** | Показывает документ как интерактивную документацию и позволяет отправлять запросы |
| **Swagger Editor** | Помогает писать и проверять описание API |
| **Генератор кода** | Создаёт клиентские библиотеки, серверные заготовки или другие артефакты по документу |

Например, Swagger Codegen — один из генераторов, а не сама спецификация. [Инструменты Swagger](https://swagger.io/open-source/).

```text
OpenAPI-документ
    ├── Swagger UI → интерактивная документация
    ├── Генератор → клиент или серверная заготовка
    └── Инструменты проверки → проверки контракта
```

**Описание не реализует API автоматически.** Серверная заготовка не содержит готовых бизнес-правил, а красивый Swagger UI не доказывает соответствие сервера контракту.

## 1.2. Swagger 2.0 и OpenAPI 3.x

**Swagger Specification — прежнее название спецификации.** Формат Swagger 2.0 также известен как OpenAPI 2.0. После передачи спецификации OpenAPI Initiative развитие продолжилось под названием OpenAPI.

Swagger сегодня — название семейства инструментов.

| Версия | Пример отличий |
|---|---|
| **2.0** | Поле `swagger: "2.0"`, адрес через `host`, `basePath`, `schemes` |
| **3.x** | Поле `openapi`, адреса через `servers`, отдельный `requestBody`, переиспользуемые определения в `components` |

**По состоянию на 27 октября 2026 года последняя опубликованная версия — OpenAPI 3.2.1.** При этом инструменты могут поддерживать разные подверсии 3.x, поэтому версию документа выбирают с учётом всей цепочки обработки. [Официальные версии OpenAPI](https://spec.openapis.org/oas/).

Переход с 2.0 на 3.x — не простое переименование поля: структура документа изменилась.

## 1.3. Структура OpenAPI-документа

| Поле | Что описывает |
|---|---|
| **`openapi`** | Версию спецификации, которой соответствует документ |
| **`info`** | Название, описание и версию описываемого API |
| **`servers`** | Базовые адреса API |
| **`paths`** | Пути и доступные на них операции |
| **`components`** | Переиспользуемые схемы, параметры, ответы и определения безопасности |
| **`security`** | Требования безопасности по умолчанию |
| **`tags`** | Описание групп операций |

Небольшой пример на YAML:

```yaml
openapi: 3.2.1

info:
  title: Orders API
  version: 1.0.0

servers:
  - url: https://api.example.com

tags:
  - name: Orders
    description: Работа с заказами

paths:
  /orders:
    get:
      tags: [Orders]
      summary: Получить список доступных пользователю заказов
      responses:
        "200":
          description: Список заказов
          content:
            application/json:
              schema:
                type: array
                items:
                  $ref: "#/components/schemas/Order"

components:
  schemas:
    Order:
      type: object
      required: [id, status]
      properties:
        id:
          type: string
        status:
          type: string

  securitySchemes:
    bearerAuth:
      type: http
      scheme: bearer

security:
  - bearerAuth: []
```

Важные различия:

- `openapi` — версия **формата документа**, `info.version` — версия **описываемого API**.
- `components` определяет элементы для повторного использования; обычно их подключают через `$ref`.
- `securitySchemes` описывает механизмы, а `security` указывает, какие из них требуются.
- Глобальные требования `security` можно переопределить для отдельной операции.

**Запись безопасности не включает защиту на сервере.** Реализация должна самостоятельно проверять токен и права доступа. Структура документа определена в [спецификации OpenAPI](https://spec.openapis.org/oas/v3.2.1.html).

## 1.4. Потребители контракта

**Контракт нужен людям и инструментам, которые разрабатывают, проверяют и используют API.**

| Потребитель | Как использует |
|---|---|
| **Клиентские команды** | Изучают операции, форматы, ошибки; создают или генерируют клиенты |
| **Тестирование** | Проверяет запросы и ответы, готовит сценарии и тестовые данные |
| **Архитектура** | Оценивает границы, согласованность контрактов и совместимость |
| **API Gateway** | Может импортировать описание для настройки маршрутов и проверок — в пределах своих возможностей |
| **Команда сервера** | Согласует поведение API и поддерживает документацию |

Нужно учитывать возможности потребителей: поддерживаемые версии, ограничения генераторов и обязательные соглашения.

**OpenAPI описывает интерфейс, но не все бизнес-гарантии выражаются схемами.** Например, идемпотентность, порядок переходов заказа и поведение при конкурентных запросах требуют явного описания и отдельных проверок.

**Запомнить:** OpenAPI — стандарт контракта, Swagger — инструменты вокруг него. Ценность документа определяется точностью, актуальностью и пригодностью для его потребителей.

# 2. Описание операций

## 2.1. Путь, метод и назначение

**Операцию API определяет сочетание пути и HTTP-метода.** Например, `GET /orders` получает список заказов, а `POST /orders` создаёт заказ.

| Поле | Назначение |
|---|---|
| **Path** | Путь относительно адреса из `servers` |
| **Method** | HTTP-метод: `get`, `post`, `patch` и другие |
| **`operationId`** | Уникальный идентификатор операции в документе |
| **`summary`** | Краткое назначение |
| **`description`** | Подробное поведение, ограничения и важные особенности |
| **`tags`** | Группы, к которым относится операция |

Фрагмент документа:

```yaml
paths:
  /orders/{orderId}:
    get:
      operationId: getOrder
      summary: Получить заказ
      description: |
        Возвращает заказ, доступный текущему пользователю.
        Не изменяет состояние заказа.
      tags:
        - Orders
```

Описания параметров и ответов добавляются ниже.

**Если `operationId` указан, он должен быть уникальным.** Генераторы могут использовать его для имён клиентских методов, поэтому изменение идентификатора способно повлиять на сгенерированный клиент даже без изменения URL.

В `description` объясняют поведение, а не пересказывают название. Например, для отмены важно уточнить допустимые состояния и асинхронность возврата. [Описание Operation Object](https://spec.openapis.org/oas/v3.2.1.html#operation-object).

## 2.2. Параметры path, query, header и cookie

**Параметр описывает отдельное значение вне тела запроса.** Его расположение задаётся через `in`.

| Расположение | Пример | Назначение |
|---|---|---|
| **`path`** | `/orders/{orderId}` | Идентификация ресурса |
| **`query`** | `/orders?status=confirmed` | Фильтры, сортировка, пагинация |
| **`header`** | `Idempotency-Key: operation-123` | Метаданные запроса |
| **`cookie`** | `locale=ru` | Значение, передаваемое через cookie |

Пример для получения заказа:

```yaml
parameters:
  - name: orderId
    in: path
    required: true
    description: Идентификатор заказа
    schema:
      type: string
      minLength: 1

  - name: includeHistory
    in: query
    required: false
    description: Включить историю изменений
    schema:
      type: boolean
      default: false
```

Основные правила:

- имя path-параметра должно совпадать с переменной в пути;
- **path-параметры всегда имеют `required: true`;**
- для остальных обязательность указывается по контракту;
- типы, ограничения и примеры помогают избежать неоднозначности;
- для массивов и объектов нужно согласовать сериализацию через `style` и `explode`.

Аутентификацию через `Authorization` или сессионную cookie описывают механизмами `securitySchemes` и `security`, а не обычным параметром. [Описание параметров](https://spec.openapis.org/oas/v3.2.1.html#parameter-object).

## 2.3. Тело запроса и content types

**Тело запроса описывается через `requestBody`.** Внутри `content` перечисляют поддерживаемые медиатипы и соответствующие схемы.

Фрагмент операции создания заказа:

```yaml
requestBody:
  required: true
  description: Данные нового заказа
  content:
    application/json:
      schema:
        type: object
        required:
          - productId
          - quantity
        properties:
          productId:
            type: string
            minLength: 1
          quantity:
            type: integer
            minimum: 1
      example:
        productId: product-42
        quantity: 2
```

Здесь две разные обязательности:

- `requestBody.required` — обязательно ли **само тело**;
- `schema.required` — какие **поля объекта** обязательны.

Типичные медиатипы:

| Медиатип | Применение |
|---|---|
| `application/json` | Структурированные данные |
| `multipart/form-data` | Формы с файлами и другими полями |
| `application/x-www-form-urlencoded` | Кодированные поля формы |
| `application/octet-stream` | Двоичное содержимое |

**Указывай только реально поддерживаемые форматы.** Перечисление JSON и XML в документе не добавляет серверу поддержку XML.

Схема определяет форму данных, но не заменяет бизнес-проверки. Например, положительное количество ещё не гарантирует наличие товара. [Описание Request Body](https://spec.openapis.org/oas/v3.2.1.html#request-body-object).

## 2.4. Успешные и ошибочные ответы

**В `responses` описывают ожидаемые результаты по HTTP-статусам:** смысл, тело и необходимые заголовки.

| Статус | Типичный смысл |
|---|---|
| **200** | Успешное выполнение с результатом |
| **201** | Ресурс создан |
| **202** | Запрос принят, обработка ещё не завершена |
| **204** | Успех без тела ответа |
| **400** | Некорректный запрос |
| **401 / 403** | Требуется аутентификация / доступ запрещён |
| **404** | Ресурс не найден |
| **409** | Конфликт с текущим состоянием |
| **422** | Синтаксически корректное содержимое невозможно обработать по заданным правилам |
| **503** | Временная недоступность |

Конкретное применение статусов согласуют для API.

```yaml
responses:
  "201":
    description: Заказ создан
    content:
      application/json:
        schema:
          type: object
          required: [id, status]
          properties:
            id:
              type: string
            status:
              type: string

  "409":
    description: Операция конфликтует с текущим состоянием
    content:
      application/json:
        schema:
          type: object
          required: [code, message]
          properties:
            code:
              type: string
            message:
              type: string
        example:
          code: RESERVATION_EXPIRED
          message: Срок действия резерва истёк
```

Для каждого ответа требуется `description`. У `204` тело не описывают. Повторяемые схемы ошибок удобно вынести в `components`.

**Не описывай только `200` для всех исходов.** Клиенту нужны различимые ошибки и стабильные машинные коды, чтобы выбирать реакцию. `default` может описывать остальные ответы, но не должен скрывать известные существенные случаи. [Описание Responses](https://spec.openapis.org/oas/v3.2.1.html#responses-object).

**Запомнить:** операция должна объяснять, что вызвать, какие данные передать и какие результаты обработать. Схемы задают форму, описания уточняют смысл, HTTP-статусы различают исходы.

# 3. Компоненты и переиспользование

## 3.1. Что выносить в `components`

**`components` хранит определения, которые можно использовать в разных местах контракта.**

| Раздел | Что содержит |
|---|---|
| **`schemas`** | Структуры данных и ограничения |
| **`parameters`** | Параметры операций |
| **`responses`** | Ответы целиком: описание, заголовки и содержимое |
| **`requestBodies`** | Тела запросов |
| **`examples`** | Именованные примеры |
| **`headers`** | Определения заголовков ответа |
| **`securitySchemes`** | Механизмы аутентификации |

Пример:

```yaml
components:
  schemas:
    Order:
      type: object
      required: [id, status]
      properties:
        id:
          type: string
        status:
          type: string

  parameters:
    OrderId:
      name: orderId
      in: path
      required: true
      schema:
        type: string

  examples:
    ConfirmedOrder:
      summary: Подтверждённый заказ
      value:
        id: order-42
        status: confirmed
```

**Определение не подключается автоматически.** Его нужно использовать в операции или другом объекте документа.

Необязательно выносить каждый небольшой фрагмент: локальное описание иногда проще цепочки ссылок.

## 3.2. `$ref` вместо дублирования

**`$ref` указывает на существующее определение.** Это позволяет изменять общий контракт в одном месте.

Фрагмент операции:

```yaml
paths:
  /orders/{orderId}:
    get:
      operationId: getOrder
      parameters:
        - $ref: "#/components/parameters/OrderId"
      responses:
        "200":
          description: Заказ найден
          content:
            application/json:
              schema:
                $ref: "#/components/schemas/Order"
              examples:
                confirmed:
                  $ref: "#/components/examples/ConfirmedOrder"
```

Внутренняя ссылка начинается с `#`. Можно ссылаться и на отдельные файлы:

```yaml
$ref: "./schemas/order.yaml"
```

Внешние ссылки удобны для больших контрактов, но инструменты должны уметь их разрешать. Для публикации документ часто собирают в один файл — выполняют **bundling**.

**Ссылка должна вести на подходящий тип объекта:** в `schema` — на схему, в ответ — на Response Object.

Не объединяй определения только из-за одинакового набора полей. Например, запрос создания заказа и ответ заказа могут развиваться независимо и иметь разные правила обязательности.

## 3.3. Пагинация, ошибки и заголовки

**Повторяемые соглашения описывают один раз и явно подключают в нужных операциях.**

### Пагинация

Можно переиспользовать параметры:

```yaml
components:
  parameters:
    PageLimit:
      name: limit
      in: query
      description: Максимальное количество элементов
      schema:
        type: integer
        minimum: 1
        maximum: 100
        default: 20
```

В контракте также описывают способ перехода к следующей странице, сортировку и поведение на последней странице.

OpenAPI не предоставляет встроенные шаблоны вроде `Page<T>`. Обычно определяют конкретную схему `OrderPage`, переиспользуя схему заказа и общие метаданные.

### Ошибки и заголовки

```yaml
components:
  schemas:
    Error:
      type: object
      required: [code, message]
      properties:
        code:
          type: string
        message:
          type: string

  headers:
    RequestId:
      description: Идентификатор запроса для диагностики
      schema:
        type: string

  responses:
    NotFound:
      description: Ресурс не найден
      headers:
        X-Request-Id:
          $ref: "#/components/headers/RequestId"
      content:
        application/json:
          schema:
            $ref: "#/components/schemas/Error"
```

В операции достаточно:

```yaml
responses:
  "404":
    $ref: "#/components/responses/NotFound"
```

**Общая схема ошибки не означает одинаковый HTTP-статус для всех ошибок.** Статус и машинный код должны различать существенные исходы.

Заголовки ответа подключают через `headers`, а заголовки запроса описывают как параметры с `in: header`.

## 3.4. `$ref` в OpenAPI 3.0 и 3.1

**Нужно различать Reference Object и `$ref` внутри Schema Object.**

| Место | OpenAPI 3.0 | OpenAPI 3.1 |
|---|---|---|
| **Reference Object**, например ссылка на ответ или параметр | Соседние поля не расширяют ссылку и игнорируются | Поддерживаются соседние `summary` и `description`; произвольные поля по-прежнему не разрешены |
| **Schema Object с `$ref`** | Ссылка сама по себе не позволяет добавлять ограничения соседними полями | Работают правила JSON Schema: соседние ключевые слова тоже применяются |

Источники: [Reference Object 3.0](https://spec.openapis.org/oas/v3.0.4.html#reference-object), [Reference Object 3.1](https://spec.openapis.org/oas/v3.1.2.html#reference-object), [Schema Object 3.1](https://spec.openapis.org/oas/v3.1.2.html#schema-object).

Для OpenAPI 3.1 допустима схема:

```yaml
schema:
  $ref: "#/components/schemas/Order"
  description: Заказ текущего пользователя
```

Для добавления описания к ссылочной схеме в OpenAPI 3.0 обычно используют обёртку:

```yaml
schema:
  allOf:
    - $ref: "#/components/schemas/Order"
  description: Заказ текущего пользователя
```

**`allOf` не переопределяет исходную схему:** данные должны удовлетворять всем перечисленным ограничениям. Например, так нельзя сделать обязательное поле исходной схемы необязательным.

Поддержку этих правил проверяют в валидаторе, документации и генераторах: указание версии 3.1 в файле не обновляет инструменты автоматически.

**Запомнить:** `components` хранит общие определения, `$ref` подключает их. Переиспользуй одинаковый смысл и учитывай версию спецификации и тип ссылочного объекта.

# 5. Безопасность

## 5.1. Схемы безопасности

**`components.securitySchemes` описывает способы аутентификации, которые поддерживает API.** Само определение схемы ещё не требует её применения.

| Механизм | Как работает | Описание в OpenAPI |
|---|---|---|
| **HTTP Bearer** | Клиент передаёт токен в `Authorization: Bearer …` | `type: http`, `scheme: bearer` |
| **API key** | Ключ передаётся в согласованном заголовке, query или cookie | `type: apiKey` |
| **OAuth 2.0** | Клиент получает access token для доступа с определёнными полномочиями | `type: oauth2`, `flows` |
| **OpenID Connect — OIDC** | Добавляет идентификацию пользователя поверх OAuth 2.0 и обнаружение конфигурации | `type: openIdConnect` |

Примеры:

```yaml
components:
  securitySchemes:
    bearerAuth:
      type: http
      scheme: bearer
      bearerFormat: JWT

    apiKeyAuth:
      type: apiKey
      in: header
      name: X-API-Key

    oauth:
      type: oauth2
      flows:
        authorizationCode:
          authorizationUrl: https://identity.example.com/authorize
          tokenUrl: https://identity.example.com/token
          scopes:
            orders:read: Чтение заказов
            orders:write: Создание и изменение заказов

    oidc:
      type: openIdConnect
      openIdConnectUrl: https://identity.example.com/.well-known/openid-configuration
```

**`bearerFormat: JWT` — подсказка, а не проверка токена.** Bearer-токен не обязательно является JWT.

Для OAuth нужно описать фактически используемый flow. Дополнительные требования, например PKCE для соответствующих клиентов, фиксируют в документации и настройках реализации.

**ID token и access token имеют разное назначение:** API не должен автоматически принимать ID token вместо токена доступа. [Security Scheme Object](https://spec.openapis.org/oas/v3.1.2.html#security-scheme-object).

## 5.2. Глобальные требования и переопределение

**`security` указывает, какие схемы обязательны.** На верхнем уровне оно задаёт требования по умолчанию:

```yaml
security:
  - bearerAuth: []
```

Операция может **заменить**, а не дополнить глобальное требование:

```yaml
paths:
  /orders:
    get:
      security:
        - oauth: [orders:read]
      responses:
        "200":
          description: Список доступных заказов

  /health:
    get:
      security: []
      responses:
        "200":
          description: Сервис работает
```

Здесь `/orders` требует OAuth со scope, а `/health` не требует аутентификации по контракту.

Важна структура:

```yaml
# ИЛИ: достаточно одного способа
security:
  - bearerAuth: []
  - apiKeyAuth: []
```

```yaml
# И: нужны оба способа
security:
  - bearerAuth: []
    apiKeyAuth: []
```

- **Отдельные элементы списка — альтернативы, ИЛИ.**
- **Несколько схем в одном элементе — совместные требования, И.**
- `security: []` снимает глобальные требования.
- Пустой объект `{}` среди альтернатив разрешает доступ без аутентификации.

**OpenAPI документирует правила, но не включает их на сервере.** Проверки должны соответствовать контракту. [Security Requirement Object](https://spec.openapis.org/oas/v3.1.2.html#security-requirement-object).

## 5.3. Секреты и примеры

**В контракт нельзя помещать реальные токены, API-ключи, пароли и client secrets.** Документ может попасть в репозиторий, опубликованную документацию и сгенерированные артефакты.

Используй очевидные заполнители:

```text
Authorization: Bearer <ACCESS_TOKEN>
X-API-Key: <API_KEY>
```

Практические правила:

- примеры должны содержать вымышленные данные;
- секреты вводятся отдельно во время работы;
- CI проверяет изменения на случайные утечки;
- доступ к интерактивной документации и production-вызовам организуется осознанно.

Ключи в URL могут попадать в журналы и историю, поэтому при возможности предпочитают заголовок.

**Если секрет опубликован, удалить пример недостаточно:** секрет отзывают или заменяют, затем проверяют места распространения.

## 5.4. Scopes, `401` и `403`

**Scope — именованное полномочие токена**, например `orders:read`.

```yaml
security:
  - oauth:
      - orders:read
      - orders:write
```

В этом требовании нужны **оба scope**. Если достаточно любого одного, задают отдельные альтернативы.

Наличие scope не заменяет проверку доступа к конкретному объекту: право читать заказы не обязательно разрешает читать чужой заказ.

| Статус | Значение | Пример |
|---|---|---|
| **401 Unauthorized** | Нет действительных данных аутентификации | Bearer-токен отсутствует, недействителен или истёк |
| **403 Forbidden** | Сервер отказывает в доступе | У действительного токена недостаточно полномочий |

Для Bearer API ответы можно описать так:

```yaml
responses:
  "401":
    description: Требуется действительный токен доступа
    headers:
      WWW-Authenticate:
        description: Запрос аутентификации по схеме Bearer
        schema:
          type: string
        example: Bearer

  "403":
    description: Недостаточно полномочий для операции
```

`401` сопровождается подходящим `WWW-Authenticate`. Ошибки желательно возвращать в общем формате с машинным кодом, не раскрывая содержимое токена и внутренние детали.

**Запомнить:** схема определяет механизм, `security` — условия доступа, scopes — полномочия. Реальная защита требует серверной проверки токена, разрешений и доступа к объектам.

# 6. Примеры и публикация

## 6.1. Примеры запросов, результатов и ошибок

**Пример показывает конкретное использование контракта, а схема определяет все допустимые данные.** Они дополняют друг друга.

Для важной операции полезно показать:

- минимальный корректный запрос;
- успешный ответ;
- типовую ошибку с пояснением причины;
- особый вариант, если он существенно отличается.

Фрагмент тела запроса:

```yaml
content:
  application/json:
    schema:
      $ref: "#/components/schemas/CreateOrder"
    examples:
      singleItem:
        summary: Заказ с одной позицией
        value:
          items:
            - productId: product-42
              quantity: 2
```

Примеры тел ответов:

```json
{
  "id": "order-42",
  "status": "awaiting_payment"
}
```

```json
{
  "code": "INSUFFICIENT_STOCK",
  "message": "Недостаточно товара для заказа"
}
```

Каждый ответ связывают с соответствующим HTTP-статусом, а ошибки — с описанной схемой.

**Примеры должны соответствовать ограничениям схемы.** Проверяй обязательные поля, типы, форматы и значения `enum`.

На уровне медиатипа используют либо `example` для одного примера, либо `examples` для нескольких. Реальные персональные данные, секреты и рабочие токены не публикуют.

## 6.2. Публикация Swagger UI или Redoc

**Документацию строят из того же OpenAPI-контракта, который проходит ревью и проверки.** Отдельное ручное описание операций быстро начинает расходиться с ним.

```text
OpenAPI-контракт в репозитории
                ↓
Проверка синтаксиса, ссылок и примеров
                ↓
Сборка документации
                ↓
Публикация Swagger UI или Redoc
```

| Инструмент | Основное назначение |
|---|---|
| **Swagger UI** | Просмотр операций и интерактивные вызовы API |
| **Redoc** | Представление OpenAPI как удобной справочной документации |

Swagger UI может загружать документ по URL или получать его через конфигурацию. Redoc также строит представление из OpenAPI-описания. [Swagger UI](https://swagger.io/docs/open-source-tools/swagger-ui/usage/configuration/), [публикация Redoc](https://github.com/Redocly/redoc/blob/main/docs/deployment/intro.md).

Для публикации определяют:

- адрес документации и возможность скачать исходный контракт;
- версию API и окружение;
- доступность документации для нужной аудитории;
- поддерживаемые версии OpenAPI в выбранном рендерере;
- порядок обновления при выпуске.

**Интерактивный вызов — настоящий запрос.** Он может создать заказ или выполнить другую операцию. Для знакомства удобно использовать sandbox с тестовыми данными.

Красивое отображение не доказывает, что сервер соответствует контракту: это проверяют отдельно.

## 6.3. Описания, достаточные для вызова API

**Потребитель должен понимать операцию без чтения серверного кода.**

В документации отвечают на вопросы:

| Вопрос | Что описать |
|---|---|
| Куда обращаться? | Окружение, базовый URL, путь и метод |
| Как получить доступ? | Способ аутентификации и полномочия |
| Что передать? | Параметры, тело, заголовки и ограничения |
| Что вернётся? | Статусы, схемы и примеры |
| Что делать при ошибке? | Машинный код, допустимость повтора, способ уточнения результата |
| Есть ли особые правила? | Идемпотентность, пагинация, асинхронность, единицы измерения |

Неудачно:

> Создаёт заказ.

Лучше:

> Создаёт заказ и запускает резервирование. Возвращённое состояние ещё не означает успешную оплату. Для повтора того же запроса используйте прежний ключ идемпотентности. Текущее состояние доступно через операцию получения заказа.

**Уточняй неоднозначности:** сумма в рублях или копейках, время в какой зоне, включительны ли границы периода, что означает отсутствующее поле.

Полезная проверка — дать документацию разработчику, не знакомому с реализацией, и попросить выполнить основной сценарий.

## 6.4. Версионирование контракта вместе с API

**Контракт меняется в рамках того же изменения, что и поведение API.** Код, тесты и документация должны описывать одну версию решения.

Различай:

| Обозначение | Значение |
|---|---|
| **`openapi`** | Версия формата спецификации |
| **`info.version`** | Версия описываемого API по принятой политике |
| **`/v1` в URL** | Один из возможных способов обозначить версию интерфейса |
| **Git-коммит или тег** | Конкретная сохранённая редакция контракта |

Эти значения связаны процессом выпуска, но не обязаны совпадать.

Практические правила:

- хранить историю изменений и сохранять контракт каждого релиза;
- публиковать документацию, соответствующую развёрнутому API;
- планируемые возможности явно отделять от доступных;
- проверять совместимость при изменении полей, типов, статусов и требований;
- описывать устаревание операций и сроки прекращения поддержки.

**Обновление `info.version` не делает несовместимое изменение безопасным.** Потребителям всё равно нужен согласованный переход.

Если документация всегда собирается из основной ветки, она может показывать ещё не выпущенные возможности. Для production лучше связывать публикацию с конкретным релизом или явно обозначать различия.

**Запомнить:** хорошие примеры объясняют использование, единый контракт предотвращает расхождения, а версионирование связывает документацию с реально доступным API.

# 7. Контракт и реализация

## 7.1. Design-first и code-first

**Подходы различаются тем, где первоначально определяют API и из чего получают его описание.**

| | Design-first | Code-first |
|---|---|---|
| Начало работы | Согласование OpenAPI-контракта | Реализация операций и их описание в коде |
| Получение документа | Контракт пишут явно | Генерируют из аннотаций, типов или тестов |
| Преимущество | Потребители могут обсуждать интерфейс до реализации | Описание находится рядом с реализацией |
| Основной риск | Реализация может отстать от контракта | В контракт могут попасть случайные детали кода |

**Design-first:**

```text
Требования → Контракт → Ревью → Реализация → Проверка соответствия
```

**Code-first:**

```text
Требования → Код и описания → Генерация контракта → Ревью и проверки
```

Оба подхода требуют осознанного проектирования API. Code-first не означает «интерфейс не нужно обсуждать», а design-first не требует генерировать сервер. [Сравнение подходов](https://support.smartbear.com/swaggerhub/getting-started/introductory-topics/design-first-or-code-first-approach/).

**rswag — пример генерации из описанных интеграционных тестов:** он связывает операции, схемы и проверки ответов, затем формирует OpenAPI-документ. Это не автоматическое обнаружение всех гарантий приложения. [Документация rswag](https://github.com/rswag/rswag).

Определи источник истины и порядок обновления. Не стоит независимо редактировать сгенерированный документ и его исходные описания.

## 7.2. Проверка ответов по схемам

**Контрактный тест отправляет запрос приложению и проверяет фактический ответ относительно OpenAPI.**

Проверяют:

- HTTP-статус;
- медиатип, например `application/json`;
- обязательные заголовки;
- структуру и типы тела;
- обязательность полей, ограничения и варианты схем.

Пример:

```text
Контракт:
    id — обязательная строка
    quantity — обязательное целое число, минимум 1

Ответ:
    id: 42
    quantity: 0

Результат:
    нарушение типа id
    нарушение ограничения quantity
```

Нужны проверки успешных и существенных ошибочных ответов: отказ доступа, отсутствие ресурса, конфликт состояния.

В rswag объявленная схема ответа может проверяться при выполнении интеграционного теста. Но нужно проверить поддержку используемой версии схем и настройки строгости. [Проверки rswag](https://github.com/rswag/rswag#schema-validations).

**Соответствие схеме не доказывает правильность бизнес-результата.** Ответ с корректной структурой может содержать чужой заказ или неправильную сумму. Это проверяют отдельными утверждениями.

Кроме того, тест подтверждает только выполненные сценарии, а не все возможные ответы приложения.

## 7.3. Генерация не заменяет ревью

**Генератор воспроизводит описанный контракт, включая его недостатки.**

Он может создать:

- методы клиента;
- типы данных;
- сериализацию;
- серверные интерфейсы и заготовки.

Но не определяет самостоятельно:

- удобны ли операции потребителю;
- правильно ли выбраны статусы и обязательные поля;
- безопасны ли повторы;
- понятны ли ошибки;
- не раскрываются ли внутренние данные.

Пример: генератор успешно создаст клиент для операции возврата. Но если не описан ключ идемпотентности, клиент может не иметь безопасного способа повторить запрос.

На ревью проверяют **контракт и результат генерации**: названия методов, представление nullable, обработку `oneOf`, ошибки и сериализацию параметров.

**Успешная генерация означает, что инструмент обработал документ, а не что API хорошо спроектирован.**

## 7.4. Совместимые и ломающие изменения

**Совместимость оценивают относительно существующих потребителей:** продолжат ли они работать без обязательного обновления?

Направление имеет значение: сервер **принимает запросы**, клиент **принимает ответы**.

| Изменение | Возможное последствие |
|---|---|
| Добавить необязательное поле запроса | Обычно совместимо для старых клиентов |
| Сделать поле запроса обязательным | Старые запросы перестают проходить |
| Сузить допустимые значения запроса | Ранее корректные запросы могут отклоняться |
| Удалить используемое поле ответа | Ломает потребителей |
| Изменить тип или смысл значения | Может сломать обработку |
| Добавить поле ответа | Обычно совместимо, если клиенты допускают неизвестные поля |
| Сделать обязательное поле ответа необязательным | Клиенты могут не обработать его отсутствие |
| Добавить значение `enum` в ответ | Клиенты с закрытым перечнем могут сломаться |
| Изменить HTTP-статус или формат ошибки | Может нарушить логику клиента |
| Усилить требования к доступу | Может заблокировать существующих потребителей |

Например, разрешение нового статуса **в запросе** расширяет возможности сервера. Возвращение нового статуса **в ответе** расширяет набор значений, которые обязан понимать клиент.

**Структурной проверки недостаточно.** Замена рублей на копейки сохраняет тип числа, но ломает смысл контракта.

Зафиксируй политику совместимости, проверяй diff контрактов в CI и отдельно разбирай изменения поведения. Несовместимые изменения вводят через согласованную миграцию, период поддержки старого варианта или новую версию API.

**Запомнить:** выбранный способ разработки не отменяет проверок. Контракт, реализация и реальные ожидания клиентов должны оставаться согласованными.

# 8. Качество контракта

## 8.1. Валидация и правила команды

**Валидация проверяет соответствие документа спецификации. Линтинг проверяет дополнительные соглашения о качестве API.**

| Проверка | Пример проблемы |
|---|---|
| **Синтаксис YAML/JSON** | Ошибка отступов или повторяющийся ключ |
| **Структура OpenAPI** | Неправильный тип поля или отсутствие обязательного свойства |
| **Ссылки** | `$ref` указывает на отсутствующий компонент |
| **Правила команды** | Нет `operationId`, описания ошибки или согласованного тега |

**Spectral — настраиваемый линтер YAML/JSON с готовыми правилами для OpenAPI.** Команда может расширить базовый набор своими проверками.

Пример `.spectral.yaml`:

```yaml
extends:
  - spectral:oas

rules:
  operation-operationId: error
  operation-description: warn
```

Запуск:

```text
spectral lint openapi.yaml
```

Здесь отсутствие идентификатора операции считается ошибкой, а отсутствие описания — предупреждением. Набор правил нужно согласовать с командой. [Документация Spectral](https://github.com/stoplightio/spectral).

**Зелёный линтер не доказывает правильность контракта.** Он не определит, верно ли описана бизнес-операция, и не подтвердит поведение сервера. Поддержку используемой версии OpenAPI проверяют отдельно.

## 8.2. Полнота описания операций

**Полнота означает, что потребитель может правильно вызвать операцию и обработать существенные результаты.**

Для каждой операции проверяют:

- назначение, `operationId` и группировку;
- все фактически используемые параметры и их ограничения;
- тело запроса и поддерживаемые медиатипы, если тело предусмотрено;
- успешные и существенные ошибочные статусы;
- схемы содержимого и необходимые заголовки;
- аутентификацию и полномочия;
- примеры и особые правила поведения.

**Не каждой операции нужны параметры или тело.** Например, проверка здоровья может обходиться без них. У ответа `204` тела быть не должно.

Пример неполноты:

> Отмена возвращает `202`, но не объясняется, где проверить завершение.

Исправление:

> Описать, что отмена выполняется асинхронно, какие промежуточные состояния возможны и как получить текущий результат.

Схемы проверяют не только на наличие. `type: object` без свойств и ограничений может почти ничего не сообщать о реальном ответе.

## 8.3. Репозиторий и проверки в CI

**Контракт хранится под контролем версий и проверяется вместе с изменениями API.**

Пример структуры:

```text
api/
├── openapi.yaml
├── schemas/
├── examples/
└── .spectral.yaml
```

Типичный процесс:

```text
Изменение контракта
        ↓
Проверка структуры, ссылок и правил команды
        ↓
Проверка примеров и совместимости
        ↓
Тесты соответствия реализации
        ↓
Сборка документации
```

Нужно определить:

- источник истины: документ или описания, из которых он генерируется;
- версии инструментов и общие настройки;
- какие нарушения блокируют слияние;
- где сохраняются отчёты и собранная документация;
- с какой версией сравнивают совместимость.

**По умолчанию предупреждение линтера не обязательно приводит к падению CI.** Порог отказа задают явно согласно политике команды. [Поведение Spectral CLI](https://github.com/stoplightio/spectral/blob/develop/docs/guides/2-cli.md).

Сравнивать контракт полезно с базовой веткой и, при необходимости, с последней опубликованной версией: они могут различаться.

## 8.4. Ревью как изменения публичного API

**Контракт — обязательство перед потребителями, а не внутренняя техническая заметка.** Даже внутренний API может иметь несколько независимых клиентов.

На ревью проверяют:

| Область | Основной вопрос |
|---|---|
| **Назначение** | Понятна ли операция и соответствует ли требованиям? |
| **Совместимость** | Продолжат ли работать существующие клиенты? |
| **Семантика** | Сохранились ли смысл полей, единицы и правила? |
| **Безопасность** | Достаточны ли требования доступа и не раскрываются ли лишние данные? |
| **Ошибки** | Сможет ли клиент выбрать правильную реакцию? |
| **Переход** | Нужны ли уведомление потребителей, период поддержки или новая версия? |

Автоматический diff помогает найти удалённое поле или изменённый тип. Но он может не заметить, что сумма теперь выражается в другой валюте или операция иначе обрабатывает повторы.

В описании MR фиксируют изменение поведения, затронутых потребителей, результаты проверок и план перехода. Существенные изменения обсуждают с владельцами клиентов до выпуска.

**Запомнить:** качественный контракт корректен по форме, достаточен по содержанию, проверяется в CI и проходит ревью с учётом реальных потребителей.
