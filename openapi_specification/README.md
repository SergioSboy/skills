# OpenAPI Specification / Swagger

## Цель

Научиться описывать HTTP API контрактом OpenAPI так, чтобы документация,
примеры и проверки соответствовали реальному поведению сервиса.

## План изучения

### 1. Основные понятия

- Отличать OpenAPI Specification от Swagger UI, Swagger Editor и генераторов
  кода.
- Понять, что Swagger 2.0 — прежнее имя спецификации, а актуальная версия —
  OpenAPI 3.x.
- Разобрать структуру документа: `openapi`, `info`, `servers`, `paths`,
  `components`, `security`, `tags`.
- Определить потребителей контракта: клиентские команды, тестирование,
  архитектура, шлюзы.

### 2. Описание операций

- Описывать path, method, `operationId`, краткое и полное описание, теги.
- Задавать параметры path, query, header и cookie.
- Описывать тело запроса и поддерживаемые content types.
- Разделять успешные и ошибочные ответы по HTTP-статусам.

### 3. Компоненты и переиспользование

- Выносить схемы, параметры, ответы и примеры в `components`.
- Использовать `$ref` и не дублировать одинаковые модели.
- Описывать пагинацию, общий формат ошибок и общие заголовки один раз.
- Учитывать ограничения `$ref` в OpenAPI 3.0 и изменения в OpenAPI 3.1.

### 4. Схемы данных

- Описывать объекты, массивы, `enum`, nullable и форматы (`date-time`, `uuid`,
  `email`).
- Задавать `required`, `additionalProperties`, `readOnly` и `writeOnly`.
- Отличать схему OpenAPI от JSON Schema и понимать их сближение в OpenAPI 3.1.
- Описывать варианты ответа через `oneOf` и `discriminator`, где это оправдано.

### 5. Безопасность

- Описывать схемы безопасности: HTTP Bearer, API key, OAuth 2.0, OpenID Connect.
- Применять требования безопасности ко всему API и переопределять их на
  отдельных операциях.
- Не помещать секреты и реальные токены в примеры.
- Описывать scopes и ответы `401` и `403`.

### 6. Примеры и публикация

- Добавлять примеры запросов, успешных ответов и ошибок.
- Публиковать Swagger UI или Redoc из того же контракта.
- Писать описания, по которым API можно вызвать без чтения кода.
- Версионировать контракт вместе с API.

### 7. Контракт и реализация

- Сравнить design-first и code-first (например, rswag или аннотации).
- Проверять, что ответы приложения соответствуют схемам.
- Понимать, что генерация клиента или сервера не заменяет ревью контракта.
- Зафиксировать, какие изменения совместимы, а какие ломают клиентов.

### 8. Качество контракта

- Валидировать документ и проверять его правилами команды (например, Spectral).
- Проверять полноту: у каждой операции есть параметры, статусы и схемы.
- Хранить спецификацию в репозитории и проверять её в CI.
- Ревьюить изменение контракта как изменение публичного API.

## Практический проект

Описать контракт OpenAPI 3 для API заказов:

- ресурсы заказа, позиций и статуса;
- создание, чтение списка, чтение одного заказа и отмена;
- единый формат ошибок;
- пагинация списка;
- аутентификация Bearer;
- примеры успешных и ошибочных ответов;
- проверка документа валидатором и линтером;
- сверка хотя бы одной операции с фактическим ответом теста или стенда.

## Критерии завершения

- Документ проходит валидацию OpenAPI и правила линтера.
- У каждой операции заданы параметры, тело запроса, статусы и схемы.
- Примеры соответствуют схемам.
- По контракту можно вызвать API и понять возможные ошибки.
- Зафиксировано, какие изменения контракта совместимы, а какие нет.
