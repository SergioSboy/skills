# Валидация JSON Schema

## Цель

Научиться описывать и проверять структуру JSON-документов с помощью JSON Schema,
отделяя проверку формата от бизнес-правил.

## План изучения

### 1. Основные понятия

- Понять назначение JSON Schema как контракта структуры документа.
- Разобрать диалекты draft-07, 2019-09 и 2020-12 и зачем фиксировать `$schema`.
- Отличать проверку схемы от бизнес-валидации и авторизации.
- Определить, где применяется схема: тело API, событие, конфигурация, сообщение
  брокера.

### 2. Типы и ограничения

- Описывать `object`, `array`, `string`, `number`, `integer`, `boolean` и
  `null`.
- Задавать `required`, `properties`, `additionalProperties`, границы длины и
  значения, `pattern`, `format` и `enum`.
- Учитывать, что проверка `format` зависит от настроек валидатора.
- Различать отсутствие поля, `null` и пустое значение.

### 3. Композиция схем

- Выносить повторяемые определения в `$defs` и ссылаться на них через `$ref`.
- Применять `allOf`, `anyOf`, `oneOf` и `not`.
- Описывать условные требования через `if` / `then` / `else`, если диалект это
  поддерживает.
- Не переносить бизнес-процесс в чрезмерно сложную схему.

### 4. Эволюция схем

- Добавлять необязательные поля без поломки существующих потребителей.
- Понять, почему удаление поля, смена типа и сужение `enum` ломают совместимость.
- Версионировать схемы API и событий.
- Зафиксировать, какая версия схемы считается актуальной и где она хранится.

### 5. Валидация на границе

- Выбрать валидатор и зафиксировать поддерживаемый диалект.
- Проверять вход до выполнения бизнес-логики.
- Возвращать путь к полю, код и понятное сообщение без внутренних деталей.
- Отделять ошибку схемы от ошибки бизнес-правила.

### 6. Сообщения и события

- Описывать конверт: идентификатор, тип, время, версия схемы и полезная
  нагрузка.
- Проверять сообщение перед публикацией и при получении.
- Определить реакцию на невалидное сообщение: отказ, повтор, очередь ошибок,
  метрика.
- Не принимать молча сообщение неизвестной или несовместимой версии.

### 7. Проверка самих схем

- Хранить валидные и невалидные примеры рядом со схемой.
- Проверять, что валидные примеры проходят, а невалидные отклоняются по
  ожидаемой причине.
- Проверять совместимость при изменении схемы.
- Запускать эти проверки в CI.

### 8. Границы схемы

- Зафиксировать, что схема не проверяет уникальность в базе, права доступа и
  инварианты процесса.
- Оставлять проверку на границе доверия, даже если похожая проверка есть внутри
  сервиса.
- Оценить стоимость валидации на горячем пути.
- Описать, какие проверки остаются в коде и почему.

## Практический проект

Описать и проверить JSON Schema для тела создания заказа и события
`OrderPlaced`:

- у каждой схемы указан диалект;
- не меньше трёх невалидных примеров на схему: нет обязательного поля, неверный
  тип, лишнее поле при запрете дополнительных свойств;
- отчёт валидатора содержит путь к ошибке;
- правило эволюции: какие изменения схемы допустимы;
- описание реакции на сообщение неизвестной версии.

## Критерии завершения

- Валидные примеры проходят, невалидные отклоняются с указанием поля.
- Ошибки формата отделены от бизнес-ошибок.
- Для схем сообщений описаны версия и поведение при несовместимом сообщении.
- Проверка схем и примеров запускается автоматически.
- В документе явно перечислено, что схема не проверяет.
